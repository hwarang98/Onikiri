## 12-1 — 폰트 파이프라인 근본 수정

### 무엇이 문제였나

10단계에서 "폰트 GUID 보존"을 고쳤다고 보고했는데 그것은 틀린 수정이었다.
검증을 **문자셋이 변하지 않은 경우로만** 했기 때문이다. 11단계에서 문자셋이
231 → 237로 늘자 씬의 모든 한글이 깨졌고, 그때는 삭제 후 재생성으로 되돌렸다.

원인은 애셋 오브젝트를 매번 새로 만든 데 있었다. `TMP_FontAsset`을 지우고
다시 만들면 GUID와 머티리얼 fileID가 바뀌고, 씬에 저장된 참조는 그 순간
끊긴다. 문자셋이 그대로면 새 애셋이 우연히 같은 fileID를 받는 일이 잦아서
문제가 드러나지 않았을 뿐이다.

### 수정

`PixelFontAssetBuilder.Build()`가 애셋을 **제자리에서** 갱신한다.
TMP 자신의 API를 쓴다.

```csharp
fontAsset.atlasPopulationMode = AtlasPopulationMode.Dynamic;
fontAsset.ClearFontAssetData(true);
fontAsset.TryAddCharacters(charset, out missing);
fontAsset.atlasPopulationMode = AtlasPopulationMode.Static;
ApplyPointFiltering(fontAsset);
ApplyBitmapShader(fontAsset);
fontAsset.ReadFontAssetDefinition();
```

오브젝트를 새로 만들지 않으므로 GUID·머티리얼 fileID·아틀라스 텍스처가
동일성을 유지한다. 재생성은 되돌릴 수 없는 변화(폰트 파일 교체, 샘플링 크기,
아틀라스 크기)에서만 하고, 그때는 경고를 남긴다.

### 중간에 잡은 버그

`NeedsRecreate`가 `fontAsset.sourceFontFile != sourceFont`를 비교하고 있었다.
그런데 TMP는 `AtlasPopulationMode.Static`에서 이 참조를 **null로 만든다.**
실측하니 `sourceMatches: false, sourceFontFile: "null"`이면서 pointSize 55,
padding 1, atlas 1024×1024는 모두 일치했다. 이 비교 때문에 제자리 갱신 경로가
한 번도 타지 않고 매번 재생성으로 빠지고 있었다. 비교를 제거했다.

### 실측 (요청하신 두 가지 모두)

기준선을 기록한 뒤 `UIStrings.txt`에 글자 10개를 추가하고 **Build Combat
Content 없이** 폰트만 다시 구웠다.

| 항목 | 재빌드 전 | 재빌드 후 |
|---|---|---|
| 글리프 수 | 253 | **263** |
| 폰트 애셋 GUID | `d67e99be6fcf9eb48b43fb792bd915ff` | 동일 |
| 씬 참조 fileID (폰트) | `11400000` | 동일 |
| 씬 참조 fileID (머티리얼) | `6611367536665788242` | 동일 |
| "recreating" 경고 | — | 없음 |

플레이 모드에서 확인: **TMP 라벨 53개 전부 폰트와 머티리얼을 유지**
(`{ labels: 53, 폰트정상: 53, 끊김: 0 }`). 화면도 한글이 정상이다
(`Assets/Screenshots/step12_font_root.png`).

### VerifyWiring 글리프 검사

빌드가 씬의 모든 TMP 문자열을 훑어 구워지지 않은 글자를 찾는다.

대조 상대는 `FontCharset.txt`가 **아니라 폰트 애셋의 글리프 표**다. 문자셋
파일은 아틀라스와 따로 갱신될 수 있어서, 파일에는 있는데 아틀라스에는 없는
상태가 존재한다. 화면에 □가 뜨는지를 실제로 결정하는 것은 아틀라스 쪽이다.
라벨마다 자기 폰트에 물어보므로 한글용/숫자용 폰트가 섞여 있어도 각자 맞는
표를 본다.

**고치기 전에 검사가 나쁜 상태를 잡는지 먼저 확인했다.** 씬 라벨 하나에
안 구운 글자를 일부러 넣었다.

```
cleanPass=True  dirtyPass=False  restoredPass=True

Font 'Galmuri11 SDF' is missing glyphs used in the scene: "뷁쒫"
 - add them to Assets/_Project/Data/UIStrings.txt
   and run Onikiri/Art/Build Pixel Font Assets
```

**한계 (알고 남긴 것)**: 코드가 런타임에 조립하는 문구(보스 실패 안내 등)는
씬에 없으므로 여기서 잡히지 않는다. 그것들은 `UIStrings.txt`에 손으로
적어두는 수밖에 없고, 이 검사는 빌더가 씬에 써넣는 라벨을 담당한다.
9단계(보스 이름)와 11단계(사망 문구)에서 깨졌던 것이 정확히 이 사각지대라,
없앴다고 말하지 않고 범위를 적어둔다.

## 12-2 — EXP / 레벨 / 스탯 포인트

### 구조

| 파일 | 역할 |
|---|---|
| `ExpCurve` | 획득량과 필요량. 순수 함수 |
| `StatPointCurve` | 포인트당 증폭, 상한 |
| `CharacterLevel` | 경험치·레벨·포인트를 들고 있는 런타임 |
| `LevelHud` | 상단 레벨/경험치 바/레벨업 버튼 |
| `StatPointButton` | 증폭 축 한 줄 |
| `LockedTab` | 잠긴 탭 |

### 획득

경험치는 골드와 **같은 자리에서** 들어온다
(`EnemySpawner.OnEnemyKilled`). 보상 경로를 둘로 나누면 언젠가 한쪽만 도는
상태가 생기고, 그것은 9단계에서 보스 골드를 스포너에 맡긴 것과 같은 이유다.

값은 스폰 시점에 확정한다(`Enemy.ExpReward`). 스테이지만의 함수라 죽는 순간
계산해도 대개 같은 답이지만, 보스를 잡아 스테이지가 오르는 그 프레임에 아직
걸어오던 잡몹이 죽으면 답이 갈린다.

**요괴 종류별로 다르게 주지 않는다.** 다르게 주면 가중치 추첨이 진행 속도에
섞여 들어가고, `ExpCurve`가 재는 "스테이지당 경험치"가 추첨 결과에 따라
흔들린다.

### 레벨업은 수동

경험치가 차도 자동으로 오르지 않는다. 자동이면 레벨업이 화면 구석에서 혼자
일어나고, 스탯 포인트가 쌓여 있는데 안 쓰는 상태가 방치된다.

버튼 한 번에 **한 레벨씩**이다. 한꺼번에 올리면 포인트가 뭉텅이로 들어오고
그것은 다시 "남아 있는데 안 쓰는" 상태다.

초과분은 사라지지 않는다. 실측:

```
AddExp(3레벨분) -> pending=3
TryLevelUp x3   -> Lv.1 -> Lv.4, leftover=7.24255743999999
                   (넣기 전 보유량 7.24255744와 일치)
```

레벨업 버튼은 올릴 수 있을 때만 보인다. 항상 띄워두고 비활성으로 두면
방치형에서 곧 배경이 된다.

### 스탯 포인트 — 곱셈, 상한 500

포인트당 ×1.005, 축당 500 상한. 골드 강화와 **곱해진다.** 더하면 초반에는
스탯 포인트가 전부이고 후반에는 있으나 마나 한 값이 된다.

증폭은 공격력과 최대 체력에만 붙는다. 공격속도·치명타에 고루 뿌리면 골드
축들의 상대 효율(`UpgradeEfficiency`가 재는 값)이 레벨에 따라 흔들린다.

**회복에는 붙이지 않는다.** 회복이 최대 체력의 비율이라
(`HealthRegenCurve`) 체력 증폭이 오르면 초당 회복량이 이미 함께 오른다.
여기서 또 곱하면 체력 포인트 하나가 유효체력을 두 번 밀어올린다.

#### 끝단 실측 (11단계 ChapterHealthMultiplier 사건 재발 방지)

상수를 선언만 하고 값 흐름에 연결하지 않는 실수를 막기 위해, 게임을 돌린
상태에서 실제 전투 스탯을 쟀다.

```
levelups TrueTrueTrue -> Lv.4  unspent=3
damage after level (포인트 미사용): 5 -> 5          <- 레벨만으로는 안 오른다
공격 2 / 체력 1 찍음
damage    5 -> 5.050125   ratio=1.010025  expected=1.010025   ✓
maxHealth 161.051 -> 161.856255  ratio=1.005  expected=1.005  ✓
4번째 찍기 시도: False    <- 남은 포인트 0
```

### 세이브 v4 → v5

새 필드: `characterLevel`, `exp`, `attackPoints`, `healthPoints`,
`expPerSecond`.

**남은 포인트는 저장하지 않는다.** 총 지급량은 레벨의 함수이고 쓴 양은 두
축의 합이므로, 남은 양을 따로 적으면 셋이 어긋났을 때 무엇이 맞는지 알 수
없다.

v4 세이브는 **Lv.1에서 시작한다.** 지나온 진행만큼 소급할 수도 있지만
그러면 그만큼의 스탯 포인트가 함께 들어오고, v4 플레이어가 12단계
밸런스로 계산되지 않은 증폭을 얹은 채 다음 보스를 만난다.

테스트: 마이그레이션 / 멱등성(두 번 돌려도 진행 유지) / 미래 버전 거부 /
나머지 진행 보존.

`CharacterLevel.Restore`는 찍은 합이 지급량을 넘으면(상한이 내려갔거나 손상된
파일) 넘친 만큼 깎고 경고한다. 그냥 두면 `UnspentPoints`가 계속 0이라
정상처럼 보이는데 실제 스탯은 받지 않은 포인트를 반영한다.

### 오프라인 경험치

골드와 **같은 함수**(`IdleIncome.Reward`)를 쓴다. 둘의 계산이 갈리면 방치
효율이 재화마다 달라지고, 그때부터 "자리를 비우면 레벨만 앞선다"가 생긴다.

초당 경험치는 초당 골드에서 환산한다(`GameSession.EstimateExpPerSecond`).
처치 속도 계산이 `IdleIncome` 안에 두 상한(화력/공급)으로 들어 있어서,
여기서 다시 세우면 그 두 상한을 복제하게 되고 한쪽만 고쳐지는 날 방치 골드와
방치 경험치가 서로 다른 처치 속도를 쓴다.

### 경험치 흡수 연출

데미지 팝업 풀을 **그대로 재사용한다.** 별도 풀을 두지 않는 이유는 두 연출이
서로 배타적으로 많아지기 때문이다 — 타격이 잦은 구간은 처치가 잦은 구간이라,
풀을 나누면 양쪽 모두 최대치를 잡아둬야 한다.

호를 그리며 사라지는 대신 경험치 바로 빨려 들어간다. 위로 떠서 사라지는 것은
"여기서 무슨 일이 있었다"이고, 어딘가로 날아가는 것은 "그것이 저기로 갔다"이다.

실측: 요괴 4마리를 동시에 처치 → 활성 팝업 5개 `[+7 +7 5 +7 +7]`
(`5`는 진행 중이던 데미지 숫자). 색은 경험치 바의 채움색과 같다.
`Assets/Screenshots/step12_exp_absorb.png`

### 잠긴 탭

스킬 Lv.10 / 전직 Lv.30. 자리만 잡고 **거짓말은 하지 않는다** — 눌러도 아무
일이 없는 탭이 아니라 잠긴 모양으로 서 있고 필요 레벨을 함께 적는다.
해금 레벨에 도달하면 표시만 풀리고, 실제 화면은 다음 단계에서 붙는다.
`LockedTab.Refresh`의 `button.interactable = false` 한 줄이 사라지는 것이
스킬/전직이 실제로 구현됐다는 표시가 된다.

### 만들면서 잡은 UI 버그

증폭 값 라벨이 `×1.005 → ×1.010`을 **둘 다 `×1.01`로** 찍고 있었다. 소수
둘째 자리로는 포인트당 0.5%가 정확히 그 자리에서 사라져서, 화면에서는 눌러도
아무것도 안 바뀌는 것으로 보인다. `UpgradeButton`이 `Format` 대신
`FormatStat`을 쓰는 것과 같은 이유이고, 같은 실수를 한 번 더 한 것이다.
셋째 자리로 바꿨다.

### 알고 남긴 표시

경험치 바가 `202 / 75`처럼 필요량보다 큰 값을 찍는다. 레벨업이 수동이라
초과분이 쌓인 상태이고, 옆의 `레벨업 2` 버튼이 그 이유를 말한다.
11단계의 `2811 / 2810`과는 성격이 다르다 — 그쪽은 반올림이 만든 거짓이었고
이쪽은 실제로 보유한 양이다. 다만 12-3에서 UI를 다시 그릴 때 다시 볼 값이다.

## 12-4 — 시뮬레이션 EXP 확장

`StageSimulation`이 경험치·레벨·스탯 포인트를 함께 굴린다. 증폭은
`UpgradeSystem.Apply`와 **같은 순서로** 곱한다 — 두 곳이 갈리면 시뮬레이션이
게임과 다른 밸런스를 잰다.

포인트 정책은 골드 축과 같다: 생존이 모자라면 체력, 아니면 공격력.
골드가 들지 않으므로 미룰 이유가 없고, 미루면 골드 축이 그만큼을 대신 메워
두 축의 기여가 섞인다.

### 필요 EXP 곡선 역산

목표는 "초반 30초/레벨, 후반 완만"이었다. 상수 조합
(`BaseRequirement` × `RequirementStep`)을 훑어 고른 값:

```
BaseRequirement  = 48     (Lv.1 -> Lv.2)
RequirementStep  = 1.26   (레벨당)
ExpStageGrowth   = 1.16   (스테이지당 획득량)
```

측정 결과:

| 구간 | 소요 | 레벨 | 초/레벨 | 레벨/스테이지 |
|---|---|---|---|---|
| 1~10 | 266s | 10 | 26.6s | 1.00 |
| 11~20 | 225s | 7 | 32.2s | 0.70 |
| 21~30 | 193s | 7 | 27.6s | 0.70 |
| 31~40 | 169s | 6 | 28.1s | 0.60 |

**여기서 솔직하게 적어야 할 것**: "후반 완만"이 벽시계 초/레벨로는 깔끔하게
나오지 않는다. 후반으로 갈수록 **스테이지 자체가 짧아지기** 때문이다
(잡몹 구간이 스폰 하한 0.4초 × 10 = 4초로 수렴한다). 그래서 레벨이 느리게
오르는데도 초/레벨 숫자는 다시 내려간다.

리듬이 실제로 완만해지는지는 **스테이지당 레벨 수**로 봐야 하고, 그쪽은
1.00 → 0.70 → 0.70 → 0.60으로 분명히 내려간다. 테스트도 이 지표로 잰다.

기하급수 곡선 둘로는 초/레벨이 어느 상수를 넣어도 **일정한 값으로 수렴한다**
(정상 상태에서 레벨/스테이지 = ln(획득 증가율)/ln(필요 증가율)로 고정된다).
계속 늘어나는 초/레벨을 만들려면 필요량을 지수보다 빠르게 키워야 하는데,
그러면 어느 지점부터 레벨이 사실상 멈추고 증폭 축 둘이 화면만 차지한다.
그래서 "수렴하는 값을 초반보다 느리게" 잡는 쪽을 골랐다.

### 레벨이 골드를 앞지르지 않는가

두 축이 공격력에 곱하는 배수로 비교한다.

| 스테이지 | 공격력 Lv. | 골드 강화 배수 | 레벨 증폭 | 증폭/골드 |
|---|---|---|---|---|
| 5 | 24 | ×13.6 | ×1.020 | 0.075 |
| 20 | 83 | ×10,861 | ×1.067 | 0.0001 |
| 40 | 162 | ×8.4e7 | ×1.122 | ~0 |

앞지르지 않는다. 격차는 **벌어지는 방향**이고, 테스트가 이 관계를 못 박는다
(`LevelGrowth_DoesNotOutpaceGoldGrowth`).

#### 다만 — 지시하신 계수로는 증폭이 매우 작다

숫자를 그대로 읽으면 이렇다. 40스테이지에서 골드 강화는 ×8,400만인데 스탯
포인트는 ×1.12다. **증폭이 DPS에 기여하는 몫이 사실상 0이다.**

상한까지 다 찍어도 축당 ×12.11이고, 그것은 공격력 강화 **22레벨**에 해당한다.
40스테이지 시점의 공격력이 이미 Lv.162이므로, 500포인트를 전부 부어도 골드
강화 열 몇 레벨을 앞당기는 정도다.

지시하신 `×1.005/포인트, 상한 500`을 그대로 구현했고 수치도 그대로
보고한다. 다만 "보조 축"이라기보다 **장식에 가까운 크기**라, 다음 단계에서
조정할지 판단이 필요하다. 선택지는 대략 셋이다.

1. 포인트당 배수를 올린다 (×1.02면 상한에서 ×2만 배 — 이번엔 너무 크다)
2. 레벨당 포인트를 늘린다 (레벨 수 자체는 그대로 두고 기여만 키움)
3. 증폭을 곱셈이 아니라 **골드 강화 레벨 보너스**로 바꾼다
   (예: 포인트 하나가 공격력 강화 +1레벨과 같은 효과) — 골드 축과 같은
   지수를 타므로 후반에도 비중이 유지된다

3번이 구조적으로 맞아 보이지만, 이번 단계 지시 범위 밖이라 손대지 않았다.
