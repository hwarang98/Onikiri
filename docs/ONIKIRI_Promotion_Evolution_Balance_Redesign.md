### 1.2 v20 → v21 예정 마이그레이션

```
evolutionTier = max(기존 evolutionTier, 지나온 게이트 수)
지나온 게이트 수 = maxStageReached 이상인 게이트 스테이지(30/40/50/70/100/150)의 개수
```

| 규칙 | 이유 |
|---|---|
| `max` | ① 산 것을 뺏지 않는다 ② 진행을 되돌리지 않는다 ③ **밴드가 게이트 기반 티어를 가정하므로 게이트를 지난 플레이어는 그 티어를 가져야 계약이 성립한다** |
| 멱등 | `max`라 두 번 돌려도 안 움직인다 |
| 손실 | 없음 — 값이 줄지 않는다 |
| 기본 이름·외형·오라 | 새 `evolutionTier`에 맞춰 **자동 적용** (별도 저장 없음) |

**결과를 인정한다**: 기존 플레이어(st200대)는 배수 여섯 칸과 최종 외형을 전부
무료로 얻는다. 배수는 밴드 계약의 요구이고, 외형은 배수와 분리하지 않기로 한
결정의 결과다.

Firebase 병합: `evolutionTier`가 **무료·단조 증가·재화 비결합**이 되어
**`max` 병합이 안전하다.** 트랜잭션이 필요한 필드가 이 시스템에서 사라졌다.

## 2. `EvolutionCompensation` 지수 재유도

### 2.1 오버레이 모형과 그 정당성

지수를 일곱 번 바꿔 돌릴 수 없으므로(프로덕션 상수) 오버레이로 잰다. 그런데
그것보다 나은 이유가 있다 — **보정은 구매 궤적에 되먹이지 않는다.** `Buy()`가
보는 것은 골드 수입·강화 비용·생존 목표뿐이고 셋 다 보스 **체력**과 무관하다.
그래서 중립 세계 하나만 돌려 두면 어떤 지수의 세계든 곱셈 한 번으로 재구성된다.

```
보스 여유   neutral x A^(1-e)
보스 처치   neutral x A^(e-1)
생존 여유   neutral 그대로
잡몹 시간   neutral 그대로 (st11부터 스폰 하한에 붙어 화력과 무관)
```

두 검사가 이 모형을 못 박는다:

| 검사 | 결과 |
|---|---|
| `OverlayModel_MatchesTheSimulation` | st51~200에서 예측/실측 비가 **0.95~1.02** 안 |
| `SurvivalMargin_DoesNotRespondToTheEvolutionMultiplier` | 체력 배수 ×1.77인데 생존 비 **0.97~1.03** |

두 번째가 중요하다. **생존은 파생값이 아니라 목표값이다** — 생존 루프가
`EffectiveHealth >= 보스 피해 × 1.15`까지만 사므로, 체력 배수가 공짜로 와도
강화 레벨을 덜 사서 같은 목표에 닿는다.

### 2.4 권장 지수 — **0.00 (보정항 제거)**

근거:

1. **기존 근거가 소멸했다.** 33단계가 0.42를 고른 이유는 "무과금은 1티어,
   과금은 여섯"이었다. 전원이 무료로 같은 티어를 받으면 그 분리가 없다.
2. **밴드는 고를 근거가 되지 못한다** — 후보 일곱이 전부 통과한다.
3. **체감이 유일한 차별자이고 0.00이 최대다.** 문 하나가 +10~20%, 보스 처치가
   9~17% 빨라진다. 0.50 이상은 최소 체감이 5% 아래로 떨어져
   `FeltGain_StaysAboveTheMilestoneFloor`가 기각한다.
4. **가장 단순하다.** `BossHealthForStage`의 곱이 하나 줄고, 코리더 불변이
   계수가 아니라 **"항이 없음"**으로 지켜진다.

`RecommendedExponent_PassesEveryContract`가 이 값 하나를 못 박는다. 권장을
바꾸려면 `PromotionBandModel.RecommendedExponent` 한 줄만 고치면 된다.

**대안: e = 0.30.** 천장 여유를 조금 더 남긴다(추종 일반 3.13 대 3.32).
미래 축을 위한 헤드룸을 우선한다면 이쪽이고, §7의 승인 항목으로 올린다.

### 3.2 하한 화력 0.70 / 0.50배는 어떻게 되는가

전투 시뮬레이션이 답한다(§5.4) — 0.70×는 62.6초에 통과하고, 0.50×는 문1에서
사망하고 문2~6은 86초에 통과한다. 즉 **0.70×는 파밍 없이 넘고, 0.50×는 문1에서
파밍이 필요하다.** 위 표의 "파밍 5분/10분" 행이 그 세계의 도달일이다.

### 3.3 파밍 되먹임의 크기 — 무시할 수 없다

`FarmingFeedback_IsLargeEnoughToNeedItsOwnModel`이 재는 값:

```
5분 파밍 골드 / 그 게이트 보스 보상 = 게이트 여섯에서 모두 5배 이상
(st30 기준 43배, 스테이지 약 9개 분량의 수입)
```

**그래서 파밍이 0이 아닌 앵커를 고르면 별도 되먹임 모형이 필요하다.** 이 장부는
파밍 시간과 골드를 세어 보고할 뿐, 그 골드가 화력으로 바뀌는 경로는 모형화하지
않는다 — 그것은 `StageSimulation`의 일이다. 권장 앵커(§5)에서는 파밍이 0이라
이 항이 열리지 않는다.

### 3.4 계산기에서 고친 것 — 예약 규칙

무료 세계에서 배정률(`alpha`)이 뽑기 지출을 움직이는 버그가 드러났다. 뽑기 예약이
**배정 예산 전체**를 묶고 있어서, 쓸 곳 없는 예산이 뽑기를 막았다. 예약을
**아직 안 낸 승급 비용까지만**으로 고쳤다. 비용이 0이면 예약도 0이다.

그 결과 `AllocationPolicy_NoLongerChangesAnything`이 통과한다 — **배정률이
아무것도 바꾸지 않는다.** v1.2~v1.4에서 `alpha`가 문제였던 이유는 그것이 진행과
파워 수령을 결정했기 때문이고, 비용이 0이면 곱할 것이 없다. **플레이어 행동
가정이 계약에서 완전히 빠졌다.**

## 4. `TrialPowerScore` 산식과 포함 범위

### 4.1 무엇을 세는가

여섯 항. **전부 초당 피해로 환산한다.** 무기·장비 배수와 귀문으로 받은
`evolutionTier` 배수는 각 항에 **이미 곱해져 있다**(곱 자리가
`UpgradeSystem.Apply` 한 곳이므로 런타임에서도 자연히 그렇게 된다).

| 항 | 내용 |
|---|---|
| `AutoAttack` | 기본 공격력 × 공격속도 × 치명타 기대배수(확률·배율 포함) |
| `Skills` | 장착 오의별 (배율 × 공격력 × 상성) / 쿨타임. **다단은 타수를 합산** |
| `MultiHit` | 위에 안 들어간 다단(연격 등)의 몫 |
| `DamageOverTime` | 지속 피해의 초당 환산 |
| `Companions` | 동료(펫)의 초당 피해 |
| `BossApplicableSpecials` | 처형 등 특수 규칙의 **보스 적용값**. 잡몹 전용 규칙은 0 |

마지막 항이 중요하다 — 귀문의 적은 셋 다 보스다. 잡몹 기준으로 세고 보스전에서
안 듣는 축이 점수를 부풀리면 **그 플레이어만 손해를 본다.**

### 4.2 언제 정하는가 — 입장 시 한 번

```
ref  = 귀문 총 체력 / 41초        <- 시험 자신에서 나온다. 별도 곡선 상수 없음
power = TrialPowerScore.Total

power <= ref :  damageScale = 1
power >  ref :  effectivePower = ref * pow(power / ref, k)
                damageScale    = effectivePower / power
```

**`damageScale` 하나를 입장 시 계산하고, 귀문 안의 모든 플레이어 측 피해 경로
(평타·오의·다단·지속·동료·특수)에 같은 값을 곱한다.**

### 4.3 타격당 적용 금지 — 검사가 지킨다

| 검사 | 무엇을 막는가 |
|---|---|
| `EveryDamageSource_GoesThroughTheCommonScale` | 항별로 곱한 합 == 총합에 곱한 값. 동료·지속·다단·특수가 각각 우회하지 않는지 개별 단언 |
| `SameScore_DifferentBuildShape_GetsTheSameEffectivePower` | 평타 90% 빌드와 오의 90% 빌드가 같은 총점이면 실효도 같다. 타격 단위로 걸면 여기서 갈린다 |
| `DamageScale_IsOneAtOrBelowTheReference` | 기준 이하를 깎지 않는다 |
| `MorePower_AlwaysMeansMoreEffectivePower` | 화력을 올리면 실효도 반드시 오른다 |
| `Reference_IsDerivedFromTheTrialItself` | 기준이 귀문 총 체력에서 유도된다 |

### 4.4 런타임 구현 시 확인할 것 (2단계)

- `damageScale`을 적용하는 지점이 **하나**여야 한다. 피해 계산의 마지막 곱 자리
- 동료(`PetCombat`)와 지속 피해가 그 자리를 지나는지
- 입장 후 강화·장비 변경이 막혀 있으므로(패널 잠금) 점수를 다시 계산할 필요가 없다

## 5. 소프트캡 k 후보 비교

### 5.1 캡이 필요한 이유 — 산수로 증명된다

`WithoutTheSoftCap_NoAnchorCanSatisfyBothPlayers`가 재는 값:

```
하나의 M이 두 플레이어에게 주는 시간의 비 = 두 플레이어의 DPS 비
게이트 5·6에서 그 값이 x3.61
밴드 [35, 55] 가 허용하는 최대 비 = 55/35 = 1.571
```

**캡 없이는 어떤 `M`으로도 둘을 동시에 넣을 수 없다.**

### 5.2 앵커 = 하한 45초

```
M(gate) = (45초 - 전환 4초) / 보석 하한 플레이어의 그 게이트 보스 처치 시간
        = 1.74 / 1.68 / 1.49 / 1.91 / 4.75 / 5.36
```

### 7.2 `alpha = 1.00 / 0.40 / 0.25`가 전부 같다

세 배정률의 표가 **한 글자도 다르지 않다.** 승급 비용이 0이라 배정할 것이
없기 때문이고, `AllocationPolicy_NoLongerChangesAnything`이 그것을 단언한다.

**"alpha는 플레이어 행동 가정이지 게임이 보장하는 계약이 아니다"라는 지적이
구조로 해소됐다** — 가정 자체가 결과에 닿지 않는다.

### 7.3 UX 개선 방향과의 충돌 해소

기존 방향은 "상점(st14)·스킬 뽑기(st41)·동료(st31)를 빠르게 체험시킨다"이다.
v1.3 유료안은 **30일까지 유료 뽑기 0회**로 정면 충돌했다.

원인은 총액이 아니라 **우선순위 자리**였다 — 경지가 방어구 다음·동료 앞이라
1~3일에 지갑 950을 통과했다. 비용이 0이 되면서 그 자리가 사라졌고,
`PaidGachaIsReachableWithinThirtyDays`(30일에 10연 3회 이상)와
`CoreAxesFinishWithinAMonth`(무기·동료·방어구 전부 30일 내)가 계약이 됐다.

## 10. 결론

1.6단계는 v1.4가 남긴 미지수를 **계산기와 검사로** 닫았다.

```
지수         후보 일곱 실측 -> 권장 0.00 (밴드 동률, 체감 최대, 항이 사라진다)
통합 장부    귀문 시간 여섯 항이 계산기에 들어갔다. 손계산 표를 폐기했다
소프트캡     TrialPowerScore 산식 + 공통 damageScale 계약 + k=0.45
초기 경제    승급 무료가 동료 27->12일, 무기 16->5일, 30일 뽑기 0->4회로 푼다
배정률       결과에 닿지 않는다 - 가정이 계약에서 빠졌다
```

C-2 ~ C-6이 닫혔고 **C-1(승인) · C-7(기존 테스트 재계약) · C-8(v21 리뷰)이
열려 있다.**

**이 문서는 구현 가능 판정을 내리지 않는다.** A-1~A-8의 검토를 기다린다.
특히 **A-2(과금 리드 224→47층)**는 밸런스가 아니라 사업 판단이므로, 그 승인
없이는 2단계를 시작하지 않는다. 프로덕션 코드는 한 줄도 시작하지 않았다.
