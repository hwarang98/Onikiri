# ONIKIRI 9단계 작업 보고서

밸런스 수정 + 보스/스테이지 게이트

---

## 정정 (초안의 오류)

초안에서 **실패 스크린샷과 계산표가 서로 모순**됐다. 계산표는 "무강화 1스테이지
보스 = 19.8초 클리어"라고 했는데 스크린샷은 실패를 보여줬다.

**원인은 스크린샷 쪽이었다.** 그 화면은 자연 발생 실패가 아니라
`BossFight.DebugExpireTimer()`로 남은 시간 18.2초 지점에서 시계를 강제로 0으로
민 것이었다. 실제 경과는 30초가 아니라 약 11.8초였고, "2.3배 모자란다"는 그
11.8초 동안 넣은 피해로 계산된 값이다. 보고서에 그것을 그냥 "실패 화면"이라고
적은 것이 잘못이었다.

실측으로 확정했다 (`DebugExpireTimer` 없이 실제 30초를 흘림):

| 조건 | 결과 |
|---|---|
| 무강화 · 스테이지 1 보스 | **클리어** — 스테이지 1→2, bossKillCount 0→1, 실패 문구 없음 |
| 무강화 · 스테이지 2 보스 | **실패** — 스테이지 2 유지, "한 끗이 모자랐다" |

계산이 맞았다. 실패 스크린샷은 **무강화 스테이지 2의 자연 발생 실패**로 교체했다.

이 사건에서 진짜 문제는 어느 쪽이 틀렸는지 **판단할 근거가 코드에 없었다는 것**이다.
그래서 계산을 일회용 스크립트에서 런타임 코드(`StageSimulation`)로 옮기고,
그것이 실제 게임과 같은 수치를 쓰는지 테스트로 못 박았다. 아래 "계산과 실전의
수치 일치" 절 참고.

그 과정에서 초안 계산의 실제 결함도 두 개 나왔다 — **치명타 기대값(x1.12)** 과
**보스가 걸어 들어오는 동안 제한 시간이 흐르는 것(-5.3초)** 이 둘 다 빠져 있었다.
서로 반대 방향으로 크기가 비슷해 결과가 우연히 맞았을 뿐이다. 둘 다 모델에 넣었고
1~5 스테이지 시간이 144초에서 **135초**로 바뀌었다.

## 9-1 공격속도 상한 — 실측과 교정

### 무엇이 틀려 있었나

곡선은 이미 곱연산(`1.15 x 1.04^n`)이었지만 **상한 51레벨 = 8.17회/초**는
근거 없이 손으로 적힌 값이었다. 주석에는 "이전 상한 8.23과 사실상 같다"라고만
적혀 있었고, 그 8.23의 출처는 어디에도 없었다.

그 속도에서 실제로 무슨 일이 벌어지는지 계산하면 이렇다.

```
Mattz FULL_Samurai / ATTACK 1.png = 7프레임        (실측: 스프라이트 시트 슬라이스 7장)
PlayerCombat.attackFrameRate      = 14 fps         (실측: Main.unity 2350행)
클립 길이                          = 7 / 14 = 0.500초
```

`PlayerCombat`은 스윙이 공격 간격 안에 들어가도록 재생 속도를 압축한다.
초당 8.17회면 간격이 0.1224초이므로 스윙은 **4.09배속**으로 재생된다.
프레임 하나가 17ms — 60fps 화면에서 정확히 한 프레임이다. 그 시점에 보이는
것은 발도 동작이 아니라 스프라이트 깜빡임이다.

### 실측 캡

| 항목 | 값 |
|---|---|
| 클립 길이 | **0.500초** (7프레임 / 14fps) |
| 자연 속도 (1배속) 최대 APS | **2.00회/초** |
| **2배속 최대 APS (= 캡)** | **4.00회/초** |
| 캡을 넘지 않는 마지막 강화 레벨 | **Lv.32** |
| Lv.32의 실제 공격속도 | **3.879회/초** (2배속의 97.0%) |
| Lv.33이었다면 | 4.035회/초 → 캡 초과 |

캡은 이제 **상수가 아니라 계산 결과**다. `AttackSpeedCurve`가 클립 길이에서
유도하고, `UpgradePanelBuilder`가 그 값을 `maxLevel`에 기록한다. 클립을 다른
것으로 교체하면 상한도 함께 움직인다.

`BattleContentBuilder.VerifyWiring`에 검사를 하나 추가했다 — 씬의 공격 클립이
7프레임/14fps가 아니면 빌드 시점에 에러를 낸다. 아트를 바꿨는데 상한만 예전
값으로 남는 경로를 막는다.

### 구현 위치

- `CombatFeel.MaxAnimationSpeed = 2f` — 왜 2배가 한계인지가 여기 적혀 있다
- `PlayerCombat.MaxAttacksPerSecond` — 클립에서 유도한 상한
- `PlayerCombat.AttacksPerSecond` 세터가 상한에서 자른다 (진입점 하나)
- `PlayerCombat.Update`의 스윙 압축이 `MinSwingDuration` 아래로 내려가지 않는다
- `UpgradeButton`이 상한에서 **`MAX`** 를 표시하고 버튼을 비활성화한다

### 밸런스 영향 — 짚고 넘어갈 것

**DPS 상한이 절반이 된다.** 8.17 → 3.88회/초이므로 공격속도 축이 기여할 수
있는 최대치가 2.1배 줄었다. 그만큼은 이제 공격력(상한 없음)이 메꾼다.
`StageProgressionTests.HitsPerKill_StaysInAPlayableBandFor50Stages`와
`Boss_IsBeatableWithinTheTimeLimit`이 둘 다 통과하므로 50스테이지까지의
진행은 유지되지만, 후반 성장이 공격력 한 축에 몰린다는 뜻이기도 하다.
치명타·골드획득 축을 추가할 때 이 자리가 비어 있다.

### 기존 세이브의 Lv.33 이상 — 레벨을 유지하고 효과만 막는다

초안에서는 `SetLevel`이 레벨을 `maxLevel`로 잘랐다. Lv.44 세이브가 Lv.32가 되고,
플레이어가 산 12레벨이 영구히 사라진다. 골드는 이미 썼는데 되돌릴 방법이 없다.

이제 **레벨은 그대로 남고 효과만 상한에서 막힌다.** `UpgradeTrack`에 `valueCeiling`을
추가했다. `maxLevel`과 뜻이 다르다:

| | 뜻 | 걸리는 곳 |
|---|---|---|
| `maxLevel` | 더 **팔지** 않는다 | 구매(`IsMaxed`), MAX 표시 |
| `valueCeiling` | 더 **세지지** 않는다 | 효과값(`ValueAtLevel`) |

보통은 둘 다 같은 상한에서 나오지만 세이브 복원에서 갈라진다.

**캡이 오르면 잠들어 있던 레벨이 스스로 깨어난다.** 더 긴 공격 클립으로 바꾸거나
2배속 규칙을 손보면 상한이 오르고, Lv.44는 다시 사지 않아도 제 값을 낸다.
`RaisingTheCeiling_RestoresTheSleepingLevels`가 이것을 검사한다 — 상한을 두 배로
올리면 Lv.44의 효과가 곡선값으로 복원되고 `IsMaxed`도 거짓으로 돌아간다.

효율 지표는 상한을 **걷어낸** 곡선으로 잰다(`UncappedValueAtLevel`). 상한이 걸린
값을 쓰면 상한 위에서 증가율이 0이 되어 두 축의 비율이 무한대로 발산하고,
"공격속도가 죽었다"는 틀린 결론이 나온다. 상한 위의 레벨은 팔리지 않으므로
죽은 버튼이 아니라 아예 없는 버튼이다.

## 9-2 성장 축 교차 효율 테스트

### 정의

- **효율 = 골드 1당 DPS 증가율(%)**. 절대 증가량이 아니다 —
  DPS = 공격력 x 공격속도라 절대 증가량은 상대 축의 레벨에 의존하고,
  그러면 비교할 때마다 상대 축 레벨을 함께 정해야 한다.
- **같은 레벨끼리** 비교한다. 레벨 n에서 다음 1레벨을 살 때의 %DPS/골드.
- **레벨 1~200** 전 구간, 모든 축 쌍, **5배** 초과 시 실패.

현재 두 축의 실제 비율은 **1.20배이고 레벨과 무관하게 일정**하다.
두 축이 같은 형태(곱연산)에 같은 비용 증가율(x1.15)을 쓰기 때문이다.

### 테스트가 유효한지 증명

요청받은 대로 **변경 전 곡선에서 실제로 실패하는지** 확인했다.
`Axes()`를 8단계 곡선(`선형 +0.12/레벨`, `비용 x1.35`)으로 임시 교체하고
EditMode를 돌린 결과:

```
Onikiri.Tests.UpgradeEfficiencyTests.EveryPairOfAxesStaysWithinTheAllowedRatio
  '공격력 강화' 와 '공격속도 강화 (구)' 이 Lv.200에서 4507653849336600.0배 차이 (허용 5배)
    공격력 강화 Lv.200  +12.0 % / 12.0T골드
    공격속도 강화 (구) Lv.200  +0.5 % / 2.2ae골드
  Expected: less than or equal to 5.0d
  But was:  4507653849336602.0d

Onikiri.Tests.UpgradeEfficiencyTests.NoAxisDecaysStructurally
  '공격속도 강화 (구)' 의 레벨당 증가율이 10.43 % -> 0.48 % 로 줄어든다.
  값이 합연산인데 비용이 지수면 이 축은 반드시 죽는다
  Expected: False
  But was:  True
```

두 테스트가 서로 다른 방식으로 잡는다 — 하나는 **얼마나** 벌어졌는지,
다른 하나는 **왜** 벌어지는지(구조)다. 확인 후 되돌렸다.

이 대조군은 `TheOldLinearCurve_WouldFailTheSameCheck`로 영구히 남겨두었다.
"5배를 넘지 않았다"는 5배를 넘는 곡선을 실제로 잡아낼 수 있을 때만 성과다.

### 새 축 추가 방법

`UpgradeEfficiencyTests.Axes()`에 한 줄 추가하면 모든 쌍 조합 x 1~200 레벨이
자동으로 검사된다. 치명타율·골드획득이 여기로 온다.

## 9-3 데미지 숫자 겹침 — 선택 A

**선택 A(합산 + 스케일 튀기기)** 를 택했다. 이유는 두 가지다.

1. **방치형은 숫자 개수보다 타격감이다.** 초당 네 번 구간에서 숫자 네 개가
   따로 뜨면 어느 것도 읽히지 않는다. 합쳐진 하나는 "이 요괴에게 지금까지
   얼마가 들어갔는가"라는, 개별 타격보다 더 쓸모 있는 정보가 된다.
2. **선택 B는 문제를 옮길 뿐이다.** 산포를 넓히면 숫자가 전투 영역 밖으로
   나가고, y 계단식은 공격속도가 오를수록 계단이 화면 위로 넘친다. 공격속도가
   성장 축인 이상 어떤 고정 오프셋도 결국 부족해진다.

이번에 추가한 것은 **스케일 펀치**다. 합산될 때 `1.0 → 1.15`로 튀고 0.12초에
걸쳐 돌아온다. 위치 상승만으로는 부족했다 — 그 구간에서 숫자는 이미 계속
움직이고 있어서 작은 상승이 다른 팝업의 움직임과 구분되지 않는다. 크기는 그
화면에서 유일하게 변하지 않던 축이라 눈에 걸린다.

폰트 크기가 아니라 트랜스폼 스케일을 쓴다. 비트맵 폰트라 `fontSize`를 정수배
사이 값으로 흔들면 글리프가 리샘플되어 강조하려던 숫자가 오히려 흐려진다.

## 9-4 보스 + 스테이지 게이트

### 구조

```
Farming   잡몹 무한 스폰. 10마리를 채우면 도전 버튼이 열린다
   |  [보스 도전] 버튼 (수동)
Intro     화면 어둡게 + 이름 1초. 필드는 이미 비어 있다
   |
Fighting  보스 하나. 30초 시계
   |                        \
성공: 스테이지 +1            실패: 문구 3초
   \                        /
    ------> Farming <-------
```

- `StageProgress` — 게이트 상태만 안다. 잡몹 처치는 **더 이상 스테이지를
  올리지 않고** 할당량만 채운다. 스테이지가 오르는 유일한 경로는 `AdvanceStage()`
  이고 보스 처치만 그것을 부른다.
- `BossFight` — 상태 기계. 필드 비우기, 스폰, 시계, 실패 판정.
- `BossHud` — 상태 하나에 화면 하나. 네 화면이 배타적으로만 켜진다(실측 확인).
- `BossFailureAdvice` — 순수 계산. 실패 문구를 만든다.

### 수치

| 항목 | 값 | 근거 |
|---|---|---|
| 잡몹 할당량 | 10마리 | 기존 `StageCurve.KillsPerStage` |
| 보스 HP | 잡몹 평균 x **8** | 스폰 가중 평균에 스테이지 배수를 곱한 값 기준 |
| 보스 골드 | 잡몹 평균 x **12** | 8보다 크게 잡아야 30초 위험을 감수할 이유가 생긴다 (1.5배 웃돈) |
| 제한 시간 | **30초** | 스케일 타임 — 히트스톱이 제한 시간을 갉아먹지 않는다 |
| 실패 패널티 | **없음** | 스테이지·골드·kill count 전부 유지 |
| 스테이지 클리어 | HP x1.55, 골드 x1.72 | 기존 곡선 그대로 |

1스테이지 기준 실측: 보스 HP **113.78** (= 14.22 x 8), 골드 **65.33** (= 5.44 x 12).

### 소프트락 방지

이것이 이 단계에서 가장 신경 쓴 부분이다. 보스에서 막힌 플레이어가 강화할
골드를 못 버는 상태로 갇히면 그건 난이도가 아니라 버그다.

- 실패하면 **자동으로 잡몹 파밍으로 복귀**한다. 성공과 실패가 같은
  `ReturnToFarming()`을 지나므로, 한쪽만 스폰을 다시 켜는 것을 잊을 수 없다.
- 할당량을 채운 뒤에도 **잡몹은 계속 나오고 골드도 계속 들어온다.**
  `killsThisStage`가 상한에서 멈출 뿐이다(50/10 같은 표시가 나오지 않는다).
- 재도전은 **수동**이다. kill count 재적립은 없다 — 잡몹 10마리를 다시 잡는
  것은 강해지는 일이 아니라 기다리는 일이고, 실패의 대가로 기다림을 물리면
  플레이어가 배우는 것은 "보스에 도전하지 말자"다.
- 자동 재도전도 넣지 않았다. 30초마다 조용히 실패하는 화면에서는 강화가
  필요하다는 신호가 전달되지 않는다.

**실측 확인**: 실패 직후 `phase=Farming, suspended=false, mobsAlive=4,
stage=1, kills=10, canChallenge=true, gold 계속 증가`.

### 실패가 신호가 되게 하기

실패 화면은 두 줄이다. 첫 줄은 무슨 일이 있었는지, 둘째 줄은 무엇을 하면
되는지다. 순서를 바꾸지 않는다 — 지시가 먼저 오면 왜 그래야 하는지 모르는
채로 읽게 된다.

```
화력이 2.3배 모자란다.
공격력 강화를 올리고 다시 도전하라
```

- **배율**은 추정이 아니라 방금 일어난 일의 나눗셈이다.
  `보스 최대 체력 / 제한 시간 동안 실제로 넣은 피해`.
- **어느 축**은 `UpgradeEfficiency.GainPerGold`가 고른다 — 지금 골드당 이득이
  가장 큰, 아직 상한이 아닌 축이다. 이미 있는 지표를 재사용하므로 새 판단
  기준을 만들지 않는다. 상한에 닿은 축은 후보에서 뺀다(실행할 수 없는 지시다).

실패 문구 패널은 **레이캐스트를 먹지 않는다.** 뒤의 강화 버튼이 그대로 눌린다 —
실패 직후에 해야 할 일이 정확히 그 버튼을 누르는 것이기 때문이다.

### 등장 연출

- 화면 전체를 덮는 어두운 판 + 붉은 이름 1초. 판이 레이캐스트를 먹어 연출 중
  강화 버튼이 눌리지 않는다.
- **BGM 정지는 건너뛰었다.** 현재 빌드에 BGM이 없다(오디오는 Leohpaz 타격/처치
  효과음뿐). 지시대로 새로 넣지 않았다.
- 히트스톱/셰이크 예산(`CombatFeel`)은 손대지 않았다. 보스전도 잡몹과 같은
  `PlayerCombat` 경로를 그대로 지난다.

### 세이브 마이그레이션 (v1 → v2)

`SaveData.CurrentVersion`을 2로 올리고 `bossKillCount`를 추가했다.
`stage`가 곧 currentStage이므로 필드를 새로 만들지 않고 그대로 쓴다
(이름을 바꾸면 v1 JSON 매핑이 깨진다).

**버전이 다르다고 새 게임으로 되돌리지 않는다.** 8단계까지는 그렇게 했는데,
그건 형식을 손댈 때마다 플레이어의 진행을 지운다는 뜻이다. 실제 배포에서는
그 한 줄이 "업데이트했더니 처음부터"가 된다. 이제 `SaveData.Migrate`가 올리고,
**이 빌드보다 새 버전**일 때만 새 게임으로 간다.

v1 → v2 규칙: `bossKillCount = stage - 1` (그동안 넘어온 스테이지 수를
보스 처치 수로 친다. 0으로 두면 통계가 진행과 어긋난 채로 남는다).

**실측 확인** — 디스크에 v1 JSON을 직접 쓰고 로드:

```
입력  {"version":1, "stage":9, "killsThisStage":6, "upgradeLevels":[27,44], "gold":4200, ...}
출력  version=2, stage=9, kills=6, bossKillCount=8, gold=4200, 공격력 Lv.27 유지
      (공격속도 Lv.44는 복원 시 새 상한 Lv.32로 잘림 — 9-1 참고)
```

10/10(보스 개방) 상태의 저장/복원도 확인했다. v1에서는 `killsThisStage`가
상한 미만이어야 했지만(10에 닿는 순간 스테이지가 올라갔으므로) v2에서는
10이 유효한 상태다 — `SetProgress`의 클램프 상한을 함께 고쳤다.

## 9-5 벚꽃 참격 파티클

- 색 **#D9A7B0 / #F0CDD3** 두 가지를 섞는다. 전부 한 색이면 조각들이 한
  덩어리로 읽힌다.
- **1~2px 네 모양**을 코드로 굽는다(`SakuraContentBuilder`). 4x4 셀 4개짜리
  16x4 시트. 시트는 흰색으로 굽고 색은 런타임에 입힌다 — 나중에 스테이지별로
  다른 색(단풍, 눈)을 넣을 때 아트를 다시 굽지 않아도 된다.
- 타격당 **6~10개**, 참격 방향(1, 0.45)을 중심으로 ±42° 부채꼴, 회전하며 낙하.
- **풀링** — prewarm 40. 실측에서 풀 증식 0.
- **ParticleSystem을 쓰지 않았다.** 1px 조각이 픽셀 격자에 스냅되지 않아
  프레임마다 다른 모양으로 리샘플되고, 히트스톱(`Time.timeScale`)과 시뮬레이션
  정지 시점이 어긋난다. `SpriteRenderer` + `Update`면 픽셀 퍼펙트 스냅을 그대로
  받고 스케일 타임으로 돌아 히트스톱이 꽃잎까지 함께 얼린다.

### 예산: 수명에 하한을 두고 초과분은 개수로 흡수

참격은 수명만 줄여도 됐지만 꽃잎은 다르다. 참격은 큰 흰 호 하나라 0.13초만 떠
있어도 "번쩍였다"로 읽히는데, 1~2px 조각은 그 시간에 눈이 따라갈 수 없다.
초안대로 상한 공격속도에서 0.129초까지 줄이면 꽃잎이 흩날리는 것이 아니라 타격
지점에서 분홍색이 **점멸**한다. 흩날림은 궤적이 보여야 성립하고, 궤적에는
최소한의 시간이 필요하다.

그래서 수명은 **0.25초**(60fps에서 15프레임)에서 멈추고, 남은 초과분을 개수로
흡수한다. 예산이 지키는 것은 "화면에 떠 있는 꽃잎의 총량"이고 그것은 수명 × 개수
이므로, 어느 쪽으로 줄여도 예산은 그대로다.

**실측** (`SakuraBurst.LifetimeAt` / `PetalsAt` / `ConcurrentPetalsAt`):

| 공격속도 | 수명 | 타격당 개수 | 동시 표시 개수 |
|---|---|---|---|
| 1.15회/초 (Lv.1) | 0.435초 | 8 | 4.00 |
| 2.00회/초 | 0.250초 | 8 | 4.00 |
| 3.00회/초 | 0.250초 | 5 | 3.75 |
| **3.88회/초 (Lv.32, 상한)** | **0.250초** | **4** | **3.88** |

수명은 하한 아래로 내려가지 않고, 동시 표시 개수는 전 구간에서 4개 내외로
유지된다. 2.00회/초가 정확한 분기점이다 — 그 지점에서 예산이 요구하는 수명
(0.5 / 2.0)이 하한과 같아지고, 그 위부터 개수가 줄기 시작한다.

개수에는 하한 3개를 뒀다. 타격 자체가 안 보이는 것보다는 예산을 조금 넘기는
편이 낫다.

## 계산과 실전의 수치 일치

초안의 진행 시간 계산은 일회용 스크립트였고, 그 스크립트가 쓴 상수가 실제 게임의
값과 같다는 보장이 없었다. 그래서 계산과 화면이 어긋났을 때 어느 쪽을 믿어야
할지 판단할 수 없었다.

계산을 런타임 코드로 옮겼다.

| 파일 | 역할 |
|---|---|
| `AttackPowerCurve` / `AttackSpeedCurve` | 강화 곡선의 단일 출처. 빌더가 씬에 기록하고 시뮬레이션이 읽는다 |
| `CombatBaseline` | 치명타 확률·배수. 빌더가 씬에 기록하고 `VerifyWiring`이 어긋남을 잡는다 |
| `StageCurve.BossHealthForStage` | 보스 체력. `BossFight`와 시뮬레이션이 **같은 함수**를 부른다 |
| `StageSimulation` | 진행 시뮬레이션. 보고서의 표가 여기서 나온다 |

`StageSimulationTests`가 이것들을 못 박는다:

- 잡몹 평균 체력/골드를 **에셋에서 직접 읽어** 확인한다 (상수를 복사해두지 않는다)
- 시뮬레이션 곡선과 실제 `UpgradeTrack`이 Lv.1~60에서 값·비용 모두 일치하는지
- 시뮬레이션의 보스 체력이 `BossFight`가 스폰할 체력과 같은지 (20스테이지까지)
- 시작 스탯이 두 곡선의 Lv.1과 같은지
- 치명타가 기대 DPS에 반영되는지

### 초안 계산에 있던 결함 두 개

**치명타가 빠져 있었다.** 12% 확률 x 2배 = 기대 피해 1.12배. 보스전은 제한 시간
판정이라 이 12%가 통과와 실패를 가르는 구간이 실제로 있다.

**보스가 걸어 들어오는 동안 제한 시간이 흐른다.** 시계는 보스 스폰 순간 시작하지만
보스는 화면 밖에서 5.3초를 걸어온다. 그동안 사무라이의 사거리에는 아무도 없다.
때릴 수 있는 시간은 30초가 아니라 **24.7초**다.

둘이 반대 방향으로 크기가 비슷해 결과가 우연히 맞았다. 우연히 맞는 계산은 다음
계수 변경에서 조용히 틀린다. 둘 다 모델에 넣었고, `BossDamageWindow_IsShorterThanTheClock`과
`ExpectedDps_IncludesCrit`이 다시 빠지는 것을 막는다.

시계를 보스 도착 후에 시작하도록 고치지 않은 이유는, 걸어 들어오는 장면이
연출이기도 하기 때문이다. 시계가 도착 후에 시작하면 등장이 공짜가 되어
플레이어가 그 시간을 기다림으로만 느낀다.

## 스테이지 1 → 5 예상 시간

`StageSimulation.Run(5, ...)`의 출력이다. 정책은 "골드가 되는 대로 지금 더 싼 축을
산다"(두 축의 골드당 효율이 같은 레벨에서 1.20배로 일정하므로 실제로 번갈아 오른다).
잡몹 처치 간격은 스폰 공급(생존 4마리 / 1.1초)이 하한이다.

**보스에게 때릴 수 있는 시간은 24.7초** (제한 30초 − 걸어 들어오는 5.3초).

| 스테이지 | 잡몹 10마리 | 보스 처치 | 여유 | 강화 도달 |
|---|---|---|---|---|
| 1 | 19.0초 | 12.0초 | 2.1배 | 공격력 Lv.4 / 공격속도 Lv.11 (1.51/s) |
| 2 | 13.6초 | 8.7초 | 2.9배 | Lv.9 / Lv.15 (1.84/s) |
| 3 | 11.3초 | 7.0초 | 3.5배 | Lv.13 / Lv.20 (2.24/s) |
| 4 | 11.0초 | 5.3초 | 4.7배 | Lv.18 / Lv.24 (2.62/s) |
| 5 | 11.0초 | 4.4초 | 5.6배 | Lv.22 / Lv.28 (3.07/s) |

각 스테이지에 등장 연출 1초 + 걸어 들어오는 5.3초가 더해진다.

### **스테이지 1 → 5 클리어: 약 135초 = 2.2분**

4스테이지부터 잡몹 구간이 11.0초에 고정되는 것은 **처치가 DPS가 아니라 요괴
공급에 묶이기 시작한다**는 뜻이다(10 x 1.1초). 여기가 다음 단계에서 봐야 할
지점이다 — 화면의 동시 생존 수나 스폰 간격을 손대지 않으면 공격력 강화가
잡몹 구간에서는 의미를 잃는다. 보스전은 순수 DPS 싸움이라 그 축을 계속 살려둔다.

### 게이트가 실제로 무는가 — 계산과 실측

| 시나리오 | 계산 | 실제 플레이 |
|---|---|---|
| 무강화 · 1스테이지 보스 | 17.7초 / 24.7초 → 클리어 | **클리어** (스테이지 1→2) |
| 무강화 · 2스테이지 보스 | 27.4초 / 24.7초 → 실패 | **실패** ("한 끗이 모자랐다") |

계산과 실측이 일치한다. 첫 보스는 튜토리얼이고 두 번째부터 게이트가 문다.
2스테이지에서 나온 문구가 "한 끗이 모자랐다"(부족 배율 1.1배 미만)인 것은
설계대로다 — 강화를 한 번만 해도 통과하는 거리에 벽을 세웠다.

- 보스 처치 → `stage 1→2, bossKillCount 0→1, kills 0으로 리셋`

## 작업 중 발견한 것

**폰트 파이프라인이 씬 참조를 끊는다.** `Onikiri/Art/Build Pixel Font Assets`는
폰트 에셋을 삭제하고 다시 만들기 때문에 GUID가 바뀌고, 씬의 모든 TMP 컴포넌트가
폰트를 잃는다. 증상이 고약하다 — 라틴 문자는 TMP 기본 폴백으로 멀쩡히 나오고
한글만 □가 되어, 폰트 참조가 끊긴 것이 아니라 글리프가 안 구워진 것처럼 보인다.
**폰트를 다시 구운 뒤에는 반드시 `Build Combat Content`를 다시 돌려야 한다.**
이번에는 그렇게 해결했지만, 다음에 손볼 때 `SaveWithSubAssets`가 GUID를
보존하도록 고치는 편이 낫다.

**보스 이름의 글리프가 없었다.** 문자셋은 `UIStrings.txt`에서 나오는데 새 문구를
거기 적지 않으면 화면에 □가 뜬다. 9단계 문구 전부를 추가했다(231 글리프).

**`HitStop`이 외부에서 건 타임스케일을 지운다.** `HitStop.Update`는 정지가 끝나면
`Time.timeScale = normalTimeScale`(1)로 복구한다. 이전 값을 기억하지 않으므로,
전투 중에 배속을 걸면 **첫 타격에 1로 돌아간다**. 테스트 패널의 "시간 배속 0.25x /
4x" 버튼이 전투 중에는 사실상 동작하지 않는다는 뜻이다. 이번 측정에서는 게임 시간
기준 판정(BossFight의 시계)을 읽었으므로 결과에 영향이 없지만, 다음에 배속을
쓰려면 `HitStop`이 복구할 값을 기억하도록 고쳐야 한다.

## 다음 단계에서 볼 것

1. **잡몹 구간이 스폰 공급에 묶인다** — 4스테이지부터 10 x 1.1초에 고정된다.
   동시 생존 수나 스폰 간격을 손대지 않으면 공격력이 잡몹 구간에서 의미를 잃는다.

   Lv.32 이후 DPS는 공격력 한 축뿐이다. 치명타율·치명타 피해·골드획득이

   x 모든 쌍 검사가 자동으로 따라온다.

   스테이지에 따라 완만히 올리거나, 보스에게 행동을 주는 것이 다음 후보다.

   등장 이동 속도를 올리는 것이 조정 여지다.
5. **`HitStop`의 타임스케일 복구** — 위 "작업 중 발견한 것" 참고. 개발 편의 문제이지만
