## 원인 확인 — 에셋을 실제로 재봤다

프롬프트의 진단이 맞았다. 다만 한 가지는 달랐다.

### 참격이 두 번 그려지고 있었다 — 맞다

`ATTACK 1` 시트의 프레임별 잉크 범위를 재면 타격 프레임에서만 폭이 튄다.

| 프레임 | 잉크 오른쪽 끝 (피벗 기준) |
|---|---|
| 0~3 | 0.41~0.44u |
| **4 (타격)** | **1.375u** |
| 5 | 1.125u |
| 6 | 0.781u |

4번 프레임에서만 칼이 뻗는다. 그 확장분이 **원화가가 그려 넣은 흰 참격**이고,
스프라이트의 일부이므로 칼과 어긋날 수가 없다. 그 위에 팩 아크를 한 장 더 얹고 있었다.

### 두 호는 방향이 반대였다 — 맞다

팩 아크(`Slash_White` = Slash1의 무채화본) 5~8번 프레임의 잉크 무게중심:

```
(41.1, 40.0) -> (42.3, 29.9) -> (43.7, 22.1) -> (41.5, 18.5)
x는 고정, y만 내려간다  =  아래로 긋는 세로 베기 (-90도)
```

사무라이의 발도는 오른쪽 위 **+24도**(위 표의 1.375u × 0.969u). 종류가 반대다.
22단계에서 회전으로 맞춰보려 했지만, 애초에 **한 화면에 참격이 둘이라는 것**이 문제였다.

### 초록은 아니었다 — 이 부분만 다르다

팩 원본이 초록인 것은 맞다(실측 hue 74도, 채도 0.67~0.83). 그런데 **게임이 로드하던
시트는 그것이 아니라 `Assets/_Project/Art/VFX/Slash_White.png`, 이미 무채화된
사본이었다**(실측 채도 0.00). 화면에 초록이 나온 적은 없다.

초록 금지 요구 자체는 유효하므로 아래에서 구조로 막았다.

## 해결 — 아크는 스프라이트 하나, 별도 VFX는 불꽃

### 제거한 것

```
PlayerCombat.slashPrefab / slashFrames / slashFrameRate / slashBudgetPerSecond
             slashOffset / bladeReach / SlashAimDegrees / SlashPointFor / SpawnSlash
SlashVfx.cs                     삭제
Prefabs/SlashVfx.prefab         삭제 (컴포넌트가 사라지면 깨진 참조로 남는다)
BattleContentBuilder.SlashSheet / SlashImpactFirstFrame / BuildSlashPrefab
```

`Art/VFX/Slash_White.png`은 **지우지 않고 남겼다.** 무기 등급을 흰색 → 적색 → 금색으로
설계했다는 기록이 있어, 나중에 필살기·보스 연출에서 큰 아크가 필요해질 자리다.
지금은 아무도 로드하지 않는다.

### 새로 만든 것 — ImpactSpark

12px 네 프레임. 팩 아트가 아니라 코드로 굽는다(`ImpactSparkBuilder`).

> **왜 팩 아트를 안 썼나.** Slash2에는 실제로 쓸 만한 임팩트 별이 있다. 그런데 그것이
> **긴 찌르기 줄기와 한 프레임에 붙어 있다** — 열별 잉크 분포를 재보면 프레임 2에서
> 줄기(x 10~26)와 별(x 26~56)이 이어져 있어서, 별만 떼려면 좌표를 손으로 박아야 하고
> 팩을 갱신하는 순간 깨진다. 필요한 것은 12px짜리 가시 몇 개이고, 그 크기에서는
> 그림 파일을 관리하는 비용이 아트보다 크다. 벚꽃잎과 같은 판단이다.

| | 걷어낸 아크 | 새 불꽃 |
|---|---|---|
| 크기 | 64px = **2.0u** | 12px = **0.375u** |
| 위치 | 칼 궤적 위 (맞추려 애씀) | 요괴 앞면 (맞을 수밖에 없음) |
| 회전 | 겨냥각 계산 + 흔들림 | 없음 |
| 길이 | 4프레임 22fps = 0.18초 | 4프레임 30fps = 0.133초 |

아크 2.0u는 사무라이(1.0u)와 요괴를 통째로 덮었다. 0.375u는 잡몹 몸의 3분의 1쯤이라
"맞은 자리"를 찍고 물러난다.

회전을 뺀 이유: 가시가 사방으로 뻗는 모양이라 돌려도 달라지지 않고, 픽셀 아트를
정수배가 아닌 각도로 돌리면 가시가 뭉개지기만 한다.

### 색 — 붉은색. 흰색으로 갔다가 물렸다

처음에는 흰기 도는 살구색(#FFE2D0)으로 넣었다. **화면에서 사라졌다** — 불꽃이 서는
자리를 사무라이 스프라이트의 흰 참격이 그대로 지나가기 때문이다. 흰 아크 위의
흰 불꽃 12px은 통째로 묻힌다(`step23_spark_white_rejected.png`).

**#FF453A**(hue 3도)로 바꿨다. 흰 아크 위에서 읽히고, 먹빛 배경·단풍·벚꽃과 같은
계열에 있다. 피격 플래시(흰색)와도 갈린다 — 흰 번쩍임은 요괴 몸 전체가 하는 일이고,
불꽃은 한 점을 찍는 일이다.

**시트는 흰색으로 굽고 색은 런타임에 입힌다.** 시트에 색을 구워 넣으면 초록을 다시
넣을 여지가 남지만, 흰 시트에는 초록을 넣을 방법이 없다.

전투 이펙트 색 감사(hue 60~180 & 채도 0.3 이상 = 초록):

```
ImpactSpark  #FF453A  hue=  3  sat=0.77   ok
Sakura pale  #D9A7B0  hue=349  sat=0.23   ok
Sakura bright#F0CDD3  hue=350  sat=0.15   ok
Damage 평타  #FFF4D6  hue= 44  sat=0.16   ok
Damage 치명  #FFD34D  hue= 45  sat=0.70   ok
Damage 처치  #FF8A7A  hue=  7  sat=0.52   ok
```

> 경험치 팝업(#7CC59A)만 초록이다. 이것은 **이펙트가 아니라 숫자**이고, 경험치 바
> 채움색과 같아야 "저것이 저기로 들어갔다"가 읽힌다. 손대지 않았다.

### 좌우 반전 — artFacesLeft에서 끌어온다

`Enemy.FacingDirection`을 새로 뒀다. 그려진 방향(`artFacesLeft`)과 Spawn이 건 뒤집기를
**함께** 읽는다 — 둘 중 하나만 보면 틀린다. 팩마다 그려진 방향이 다르고(처형인은 왼쪽,
나머지는 오른쪽), 그 차이를 없애려고 뒤집는 것이 바로 그 플래그의 일이기 때문이다.

```csharp
bool drawnFacingLeft = definition != null && definition.artFacesLeft;
bool flipped = spriteRenderer != null && spriteRenderer.flipX;
return drawnFacingLeft != flipped ? -1 : 1;
```

불꽃의 **위치와 반전이 둘 다** 이 값에서 나온다. `PlayerCombat`에는 부호가 없다.

검증 — 팩이 반대로 그려진 경우를 흉내내어 요괴의 뒤집기를 반대로 걸었다:

```
artFacesLeft=False  flipX=True   -> Facing=-1   불꽃 x = 중심 - 0.22,  flipX=True
뒤집은 뒤 flipX=False            -> Facing=+1   불꽃 x = 중심 + 0.22,  flipX=False
```

위치와 반전이 함께 따라왔다(`step23_spark_hit.png` / `step23_spark_mirror.png`).

가시는 칼이 들어온 쪽으로 1.4배 길게 그려져 있다. 좌우 대칭이면 뒤집어도 같은 그림이라
반전이 의미가 없어지기 때문이다.

## 타이밍·동결 — 기존 구조가 이미 만족한다. 확인만 했다

### 같은 프레임

불꽃·꽃잎·데미지 숫자·소리·히트스톱이 전부 `DeliverHit` **한 함수 안**에서 난다.
애님 이벤트로 흩지 **않았다** — 이벤트로 흩으면 다섯 연출이 각자의 조건으로 나게 되고,
하나가 한 프레임 밀리면 타격이 두 번 일어난 것처럼 보인다. 지금은 밀릴 방법이 없다.

애니메이션 쪽을 반대로 맞춘다. 스윙을 `lead` 시간만큼 먼저 시작시켜서, 참격이 그려진
5번째 프레임이 `DeliverHit`이 도는 순간에 화면에 있다 — `impactPoint = 4/7`이
7프레임 클립의 5번째 프레임 시작과 정확히 겹친다(0.5714).

이 구조는 12단계에 "데미지는 타이머가 결정하고 애니메이션은 장식이다"로 정해진 것이고,
그때 실제 공격 횟수가 설정값의 70~85%에 머물던 문제를 고친 것이다. 애님 이벤트로
되돌리면 그 문제가 함께 돌아온다.

### 히트스톱 중 동결

```
HitStop.Request -> Time.timeScale = 0
스케일 타임(=함께 언다): SpriteAnimator(참격 클립 포함) / ImpactSpark / SakuraPetal
                        / DamageNumber / ParallaxScroller
unscaled: ScreenShake 하나뿐 — 정지 중에도 흔들려야 무게가 산다(기존 주석의 근거)
```

불꽃도 `SpriteAnimator`를 쓰므로 자동으로 얼음. 새로 만든 것이 이 규칙을 깨지 않는지가
확인 대상이었고, 깨지 않는다.
