## 1. 데이터 구조 - 계열(Family)과 등급(Grade)의 분리

### 1.1 세 축

- `GachaCurve.Grade` (일반·고급·희귀·영웅·전설 = ★1~★5) = **뽑기 희귀도**
- `SkillGachaCurve.Outcome` = **보상의 층**
- **신설** `SkillFamily` = **전투 계열**

```csharp
// SkillCatalog.cs (Progression) - 구현 2단계
public enum SkillFamily
{
    SwordForm,   // 검식   - 빠르고 안정적인 검술
    BloodForm,   // 혈식   - 피와 요괴의 힘, 변칙 기술
    OniSecret    // 귀오의 - 흐름을 바꾸는 필살기
}
```

### 1.2 UI 표기 규칙

| 탭 주 표기 | 작은 부제 | 데이터 |
|---|---|---|
| **검식** | 일반 | `SkillFamily.SwordForm` |
| **혈식** | 상급 | `SkillFamily.BloodForm` |
| **귀오의** | 각성 | `SkillFamily.OniSecret` |

희귀도 낱말과 겹치는 것은 "일반" 하나다. 화면에서 가르는 규칙:

- **뽑기 결과 화면·확률 정보에는 계열 부제를 안 쓴다.** 그 화면의 낱말은 전부 `Grade`의 것이다.
- **스킬 목록 화면에는 별(★)을 안 그린다.** 그 화면의 눈금은 전부 계열이다.
- 두 화면이 만나는 줄(뽑기 결과의 해금 알림)에는 **계열 이름만** 적는다: `혈조 · 혈식 해금`.

### 1.3 두 종류의 색을 구분한다

| 축 | 쓰이는 곳 | 값의 수 | 계약 |
|---|---|---|---|
| **계열 색** | 계열 탭 배경 틴트, 목록 행 좌측 4px 띠 | 3 | 없음 (UI 전용) |
| **`SlashRgba`** | 대형 참격 아크 · 이름 플래시 · 데미지 숫자 | 15 | `SkillShapeTests` 두 검사 (§6.8) |
| **`flashTint`** | 화면 플래시(`ScreenFlash`)의 가장자리 색 | 3 (플래시를 쓰는 오의만) | 서로 갈려야 한다 (§6.6) |

계열 색 (기존 `SlashRgba`에서 대표값을 빌린다. 신규 정의 없음):

| 계열 | 계열 색 | 출처 |
|---|---|---|
| 검식 | `#A8D8FF` | 연참 |
| 혈식 | `#C8304C` | 혈륜 |
| 귀오의 | `#FF9500` | 귀참 |

**계열 색을 아이콘에 곱하지 않는다.** 팩 아이콘은 배경 타일 색을 갖고 있어서
틴트를 곱하면 두 색이 싸운다. 아이콘의 계열 신호는 팩의 **색 변형**이 맡는다 (§10.2).

## 3. 스킬 뽑기 설계

### 3.1 해금 - 상점을 st14로 (신설 상수)

현재 `SkillGachaCurve.UnlockStage`는 `GachaCurve.UnlockStage` → `YodoCurve.UnlockStage = 41`을
가리키고, 그 한 값이 요도 배너·스킬 배너·혈폭/혈조 골드 앵커를 한꺼번에 잠근다
(`ShopPanel.cs` 253·297·370·380·444·457행).

```csharp
// 신설 - ShopCurve.cs
public static class ShopCurve
{
    /** 상점 탭과 스킬 뽑기 배너가 서는 칸. 요도 배너(st41)와 갈린다 */
    public const int UnlockStage = 14;
}

// SkillGachaCurve.UnlockStage => ShopCurve.UnlockStage   (GachaCurve에서 떼어낸다)
// GachaCurve.UnlockStage      => YodoCurve.UnlockStage   (41 유지)
```

- 뽑기 몫 9종의 `SkillSpec.UnlockStage`도 `ShopCurve.UnlockStage`를 쓴다.
- **기존 혈폭·혈조의 골드 앵커가 st41 → st14로 내려간다.** 골드 비용이 실제로 바뀌므로
  `Skills_HaveTheSameGoldEfficiencyAtUnlock`을 st14 기준으로 다시 통과시켜야 한다.
- 코리더 비트: st12 혈파동 → **st14 상점 + 무료 10연** → st15 일섬 → st18 낙혈 → st21 귀참 → st27 혈륜.

### 3.2 두 해금 풀

현재 코드는 배열이 하나이고 ★5는 배열을 안 본다 - **★5에는 지금 해금 경로 자체가 없다.**

```csharp
/** ★4 표준 해금 풀 (5종). 혈조가 머리다 - 온보딩 보상과 같은 순서여야 한다 */
public static readonly string[] StandardUnlockOrder =
{
    SkillCatalog.BloodWhipId,    // 혈조    쿨 2.5s - 첫 스킬의 체감이 가장 크다
    SkillCatalog.BloodBurstId,   // 혈폭
    SkillCatalog.DeepThrustId,   // 심격
    SkillCatalog.MoonArcId,      // 회월참
    SkillCatalog.SwordFieldId    // 검진
};

/** ★5 귀오의 해금 풀 (4종). 별도 배열 + 별도 Grant 경로 + 별도 재고 */
public static readonly string[] OniSecretUnlockOrder =
{
    SkillCatalog.OniDanceId,     // 귀신난무
    SkillCatalog.AbyssPullId,    // 나락인력
    SkillCatalog.DecapitateId,   // 참수
    SkillCatalog.OniAdventId     // 귀왕강림
};

public static int  StandardTargetFor(int owned);    // 미보유 표준 인덱스, 없으면 -1
public static int  OniSecretTargetFor(int owned);   // 미보유 귀오의 인덱스, 없으면 -1
public static bool StandardSoldOut(int owned);
public static bool OniSecretSoldOut(int owned);
```

**단일 `UnlockOrder`를 늘려 쓸 수 없는 이유**

1. `UnlockTargetFor(owned)`는 배열 앞에서부터 첫 미보유를 돌려준다. 9종을 한 배열에
   넣으면 ★5가 ★4의 재고를 먼저 가져간다.
2. 재고 소진·다음 목표 표시가 **두 줄**로 갈려야 한다. "★4는 소진, ★5는 남음"이 정상 상태다.
3. `SkillSystem.HasStock`이 배너를 닫는 조건도 갈린다 (§5.2).

### 3.3 ★5 처리 규칙 (순서 확정)

```
Grant(Awakening):
  1. OniSecretTargetFor(owned) >= 0   -> 그 귀오의를 해금한다.               [끝]
  2. 귀오의 4종 전부 보유
       AwakenEquipped() >= 0          -> 기존 개안 (장착 최저 레벨을 상한까지). [끝]
  3. 개안 대상도 없다
       -> SlideFor(Awakening) = SkillUnlock
          -> StandardTargetFor >= 0 ? 표준 해금 : SlideFor = XpSurge(240)
```

`SkillGachaSystem.Grant`의 재귀 미끄러짐 구조를 그대로 쓴다. 바뀌는 것은
`case Outcome.Awakening:` 블록 하나 - `AwakenEquipped()` 앞에 `OniSecretTargetFor` 분기가 선다.

### 3.4 무료 10연 - 결과를 덮어쓰지 않는다

```
1. 10회는 일반 뽑기와 완전히 동일하게 실행한다. 결과를 덮어쓰지 않는다.
2. 10회 전부 소프트·하드 천장 카운터에 정상 반영한다.
3. 10회 중 ★4 표준 해금이 한 번도 없었으면, 뽑기 종료 후 별도 온보딩 보상으로
   StandardUnlockOrder의 첫 미보유 스킬을 지급한다. 신규 플레이어에게 그것은 항상 혈조다.
4. 표준 5종을 이미 다 보유했으면 XP 240을 지급한다.
5. 별도 보상은 뽑기 결과가 아니다. 천장 카운터를 초기화하지 않고 확률 정보 표에도 안 들어간다.
6. skillGachaIntroClaimed(bool)로 중복 수령을 막는다.
```

- **첫 표준 스킬이 혈조인 것이 구조로 보장된다.** 두 경로(자연 ★4 / 온보딩 보상)가
  **같은 `StandardTargetFor()`를 읽는다.**

- 기존 v19 플레이어도 `skillGachaIntroClaimed = false`로 시작해 한 번 받는다 (§8).

### 3.7 이중 천장 - 확정 규칙

**★4 소프트 천장** (기존 `PityPulls = 30`)

- 마지막 **★4 이상** 결과 이후 최대 30회.
- **자연 ★4 · 자연 ★5 · 강제 ★4 · 강제 ★5가 모두 카운터를 0으로 되돌린다.**
- 즉 "★4 보장"이 아니라 **"★4 이상 보장"**이다 (표준 해금 p99 = 59회, §4.5).

**★5 하드 천장** (신설 `AwakenPityPulls = 100`)

- 마지막 ★5 이후 최대 100회. 자연 ★5·강제 ★5가 0으로 초기화.
- **★4 결과는 ★5 카운터를 초기화하지 않는다.**
- 100번째 회차에 ★5가 안 나왔으면 ★5를 강제 지급한다.
- 하드 천장이 지급한 회차에는 **소프트 천장도 함께 0으로** 돌아간다.

**처리 순서 (확정)**

```
1) 자연 결과 판정   outcome = Roll(random)
2) ★5 하드 천장     if (awakenPity + 1 >= 100 && Grade(outcome) < Legendary)
                        outcome = Awakening;   forced = hard
3) ★4 소프트 천장   else if (Grade(outcome) < Epic && pityCounter + 1 >= 30)
                        outcome = SkillUnlock; forced = soft
4) 카운터 갱신
      Legendary : awakenPity = 0, pityCounter = 0
      Epic      : pityCounter = 0, awakenPity++
      그 외     : pityCounter++,  awakenPity++
5) Grant(outcome)   §3.3의 미끄러짐 사다리
```

하드 천장이 자연 ★4를 덮어쓸 수 있다. 정상해상 빈도는 전체 뽑기의 **0.0137%**
(하드 발동 0.6542% × 자연 ★4 2.1%)이므로 규칙을 단순하게 유지한다.

### 3.8 중복 보상 - 공용 스킬 XP

> **이미 소진된 해금 결과는 공용 스킬 XP로 미끄러진다.**

별도 재화를 만들지 않는다. 재화가 하나 늘면 faucet·화면·세이브·밴드 모델이 함께 늘고,
공용 스킬 XP가 이미 그 일을 한다.

### 3.9 귀참 확정 지급

귀참(`skill_oni`)은 Lv.20 / st21 **진행 해금**이라 과금·뽑기와 무관하게 모든 플레이어가
각성 계열 1개를 확정 보유한다. 설계 변경 없음 - 계약으로 명시만 한다.

### 4.1 닫힌 식이 깨졌다 - 네 값 전부

`GachaCurve`의 닫힌 식(`PityShare`, `EffectiveRarityChance`, `ExpectedPullsPerEpic`)은

### 4.2 모델을 셋으로 나눈다 - 정상해 · 과도기 · 몬테카를로

#### 4.2.1 왜 정상해를 여정에 쓸 수 없는가 (실측)

v2.1은 정상해 값을 `StageSimulation`의 기존 누산기에 그대로 넣었다. **실측하니
그 값은 초반 구간에서 전혀 다른 이야기를 한다.**

`(soft, hard)` 분포를 (0,0)에서 출발시켜 뽑기마다 전진시킨 결과:

|---:|---:|---:|---:|---:|
| 1 | 2.10000% | 0.80000% | 18.4960 | 9.78e−1 |
| 10 | 2.10000% | 0.80000% | 18.4960 | 9.09e−1 |
| **30** | **43.45965%** | 0.80000% | 10.6176 | 7.75e−1 |
| 50 | 3.29943% | 0.80000% | 18.2675 | 6.60e−1 |
| **100** | 2.15271% | **45.58857%** | 9.9545 | 4.41e−1 |
| 101 | 3.09327% | 1.15831% | 18.2385 | 4.38e−1 |
| 200 | 3.11687% | 21.21847% | 14.4129 | 1.98e−1 |
| 300 | 3.54871% | 10.30345% | 16.4098 | 8.85e−2 |
| 400 | 3.74212% | 5.41477% | 17.3042 | 3.97e−2 |
| 600 | 3.86755% | 2.24452% | 17.8842 | 7.96e−3 |

읽어야 할 것은 두 줄이다.

- **뽑기 1회차의 XP는 18.4960이다** (= `TableXpPerPull`, 천장이 아직 아무것도 안 눌렀다).
  정상해 18.0297을 1회차에 쓰면 첫 10연의 XP를 **2.6% 적게** 준다.
- **100회차의 실제 ★5는 45.589%다.** 하드 천장이 그 회차에 몰려 있기 때문이다.
  정상해 1.449%를 쓰면 **29배 틀린다.** 그리고 그 메아리가 200회(21.2%)·300회(10.3%)·
  400회(5.4%)까지 이어진다. 무과금 A 시나리오가 **266일에 도달하는 지점이 276회**이므로,
  이 구간 전체가 과도기 안에 있다.

정상해가 재현하지 못하는 것을 그대로 적는다:

| 재현 못 하는 것 | 이유 |
|---|---|
| 신규 세이브의 카운터 0 시작 | 정상해는 시작점을 모른다 |
| 기존 세이브의 저장된 소프트·하드 상태 | 위와 같다 |
| 첫 무료 10연 | 10회 전부 1e0 수준의 과도기 안이다 |
| 첫 100회 이전 구간 | 표에서 보듯 값이 전혀 다르다 |
| ★4·★5 결과의 상관 | 두 개의 독립 누산기로는 "★5가 소프트를 초기화한다"를 못 적는다 |

#### 4.2.2 셋으로 나눈 역할

| 도구 | 쓰는 곳 | 왜 |
|---|---|---|
| **정상해** `SolveSteady` | 장기 확률 표(§4.4), 확률 정보 팝업(§5.3), 경제 보고 | 장기 평균만 필요하고, 값이 결정적이라 문서에 적을 수 있다 |
| **과도기** `Advance` | `StageSimulation`의 뽑기 여정, 세이브 복원, 무료 10연, 초기 구간 검증 | 시작 상태·첫 100회·★4/★5 상관을 전부 재현한다 |
| **몬테카를로 여정** (문서 밖 스크립트) | 중앙·p90·p99·최악값(§4.5) | 결정론적 누산기는 기댓값만 낸다. 분산은 못 낸다 |

#### 4.2.3 API 설계 (테스트 가능한 계산 함수)

```csharp
/**
 * @brief 이중 천장의 상태 분포. **정상해와 과도기가 같은 전이 함수를 쓴다.**
 *
 * 전이는 SkillGachaSystem.RollOnce와 같은 순서로 적는다 - 자연 판정 ->
 * ★5 하드 -> ★4 소프트 -> 카운터 갱신. 두 곳이 갈리면 시뮬이 재는 것과
 * 플레이어가 받는 것이 달라지고, 그 차이는 화면에도 로그에도 안 남는다.
 */
public static class SkillGachaPityModel
{
    public struct Rates
    {
        public double UnlockChance;    // 이 회차의 ★4
        public double AwakenChance;    // 이 회차의 ★5
        public double Xp;              // 이 회차의 기대 XP (수집기)
    }

    /**
     * @brief 상태 분포 한 벌. 크기는 소프트 x 하드다.
     *
     * hardPityPulls <= 0 이면 하드 천장이 꺼진 것이고, 그때는 **소프트 30칸만**
     * 쓴다(하드 축의 길이가 1). int.MaxValue 같은 값을 배열 크기로 쓰지 않는다 -
     * "끄기"는 큰 수가 아니라 **0 이하**로 말한다.
     */
    public sealed class State
    {
        public State(int softPityPulls, int hardPityPulls);
        public int SoftSize { get; }     // = softPityPulls (30)
        public int HardSize { get; }     // = hardPityPulls > 0 ? hardPityPulls : 1
        public void ResetToNewSave();                    // (0, 0) 에 확률 1
        public void ResetToSavedCounters(int soft, int hard);   // 기존 세이브
    }

    /** 분포를 뽑기 1회만큼 전진시키고, 그 회차의 기댓값을 돌려준다 */
    public static Rates Advance(State state);

    /**
     * @brief 정상해. 거듭제곱 반복으로 푼다.
     *
     * @param hardPityPulls 0 이하이면 하드 천장 없음 (소프트 30상태 경로)
     * @param tolerance     총변동거리 수렴 한계. 기본 1e-15
     * @param maxIterations 상한. 기본 20,000 (실측 4,430회 수렴)
     */
    public static Rates SolveSteady(int softPityPulls, int hardPityPulls,
                                    double tolerance = 1e-15, int maxIterations = 20000);
}
```

- **`SkillGachaCurve`의 네 프로퍼티는 `SolveSteady(PityPulls, AwakenPityPulls)`를
  가리킨다.** 이름에 장기 평균임이 드러나도록 요약 주석에 못 박는다.
- **`GachaCurve`의 닫힌 식은 요도 배너 몫으로 그대로 남는다** - 저쪽은 천장이 하나다.

#### 4.2.4 `StageSimulation` 개편

현재 두 개의 **독립 누산기**가 있다:

```csharp
levels.SkillUnlockProgress += SkillGachaCurve.EffectiveUnlockChance;   // 2984행
levels.SkillAwakenProgress += SkillGachaCurve.EffectiveAwakenChance;   // 3005행
```

이 둘을 **하나의 상태 분포**로 바꾼다.

```csharp
// TrySkillGacha 안, 뽑기 1회마다
var rates = SkillGachaPityModel.Advance(pityState);
levels.SkillXp             += rates.Xp;             // 2943행 자리
levels.SkillUnlockProgress += rates.UnlockChance;   // 2984행 자리
levels.SkillAwakenProgress += rates.AwakenChance;   // 3005행 자리
```

- **누산기 구조는 그대로 둔다.** 바뀌는 것은 **매 회차 값이 상수가 아니라 상태에서
  나온다**는 것뿐이고, 그래서 ★4·★5의 상관이 분포 안에서 보존된다.
- **상태를 `Levels` 구조체에 넣지 않는다.** 3,000 double = 24KB이고 `Levels`는
  `ref`로 도는 구조체다. `Levels.EquipScratch`가 이미 세운 **정적 스크래치** 방식을
  따라 `StageSimulation`이 `Run()` 시작에서 한 벌을 만들고 리셋한다.
- **정상해로 갈아타지 않는다.** §4.2.1의 실측이 그 이유다 - 갈아탈 만한 시점
  (859회)이 이 축의 실제 여정(귀오의 4종 276회, 최악 400회)보다 뒤에 있다.
- 비용: 3,000상태 × 3전이 ≈ 9,000 곱셈-덧셈 / 뽑기. 재고를 다 비우는 데 드는
  약 500회에서 4.5M 연산이라 `Run()` 한 번에 수십 ms다.

#### 4.2.5 회귀 안전선 - 하드 천장 OFF

`SolveSteady(30, 0)`은 **소프트 30상태만** 돌고, 기존 닫힌 식을 소수점까지 재현한다.

| 값 | `SolveSteady(30, 0)` | `GachaCurve` 닫힌 식 |
|---|---:|---:|
| ★4 | 4.145401% | 4.145401% |
| ★5 | 0.800000% | 0.800000% |
| XP | 18.1064 | 18.1064 |

이것이 §12.3의 테스트 8이다. **`int.MaxValue`를 배열 크기로 쓰지 않는다.**

| ★5 실효 확률 | 0.800000% | **1.448975%** | +81.12% |
| **★4 이상 합계** | 4.945401% | **5.347997%** | +8.14% |

|---|---:|
| ★4 중 소프트 천장이 만든 것 | 47.4982% |
| ★5 중 하드 천장이 만든 것 | 45.1498% |

| 기준 | 정상해 | 판정 |
|---|---:|---|
| ★4 실효 약 3.8990% | 3.899021% | ✅ |
| ★5 실효 약 1.4490% | 1.448975% | ✅ |
| ★4 이상 합계 약 5.3480% | 5.347997% | ✅ |
| ★5 기대 간격 69.01회 | 69.0143 | ✅ |

그리고 그 ★5가 **소프트 카운터를 초기화**해 30회 천장의 발동 기회를 가로챈다.
소프트 천장이 자연 ★5를 절대 덮어쓰지 않으므로 ★5 과정은 독립적으로 남고,
비대칭은 ★4 쪽에만 나타난다.

### 4.7 막힘 없음 검증

전투에 필요한 것(자리 + 진행 스킬 6종 + 귀참)은 전부 진행으로 열린다. 뽑기 9종은
전부 상한 기여 0.576 동률이라 없어도 기준 구성의 DPS가 안 내려간다.

## 5. UI

### 5.1 스킬 화면 - 공용 XP는 잔액이 아니라 진행도다

`SkillSystem.GrantXp`는 XP를 넣는 **즉시** `SpendXp()`로 살 수 있는 칸을 전부 산다.
화면에 남는 값은 "다음 한 칸에 모자란 나머지"뿐이다.

```
┌───────────────────────────────────────┐
│ 발도 오의                  [자동 시전 ON] │
│ [슬롯1][슬롯2][슬롯3][슬롯4]              │
│                                        │
│ 강화 중: 연참  ▓▓▓▓▓░░░  12 / 16         │  ← 보유·장착 스킬만 온다
│                                        │
│ ┌────────┬────────┬─────────┐          │
│ │  검식   │  혈식   │  귀오의   │          │
│ │  일반   │  상급   │   각성    │          │
│ └────────┴────────┴─────────┘          │
│ ╔════════════════════════════╗         │
│ ║ [아이콘] 연참    Lv.8 · 장착   ║        │
│ ║ [아이콘] 일섬    Lv.5         ║        │
│ ║ [아이콘] 심격    미보유         ║        │
│ ║          스킬 뽑기로 획득       ║        │  ← XP 진행도 없음
│ ╚════════════════════════════╝         │
└───────────────────────────────────────┘
```

| 상단 한 줄 | 표시 |
|---|---|
| 강화 대상이 있다 | `강화 중: {스킬명}` + `{잔여 XP} / {다음 레벨 필요 XP}` |
| 보유 오의가 전부 상한 | `모든 보유 오의 강화 완료` (게이지 없음) |

- **강화 대상은 반드시 보유 스킬이다.** 미보유 스킬은 이 줄에 절대 안 온다.
- 잔여 XP는 `SkillSystem.skillXp`, 필요 XP는 `XpToNextLevel(현재 레벨)`. 새 필드 없음.

| 행 상태 | 표기 |
|---|---|
| 미보유 | `미보유` + 서브라인 `스킬 뽑기로 획득` (실루엣). **XP 진행도 없음** |
| 보유·비장착 | `Lv.N` |
| 보유·장착 | `Lv.N · 장착` |
| 보유·상한 | `Lv.12 MASTER` |

**XP 적용 순서** (이미 코드에 있는 것을 화면에 드러낸다 - `SkillSystem.FindXpTarget`,
`StageSimulation.SkillXpTarget`): 장착 최저 레벨 → 벤치 최저 레벨 → 동률은 표 순서.

### 5.2 상점 배너와 **종료 조건 3단계**

`SkillSystem.HasStock`은 두 가지를 본다 (실측):

```csharp
// 1) 아직 못 얻은 가챠 몫이 있다        -> 재고 있음
// 2) 장착 오의 중 상한에 안 닿은 것이 있다 -> 재고 있음
//    (벤치의 미상한 오의는 재고에 안 센다)
```

따라서 **두 풀이 소진돼도 배너는 안 닫힌다.** 화면이 그 세 단계를 말해야 한다.

| 단계 | 상태 | 배너 표시 |
|--:|---|---|
| 1 | 두 풀에 재고 있음 | `다음 해금: 혈조 (혈식)` / `다음 귀오의: 귀신난무` |
| 2a | **표준 소진**, 귀오의 재고 있음 | `해금 소진 - XP로 지급` / `다음 귀오의: 참수` |
| 2b | 표준 재고 있음, **귀오의 소진** | `다음 해금: 검진` / `귀오의 소진 - 장착 오의 개안` |
| 2c | **두 풀 다 소진**, 장착 중 미상한 있음 | `해금 소진 - XP로 지급` / `귀오의 소진 - 장착 오의 개안` |
| 3 | 두 풀 소진 **AND 장착 오의 전부 상한** | **배너 종료.** `더 팔 것이 없습니다` |

```
┌───────────────────────────────────────┐
│ ◆ 보유 보석: 1,250                      │
│ ╔════════════════════════════╗         │
│ ║  스킬 뽑기                    ║        │
│ ║  다음 해금: 혈조 (혈식)         ║        │  ← StandardTargetFor()
│ ║  다음 귀오의: 귀신난무          ║        │  ← OniSecretTargetFor()
│ ║  [무료 1회]   (다음까지 3:12)   ║        │
│ ║  [1회 25◆]   [10회 225◆]      ║        │
│ ║  확정까지 12회    ▓▓▓▓░░░░     ║        │  ← ★4 소프트 (30)
│ ║  각성 확정까지 61회 ▓▓░░░░░░    ║        │  ← ★5 하드 (100)
│ ║  [확률 정보 〉]                ║        │
│ ╚════════════════════════════╝         │
└───────────────────────────────────────┘
```

- **`다음 해금` 문구는 반드시 `StandardTargetFor(mask)`가 돌려준 인덱스로 그린다.**
  온보딩 보상도 같은 함수를 읽으므로 세 곳(배너 문구·정상 뽑기·온보딩 보상)이
  **한 데이터**를 지난다.
- 두 게이지를 다 그린다. 하나만 그리면 ★5가 표 확률(0.8%)로만 보인다.
- `표준`의 `표`, `전환`의 `환`이 미굽기라 `해금 소진`·`지급`으로 적는다 (§10.1).

**폭발 피해 대상 - 포획 목록만 (확정)**

```
1. 시전 시각에 pullRange(5.0u) 안의 생존·비보스 적을 dx 오름차순으로
   최대 pullTargetCount(8)명 골라 **목록으로 확정(capture)**한다.
2. pullSeconds(0.25s) 동안 그 목록만 pullDestinationOffset(+1.6u)로 옮긴다.
3. hitFrames[0](0.333s)에 **그 목록에만** ×2.52를 준다.
4. 목록 밖은 피해 없음 - 9번째 이후, 범위 밖, 흡인 중 새로 스폰된 적, 보스.
5. 흡인 중 사망한 대상은 목록에서 빠진다. **총량을 남은 대상에 몰아주지 않는다.**
6. 도착 후 다음 큐 정렬에서 자기 자리로 복귀한다 (`EnemySpawner.SetTargetX`).
```

**왜 화면 전체가 아닌가**: 화면 전체에 피해를 주면 같은 rate(0.180)로 귀참·혈파동보다
**무조건 낫다**(같은 광역 + 끌어모으기 유틸리티). 그것은 §0.1의 첫 계약을 잡몹 층에서
깨는 것이다. 포획 목록 8명이 그 상한이고, 그래서 `Area = Captured`가 별도 값으로 선다.

**합격 기준 (방향을 양쪽으로 막는다)**

v2.1의 `장착 / 미장착 ≤ 1.020`은 **전투 시간이 절반이 돼도 통과한다.** 가속을 2%로
제한하려면 양방향이어야 한다.

| 검사 | 기준 |
|---|---|
| 클리어 시간 | **`0.9804 ≤ T(장착) / T(미장착) ≤ 1.0200`** |
| 초당 골드 | **`0.9804 ≤ G(장착) / G(미장착) ≤ 1.0200`** |
| 보스 여유 | 장착 구성의 모든 스테이지 `BossMargin` ≥ 기존 바닥 (Finale 1.08 / Chapter 1.25 / 그 외 1.4) |

`0.9804 = 1 / 1.0200`이다. 두 경계가 대칭이라 "빨라져도 느려져도 2%"가 된다.
±2.0%를 고른 근거: 가장 좁은 밴드 여유가 Finale의 **1.08(8%)**이고 2.0%는 그 **1/4**이다.

**측정 방법 (확정)**

| 항목 | 값 |
|---|---|
| 비교군 | **나락인력과 배율(×2.52)·쿨(14.0s)·레벨·`pullRange`·`pullTargetCount`가 모두 같고 흡인만 꺼진 대조 스킬.** 정적 테스트 훅 `SkillPerformer.SpecialsEnabled = false`로 만든다 (기본 true, 테스트만 끈다) |
| 측정 구간 | **st14~st50만.** st1~13은 이 오의를 획득할 수 없는 구간이라 제외한다 |
| 시드·웨이브 | **고정 시드 + 고정 웨이브.** 두 실행이 같은 스폰 순서를 본다 |
| 측정 경로 | **PlayMode에서 실제 전달 경로**(`DeliverSkillAll` / `DeliverSkillLane` / `DeliverSkillAround` / 포획 목록)를 지난다 |
| **금지** | **`StageSimulation`의 Rate 비교만으로 통과 처리하지 않는다.** 시뮬은 공간 거동을 모른다 - rate가 같으면 흡인이 있든 없든 같은 값을 낸다 |

**초과 시 축소 사다리 (사전 확정, 순서대로 적용하고 각 단계마다 재측정)**

| 순서 | 조정 | 값 |
|--:|---|---|
| 1 | `pullTargetCount` | 8 → **5** |
| 2 | `pullTargetCount` | 5 → **3** |
| 3 | `pullRange` | 5.0u → **3.5u** |
| 4 | `pullDestinationOffset` | +1.6u → **+2.4u** (밀집도 완화) |

네 단계를 다 적용해도 못 맞추면 **`Special`을 `None`으로 되돌려 심격과 같은
Single·Once로 폐기한다.** BaseRate 재조정은 하지 않는다 - 이 오의 하나 때문에
`ExpansionRate` 동률 계약을 깨는 것은 §0.1의 첫 계약을 무너뜨린다.

### 6.5 참수 (`skill_decapitate`) - 즉사 효과 제거

즉사는 "남은 체력과 무관하게 처치"라 초당 환산 기여로 잴 수가 없다. 그 순간 이 오의만
저울 밖에 서고 `ExpansionRate` 계약이 깨진다.

| 항목 | 확정값 | 저장 위치 |
|---|---|---|
| 피해량 | **×2.88 그대로.** 처형 연출 여부와 무관하게 항상 같다 | - |
| **`executionThreshold`** | **0.30** (공격 전 체력 비율) | **`SkillSpec`** (계약 테스트가 읽는다) |
| 처형 연출 조건 | 이 공격으로 **사망**하거나, 공격 **전** 체력 비율 ≤ `executionThreshold` | - |
| 보스 | **처형 연출 없음, 즉사 없음.** 그냥 ×2.88을 맞는다 | - |
| `clipFrameRate` / `hitFrames` | **24 / [7]** → 0.292s | Choreography |
| VFX 길이 | **1.667s** (40프레임). 상한 4.000s → 여유 2.333s ✅ | |

**합격 기준**: 처형 연출이 뜬 시전과 안 뜬 시전의 총 피해가 `1e-12` 이내로 같다.
보스 상대 총량이 다른 Single·Once 오의와 같은 규칙을 지난다.

### 6.6 귀왕강림 (`skill_oni_advent`)과 화면 플래시

**v2.1의 "`screenFlash = true`, 15종 중 유일"은 삭제한다.** 씬 실측 결과
**귀참과 혈폭이 이미 `screenFlash = 1`**이다. 귀왕강림까지 같은 플래시를 쓰면
세 오의의 큰 사건이 화면에서 같은 연출로 읽힌다.

**확정: 귀왕강림 전용 `flashTint` + `flashScale`을 준다. 기존 둘의 플래시는 제거하지 않는다.**

```csharp
// Choreography (씬) - 신설 두 필드
public Color flashTint  = Color.white;   // ScreenFlash.Play(Color) 오버로드가 이미 있다
public float flashScale = 1f;            // edgeSeconds·vignetteSeconds에만 곱한다
```

`ScreenFlash`에는 `Play()`와 `Play(Color edgeTint)`가 **이미 있다**(실측).
지속 배율만 받는 오버로드 하나(`Play(Color, float durationScale)`)를 더한다.
**강도(`edgePeak` 0.85 / `vignettePeak` 0.88)는 건드리지 않는다** - 곱하면 1을 넘어
클램프되고, 그러면 "더 세게"가 화면에서 안 읽힌다. 세기의 차이는 **색**이 말한다.

| 스킬 | `screenFlash` | `flashTint` | `flashScale` | 결과 지속 (edge / vignette) |
|---|---|---|---:|---|
| 귀참 | true (기존) | `#FFFFFF` (기존과 동일) | 1.0 | 0.100s / 0.340s |
| 혈폭 | true (기존) | `#FFFFFF` (기존과 동일) | 1.0 | 0.100s / 0.340s |
| **귀왕강림** | **true** | **`#E85A00`** (자기 `SlashRgba`) | **1.4** | **0.140s / 0.476s** |

- 귀참·혈폭은 `flashTint = white` / `flashScale = 1.0`이라 **기존 동작과 비트 동일**하다.
  기본값이 그 값이므로 씬 데이터를 손대지 않아도 된다.
- 귀왕강림만 색이 다르고 40% 길다. 그 두 가지가 "가장 큰 사건"을 말한다.
- **`flashTint`는 서로 갈려야 한다** (§1.3). 흰색과 `#E85A00`의 거리는 0.699로
  `SlashRgba` 계약의 0.25를 여유 있게 넘는다.

| 항목 | 확정값 |
|---|---|
| 거동 | Screen · Once · None (새 거동 코드 0줄) |
| `clipFrameRate` / `hitFrames` | **24 / [9]** → 0.375s |
| VFX 길이 | **2.500s** (60프레임). 상한 4.750s → 여유 2.250s ✅ |

**"가장 강한 한 방"이 아니다.** 배율 ×3.42는 귀참 ×3.52보다 낮다.

| 항목 | 문구 |
|---|---|
| 무엇인가 | **가장 큰 연출을 가진 장기 목표 스킬.** 15종 수집의 마지막 칸 |
| 단발 피해 최상위 | **귀참**(×3.52). 진행 확정이라 모든 플레이어가 갖는다 |
| 귀왕강림의 값 | 최장 쿨(19.0s)의 무게 + 전용 플래시 + 수집 완성의 정점 |

배너·도감 문구에서 "최강"·"가장 강한"이라는 낱말을 쓰지 않는다.

### 6.7 거동 데이터 구조 - 세 필드로 확정

`SkillArea` + `SkillSplit` **둘로는 부족하다.** 흡인·처형·장판 지속·화면 플래시를
구분할 수 없어서, 구현이 ID나 `VfxId` 문자열로 특수 효과를 추측하는 쪽으로 흐른다.
그것은 `SkillFamily`를 명시적 데이터로 둔 이유(§1.1)와 정면으로 어긋난다.

```csharp
/** 어디를 때리는가 */
public enum SkillArea
{
    Single,     // 최근접 하나
    Pierce,     // 전방 일렬 (dx ∈ [-0.3, pierceRange])
    Screen,     // 살아 있는 전부
    Around,     // 시전자 중심 원 (aroundRadius)
    Field,      // 전방 장판 (fieldRange x fieldHeight), 시간에 걸쳐 틱
    Captured    // 특수 거동이 확정한 목록 (지금은 Pull 하나)
}

/** 몇 번에 나눠 때리는가 */
public enum SkillSplit { Once, MultiHit }

/** 데미지 공식 밖의 특수 거동. **문자열로 추측하지 않는다** */
public enum SkillSpecial
{
    None,
    Pull,        // 대상을 포획해 한 점으로 옮긴다 (나락인력)
    Execution    // 처형 연출 판정 (참수). 피해량은 안 바꾼다
}
```

**수치의 저장 위치 (확정)**

규칙은 기존 코드가 이미 세운 것을 따른다 - **밸런스 계약에 들어가는 값은
`SkillSpec`(코드, 테스트·시뮬이 읽는다), 화면 배치·타이밍은 `Choreography`(씬)**.
`pierceRange`/`pierceHeight`가 씬에 있는 것이 그 선례다.

| 값 | 위치 | 이유 |
|---|---|---|
| `Area` · `Split` · `Special` | **`SkillSpec`** | 거동 분기. 시뮬·테스트가 읽는다 |
| `HitCount` (검진 4틱, 귀신난무 5타) | **`SkillSpec`** (기존 필드 재사용) | 총량 분할 수 = 총량 계약 |
| **`pullTargetCount`** (8) | **`SkillSpec`** | 최대 피해 대상 수 = 총량 계약 |
| **`executionThreshold`** (0.30) | **`SkillSpec`** | 계약 테스트가 읽는다 |
| `pierceRange` · `pierceHeight` | Choreography (기존) | 화면 배치 |
| **`aroundRadius`** (회월참 3.0) | Choreography (신설) | 화면 배치 |
| **`fieldRange`·`fieldHeight`** (검진 3.6 / 2.6) | Choreography (신설) | `pierceRange`/`pierceHeight`와 같은 자리 |
| **`fieldDuration`** (검진 1.5s) | Choreography (신설) | 클립 길이와 같은 자리 |
| **`pullRange`** (5.0) · **`pullDestinationOffset`** (+1.6) · **`pullSeconds`** (0.25) | Choreography (신설) | 화면 배치·타이밍 |
| `screenFlash` (기존) · **`flashTint`** · **`flashScale`** | Choreography (신설 둘) | 연출 |

## 8. 세이브 v20

현재 `SaveData.CurrentVersion = 19`. **추가 필드는 정확히 셋이다.**

| 항목 | 현재 | 신규 요구 | 버전 영향 |
|---|---|---|---|
| 신규 스킬 ID 추가 | `skillIds[]`/`skillLevels[]` id 병렬 배열 | 카탈로그 7종 추가만 | **없음** |
| 뽑기 보유 | `gachaSkillIds[]` (string) | 그대로 (9종으로 확대) | **없음** |
| 공용 스킬 XP | `skillXp` (long) | 그대로 | **없음** |
| ★4 소프트 천장 | `skillGachaPity` | 그대로 | **없음** |
| **★5 하드 천장** | 없음 | **`skillGachaAwakenPity`** (int) | **v20** |
| **온보딩 10연 수령** | 없음 | **`skillGachaIntroClaimed`** (bool) | **v20** |
| **온보딩 장착 완료** | 없음 | **`skillGachaIntroEquipDone`** (bool) | **v20** |
| 일일 무료 시각 | `skillGachaFreePullDayTicks` | 그대로 | 없음 |

**세 번째 필드가 필요한 이유**: 파생 조건(`introClaimed && 혈조 보유 && 혈조 미장착`)은
**1회성이 아니다.** 플레이어가 나중에 혈조를 빼면 온보딩 강조가 되살아난다.
`skillGachaIntroEquipDone`을 두면 **혈조를 처음 장착한 순간 true**가 되고 이후
다시 강조하지 않는다 (§10.3).

### 8.1 v19 → v20 마이그레이션 정책 (확정)

```
skillGachaAwakenPity     = 0
skillGachaIntroClaimed   = false
skillGachaIntroEquipDone = false
```

**`min(skillGachaTotalPulls, 99)`로 소급하지 않는다.** `skillGachaTotalPulls`는 누적
횟수일 뿐이고 하드 천장이 재는 것은 **마지막 ★5 이후**의 횟수다. 두 값 사이에 함수
관계가 없다:

- 200회를 돌며 ★5를 세 번 받은 플레이어와 한 번도 못 받은 플레이어가 같은
  `totalPulls = 200`을 갖는다.
- 게다가 v19의 ★5는 "개안"이라 **해금 이력이 저장되지 않았다.** 복원할 원본이 없다.

그 대신:

> **모든 기존 플레이어에게 온보딩 무료 10연을 제공한다.**
> `skillGachaIntroClaimed = false`가 그 지급 경로이고, **의도한 업데이트 보상**이다.

한 줄 정책: **하드 천장은 리셋, 보상은 무료 10연.**

### 8.2 복원 규칙

```csharp
// SkillGachaSystem.Restore - 기존 소프트 천장과 같은 처리
awakenPity     = Mathf.Clamp(savedAwakenPity, 0, SkillGachaCurve.AwakenPityPulls - 1);
introClaimed   = savedIntroClaimed;
introEquipDone = savedIntroEquipDone;
```

복원된 `(pityCounter, awakenPity)`는 §4.2의 `State.ResetToSavedCounters(soft, hard)`로
그대로 들어간다. **기존 세이브의 천장 상태에서 과도기를 이어서 전진시킨다** -
이것이 정상해로는 못 하는 일이다 (§4.2.1).

## 9. Firebase 크로스 저장 - 이번 범위 밖

**Firebase는 이번 스킬 구현 범위에 포함하지 않는다.** 남기는 것은 요구사항뿐이다.

- `gachaSkillIds`는 **획득 손실 방지가 필요**하다.
- **무료 10연 중복 수령 방지가 필요**하다 (`skillGachaIntroClaimed`).
- **천장·XP·레벨은 서로 연관된 상태이므로 필드별 `max` 병합을 금지한다.**
  기기 A에서 XP를 레벨로 바꾸고 B에서 XP를 쌓았다면 max는 **레벨과 XP를 둘 다
  높은 쪽으로 가져와 재화를 복제**한다. 천장도 같다 - ★5를 받아 0이 된 기기와
  99까지 쌓은 기기를 max로 합치면 **★5를 받은 사실이 사라진다.**
- 향후 크로스 저장 단계에서 `saveVersion`·`revision`·`updatedAt` 기반의
  **전체 저장 충돌 정책**을 별도로 설계한다.

### 10.1 폰트 문자셋 (실측)

`Assets/_Project/Data/FontCharset.txt`를 대조한 결과, **반드시 새로 구워야 하는 글자는
6자**다: **식 · 신 · 난 · 락 · 왕 · 림** (검식/혈식, 귀신난무, 나락인력, 귀왕강림).

문구에서 걸린 나머지는 **이미 구워진 낱말로 다시 써서 굽지 않는다**:

| 미굽기 | 초안 문구 | 확정 문구 |
|---|---|---|
| 표 | 확률**표** / **표**준 해금 소진 | `확률 정보` / `해금 소진` |
| 환 | XP로 전**환** | `XP로 지급` |
| 쓰 | **쓰**입니다 | `필요합니다` |
| 넣 | **넣**어라 | `장착하라` |
| 얻 | **얻**은 | `받은` |
| 카 | 중복 **카**드 | (표현 자체를 폐기 - §3.8) |

**하베스트 경로**

`FontCharsetBuilder.DisplayNames()`는 **이미** 다음을 걷는다 (실측 - 86·106·109행):

- `SkillCatalog.Skills[].DisplayName` → **신규 7종의 이름이 자동으로 따라간다**
- `GuideQuestCatalog.Steps[].Action` → **신규 가이드 문구가 자동으로 따라간다**
- `GuideQuestCatalog.StateWords`

따라서 **새 하베스트를 만들지 않는다.** 새로 연결할 것은 하나뿐이다:

> **계열 표시 문자열(`검식`·`혈식`·`귀오의`와 부제 `일반`·`상급`·`각성`)의 원본을
> `FontCharsetBuilder.DisplayNames()`에 물린다.**

원본은 `SkillCatalog.FamilyNames` / `FamilySubtitles` 정적 표로 둔다.
표를 UI 쪽에 두면 하베스트가 에디터 어셈블리를 참조하게 되고, 그것은 `SkillVfx`
상수를 런타임에 둔 이유와 같은 함정이다.

**실행**: 구현 2단계에서 `Rebuild Font Charset` → `Build Pixel Font Assets`.

### 10.3 st14 온보딩 가이드 - 최소 구조로 확정

**업적도, 퀘스트 메트릭도, 보석 보상도 추가하지 않는다.**

**기존 진행선 (실측 - `GuideQuestCatalog.steps`)**

```
1 ach_stage5     "요괴를 베고 나아가라"   (st5)
2 ach_level10    "레벨을 올려라"          (Lv.10)
3 ach_upgrade50  "골드로 강화를 사라"     (강화 총합 400)
4 ach_stage10    "지역 1을 돌파하라"      (st10)
5 ach_skill12    "오의를 배우고 올려라"   (오의 강화 9회, SkillLevelTotal)
6 ach_stage20    "지역 2를 돌파하라"      (st20)
...
```

`ach_skill12`는 **오의 강화 9회**이지 Lv.10 해금이 아니고, Lv.10은 **두 번째 칸**이다.
v2의 `st10 → st14 → Lv.10` 설명은 코드와 다르므로 **삭제한다.**

**확정 구조**

| 항목 | 값 |
|---|---|
| 삽입 위치 | `ach_stage10`(4번 칸)과 `ach_skill12`(5번 칸) **사이** = 새 5번 칸 |
| 가이드 문구 | **`상점에서 무료 스킬 10회를 받아라`** |
| 완료 조건 | **`skillGachaIntroClaimed == true`** |
| 표시 조건 | `frontierStage >= ShopCurve.UnlockStage` (14). 그 전에는 칸을 건너뛴다 |
| 보상 | **없음.** 카드의 보상 칸을 숨긴다 |

**최소 코드 변경 (퀘스트 표 0행, 메트릭 0개 추가)**

```csharp
// GuideQuestCatalog.cs
public enum GuideGate { Quest, SkillGachaIntro }   // 신설

public struct GuideStep
{
    public string     QuestId;   // Gate == Quest 일 때만 쓴다
    public QuestKind  Kind;
    public int        Index;
    public string     Action;
    public GuideGate  Gate;      // 신설. 기본값 Quest
    public int        MinStage;  // 신설. 0이면 조건 없음
}

// GuideQuestLine.cs - 인자 둘이 늘어난다
public static GuideQuestView Resolve(QuestSystem quests, int frontierStage, bool introClaimed);
```

- `Gate` 칸은 `ClaimableCount`를 안 지나므로 **절대 `Claimable`이 안 된다.** 항상
  `InProgress`로 떴다가 완료되면 사라진다. "받기" 버튼이 없는 것이 이 칸의 정의다.
- `Describe`: `Title = "무료 10회 뽑기"`, `Target = 1`, `Progress = introClaimed ? 1 : 0`,
  `Gems = 0`. `GuideQuestCard`는 `Gems == 0`이면 보상 칸을 숨긴다.

#### 10.3.1 혈조 온보딩 - **강화 먼저, 교체는 그 다음**

v2.1의 "혈조와 연참은 상한 기여가 같으니 교체해도 손해가 아니다"는 **온보딩 시점에는
틀린다.** 혈조는 방금 받아 **Lv.1**이고 연참은 이미 골드로 강화됐으며 상성까지 얹혀
있을 수 있다.

**실제 기여의 정의 (코드에 이미 있다)**

```csharp
// SkillSystem.CastRate 루프 본문을 CurrentRateOf(int)로 추출한다
현재 기여(i) = MultiplierOf(i) / cooldownSeconds(i)
             = CappedMultiplierAtLevel(base, level)          // 현재 레벨
               x YodoSystem.CurrentAffinityForSkill(i)       // 적용 중인 상성
               / cooldownSeconds
```

**상한값(`CeilingRateOf`)만 비교하지 않는다.** 상성은 상한 **위에** 얹히는 별개 층이고
(`MultiplierOf` 주석), 레벨은 지금 값이다.

**실측 예**: 혈조 Lv.1 = `0.45 / 2.5` = **0.180**. 연참 Lv.5 = `0.54 × 1.12⁴ / 3`
= **0.283**. 혈조가 연참 Lv.5를 따라잡으려면 `1.12^k ≥ 1.5735` → **혈조도 Lv.5**여야 한다.
Lv.1 혈조를 그 자리에 끼우면 **기여가 36% 줄어든다.**

**확정 흐름**

```
1. 혈조 획득 (온보딩 보상 또는 자연 ★4)
2. weakest = 장착 슬롯 중 CurrentRateOf 가 가장 낮은 것
3. CurrentRateOf(혈조) < CurrentRateOf(weakest)
     -> **혈조 강화 버튼을 먼저 강조**한다
        목표: NextRateOf(혈조) >= CurrentRateOf(weakest)
        (NextMultiplierOf 가 이미 있으므로 다음 칸의 기여를 미리 잴 수 있다)
4. CurrentRateOf(혈조) >= CurrentRateOf(weakest)
     -> **weakest 슬롯을 강조**한다 (교체)
5. 혈조가 장착되는 순간 skillGachaIntroEquipDone = true. 이후 다시 강조하지 않는다
```

- 빈 슬롯이 있으면 3·4단계를 건너뛴다. `GrantGachaSkill`이 `FillEmptySlots`를
  부르므로 혈조가 이미 자동으로 들어가 있고, 그 순간 `introEquipDone = true`가 된다.
- st14 시점의 자리 수는 `SkillCurve.SlotsFor`가 **레벨 게이트 오의의 수**로 정하므로
  연참(Lv.10)·일섬(Lv.15) 기준 **1~2칸**이다. 실전에서 `weakest`는 대개 연참이다.
- **일섬을 밀어내지 않는다.** 일섬의 상한 기여는 0.800으로 뽑기 9종(0.576)보다 높고,
  현재 기여 비교에서도 대개 가장 낮은 자리가 아니다. "가장 낮은 기여" 규칙이 그 보증이다.

**문구 글자 검사**: `상점에서 무료 스킬 10회를 받아라`의 모든 글자가 아틀라스에 있다. ✅

### 12.7 7단계 실기 확인에서 드러난 미연결 두 곳 (2026-08-15)

**632개 테스트가 전부 통과하는 상태에서도 이 둘은 안 잡혔다.** 잡힐 수가 없었다 -
§12.3의 테스트 23·24가 **아직 안 쓰여 있었기** 때문이다. 스위트가 초록인 것과
기능이 붙어 있는 것은 다른 사실이고, 그 차이를 메우는 것이 실기 확인이다.

| # | 무엇이 끊겨 있었나 | 왜 조용했나 | 이번에 한 것 |
|--:|---|---|---|
| 1 | **가이드 카드가 온보딩 칸을 못 그린다** | `GuideQuestCard`가 세 자리에서 전부 **1인수 `Resolve(quests)`**를 부르고 있었다. 그 판의 기본값이 `frontierStage: int.MaxValue, introClaimed: false`라, 온보딩 칸이 **st1부터 뜨고 받은 뒤에도 안 사라진다** - 완료할 수 없는 안내가 카드를 영영 붙잡는다. 3인수 판은 테스트만 쓰고 있었다 | 카드가 `SkillGachaSystem`을 물고 `stage.MaxStageReached`·`gacha.IntroClaimed`를 넘긴다(`Current()` 한 자리로 모았다). 뽑기의 `Changed`도 구독한다 - 무료 10연을 받는 순간 칸이 빠져야 하는데 그 사실은 다른 넷 중 누구도 안 알린다. **1인수 판의 기본값도 뒤집었다**(`0, true` = 감춘다): 두 기본값 다 틀릴 수 있지만 감추는 쪽은 안내 한 줄이 없는 것이고 띄우는 쪽은 못 깨는 안내다 |
| 2 | **혈조 강조가 아예 없다** | `skillGachaIntroEquipDone`은 세이브에 있고 왕복도 하는데 **읽는 화면이 없었다.** `MarkIntroEquipDone`은 호출자가 0개였다. §10.3.1의 "강화 → 교체" 흐름이 문서에만 있었다 | `SkillIntroGuide`(순수 계산) + `IntroHighlight`(금색 깜빡임) 신설. `SkillButton`·`SkillSlotChip`이 각각 자기 차례에 켠다. 표식은 `SkillGachaSystem`이 `skills.Changed`에서 스스로 세운다 - 장착 경로가 하나가 아니라(`FillEmptySlots`가 사람 손 없이 끼운다) 버튼에 맡기면 그 길을 놓친다 |

**흐름이 두 걸음이 아니라 세 걸음이다.** 문서의 `강화 → 교체`는 이 게임에 없는
동작을 가정했다 - **밀어내며 끼우기가 없다.** 칩을 눌러 비우고(`Equip(slot, -1)`)
줄의 장착을 누르는 **두 동작**이라, 안내도 그만큼 나뉜다:

```
Upgrade   혈조 줄        아직 약하다. 강화 버튼을 가리킨다
Swap      가장 약한 칩   따라잡았다. 눌러서 비우라고 가리킨다
Equip     혈조 줄        자리가 비었다. 장착 버튼을 가리킨다
None      -              끼웠다(introEquipDone). 다시는 안 뜬다
```

`Swap` 다음에 `Equip`이 없으면 방금 비운 빈 칩이 계속 깜빡인다 - 플레이어가
이미 한 일을 또 하라는 말로 읽는다.

**비교 기준도 문서보다 좁혔다.** §10.3.1은 연참을 상대로 적었는데, 판정이 실제로
보는 것은 **그 구성에서 가장 약한 자리**다. 자리가 둘이면 채움용으로 들어간 일섬
(0.250)이 연참 Lv.5(0.283)보다 약해 그쪽이 기준이 된다. 테스트를 연참 기준으로
짰다가 `Swap`이 먼저 떠서 걸렸고, 그것이 맞는 동작이다.

| 새 테스트 | 무엇을 잠그나 |
|---|---|
| `TheIntroHighlight_NeverReturnsAfterEquipping` | 끼운 뒤 **다시 빼도** 강조가 안 돌아온다. 대조군으로 표식만 없애면 조언이 나오는 것까지 확인한다 - 아니면 "언제나 None"이라서 통과한 것과 구별이 안 된다 |
| `TheIntroFlow_UpgradesBeforeSwapping` | 가장 약한 자리를 넘어서기 **전까지는 계속 강화**, 넘어선 칸에서 교체로 바뀐다. 경계 레벨을 상수로 안 적고 실제 값을 재서 찾는다 |
| `TheIntroFlow_PointsAtTheRowOnceASlotIsFree` | 자리를 비우면 조언이 칩에서 **줄로 옮겨간다** |
| `TheIntroHighlight_StaysQuietBeforeTheFreePull` | 안 받았으면 아무 말도 안 한다 |
| `TheIntroHighlight_NeedsTheSkillFirst` | 없는 오의를 끼우라고 안 한다 |

   노출되는 창이 존재하지 않는다.

**단 하나의 외부 의존 - 확인 결과 막혀 있다 (2026-08-15)**

아이콘 원본 팩(`RPG SKILL ICONS v1.7`)이 **이 기기에 없다.** `SOURCE.txt`의 경로는
다른 사용자 계정(`C:\Users\User\...`)이고, 현재 계정의 애셋 폴더
(`C:\Users\ASUS\Desktop\UnityAssets`)에도 KURAI 팩이 없다. 리포 안의 16개는
8개가 오의, 8개가 강화 축·재화라 **남는 것이 0개**다(§10.2).

그래서 **4단계(신규 7종 카탈로그·VFX·아이콘)가 여기서 멈춘다.** 1~3단계는
영향받지 않고 이미 끝났다. 푸는 방법은 셋이고, 고르는 것은 사용자의 몫이다:

| 안 | 내용 | 대가 |
|---|---|---|
| **A** | 원본 팩을 이 기기로 옮긴다 (구매판이라 재다운로드 가능) | 없음. 설계 그대로 간다 |
| **B** | 다른 16px 아이콘 팩을 새로 들인다 | 15종의 그림 언어가 두 팩으로 갈린다 |
| **C** | 7종을 절차적으로 굽는다 (BackdropTextureBuilder와 같은 방식) | 구매 팩과 나란히 두면 손그림 티가 난다 |

**권장은 A다.** B·C는 §10.2가 "신규 아트 필요 없음"으로 잡아 둔 전제를 깬다.

**착수 순서**: 1단계(테스트 선행 보강) → 2단계(SkillFamily·탭·폰트) → 3단계(거동 구조).
1단계는 코드 변경 없이 테스트만 늘리므로 되돌리기가 가장 싸고, 3·5단계의 안전선을
미리 세워 둔다.
