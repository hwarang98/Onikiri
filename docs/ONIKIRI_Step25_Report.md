## F-1 밑동 rooting (재검증)

원인은 **나무 시트 자체의 바닥 여백**이었다. 나무 레이어 Y도 지면 스트립 Y도 아니다.

| 시트 | 캔버스 | 잉크 y | 바닥 여백 |
|---|---|---|---|
| 가을 `Trees.png` | 400×160 | 0..130 | **0px** |
| 봄 `Color 1.png` | 448×160 | 16..154 | **16px (0.5u)** |

두 지면 스트립 모두 바닥 여백 0px이라 조립은 처져 있지 않았다. 가을이 안 떠 보인 것은
아트가 캔버스 바닥에 붙어 있어서다 - 그래서 **가을의 나무↔지면 상대 Y가 곧 기준값**이고,
봄도 같은 규칙(그려진 밑동을 지면선에 맞춤)으로 맞췄다.

```
lift = (groundSurfacePixels − artBottomPixels) / PPU
가을 Maples  (48 − 0)/32 = 1.500u   <- 기준값. 안 움직였다
봄   Sakura  (24 − 16)/32 = 0.250u
```

값은 빌더가 픽셀로 실측해 채운다(`MeasureArtBottom` / `BackfillArtBottom`).
요괴의 `EnemyDefinition.artBottomOffset`과 같은 값·같은 이유다.

**F-2로 벚꽃을 뒤로 보낸 뒤 다시 쟀다:**

```
잉크 밑동 -0.164  vs  GroundY -0.164   차이 0.0000
스크롤 중  x -12.91 -> -0.93 (되감기 포함), 잉크 밑동 -0.164 고정
```

`ParallaxScroller.Place`가 `new Vector3(x, local.y, local.z)`로 y를 보존하므로 세로
정렬은 구조적으로 가로 스크롤과 무관하다. 정렬 순서도 그대로 `Sakura < Ground`라
밑동이 잔디 띠에 가려진다.

## F-2 벚꽃을 먼 레이어로

24단계에는 0.88(지면 바로 뒤)이었다. 큰 나무가 캐릭터·대장간과 같은 깊이에 서서
화면 앞을 막았다.

레이어를 **속도 순으로 다시 세웠다.**

```
        24단계                        25단계
  0     Sky_Fill                      Sky_Fill
  0.12  Sky                           Sky
  0.30  Mountains                     Mountains
  0.52  Conifers                      Sakura      0.38   <- 뒤로
  0.72  Brush                         Conifers    0.52
  0.10  DawnHaze                      Blacksmith  0.60   <- 벚꽃 앞
  0.26  Blacksmith                    DawnHaze           <- 덤불 뒤로
  0.88  Sakura                        Brush       0.72
  1.00  Ground                        Ground      1.00
```

크기는 그대로지만 침엽수·덤불·대장간이 앞에 서면서 줄기가 가려지고 꽃 덩어리만
남아 **원경의 벚꽃 숲**으로 읽힌다. 대장간이 벚꽃 앞으로 나와 랜드마크가 나무에
가리지 않는다.

### 상단은 허전해지지 않았다 — 채울 것 없음

패럴랙스를 늦춰도 **스프라이트 크기는 그대로**라 화면에서 차지하는 면적이 줄지 않는다.
달라진 것은 깊이(가려지는 순서)와 흐르는 속도뿐이다. 후지산·구름·벚꽃 캐노피가 위쪽을
그대로 채우고 있어 추가 아트가 필요 없다고 판단했다.

### 대신 중경이 평평해져서 안개를 옮겼다

벚꽃이 빠지자 덤불(layer_4)이 화면에서 가장 넓은 면이 되었고, 그 위에 여명 안개가
덮이니 중경 전체가 평평한 갈색 덩어리가 됐다. 안개를 **덤불 뒤로** 옮겼다 - 대기
원근은 먼 것에만 끼는 것이므로 원래도 그게 맞았고, 벚꽃이 앞에 있던 동안에는 덤불이
나무에 가려 티가 안 났을 뿐이다.

## F-3 강화 패널 배경 분리

24단계까지 하단 UI 뒤는 **비어 있었고 라이브 씬의 하늘 채움이 그대로 비쳤다.**
문제가 없어 보였던 것은 지역 1·3이 자줏빛 밤이라 뒤가 어두웠기 때문이다 - 패널이
불투명해 보였을 뿐 실은 씬을 비추고 있었다. 봄숲이 들어오자 하단 절반이 하늘색으로
물들었다.

`SafeArea` 맨 뒤에 **지역과 무관한 고정 바탕** 한 장을 깔았다.

```
PanelBackdrop   y 0 .. GrowthPanelTop(0.45), 안전 영역 아래로 -400 흘림
  sprite  WashiPaper (64x64 타일)
  color   #221D30  (UiSkin.PanelInk)
  TopEdge 6px, #4A3E5C  (UiSkin.PanelEdge)
```

- **화지 질감**: 64×64 타일. 펄린 얼룩 + 가로 섬유 7줄 + 세로 3줄. 값 범위를
  **0.90~1.00으로 좁게** 잡았다 - 곱연산이라 원본 대비가 그대로 증폭되고, 세게 잡으면
  행 카드·아이콘 경계가 질감에 묻힌다(프롬프트가 경고한 함정). 결정론적 시드라 다시
  구워도 무늬가 같다.
- **경계선**: 탭 바 위 6px 먹선. 바탕이 아무리 어두워도 선이 없으면 두 영역이
  그라디언트처럼 이어져 "위=씬 / 아래=UI"가 안 읽힌다.
- **행 카드·헤더 색·MASTER 표기는 손대지 않았다.** 바뀐 것은 밑바탕뿐이다.
- `PanelInk`(#221D30)를 `BarTrack`(#181424)보다 살짝 밝게 잡았다. 둘이 같으면 체력·
  경험치 바의 빈 칸이 바탕에 묻혀 테두리가 사라진다.

세 지역 모두에서 `PanelBackdrop color = RGBA(34,29,48)` 동일함을 확인했다.

## F-4 가로 이음새 — 원인은 **(c) 세로 타일링**

### 진단

하늘 채움은 그 지역의 **먼 배경 시트를 그대로** 쓰고 `BattleStageLayout`이 카메라
크기로 타일링했다. 타일링은 세로로도 반복된다:

```
가을 3.png 180px(5.63u)  vs  채움 크기 19.36u  =>  세로로 3.44번
이음매 위치 world y = -9.68 + 5.63k  =>  -4.05, 1.58, 7.21
전투 밴드 -0.91..6.22  =>  y=1.58 이 밴드 한가운데
```

3.png는 아래쪽에 창백한 나무 줄기 띠가 그려져 있다. 세로로 반복되면 **그 줄기 띠가
화면 중턱에 다시 나타나** 배경이 갈린 것처럼 보인다.

> (a)도 (b)도 아니었다. 시트 맨 윗줄과 맨 아랫줄의 색차는 **0.0000**이라 타일 경계
> 자체에는 색 단차가 없었다 - 색이 아니라 **내용의 반복**이다.

### 수정

채움을 그림이 아니라 **면**으로 바꿨다(`BackdropTextureBuilder.SkyFill`, 64×704).
내용이 없으면 반복해도 이음매가 없고, 22u는 가장 긴 지원 비율(카메라 19.36u)보다
길어 애초에 세로 반복이 일어나지 않는다. 색은 지역별 틴트가 정한다.

### (c)를 고치자 (a)가 드러났다

먼 아트는 180px에서 끝나는데 밴드는 9:19.5에서 211px이다. 그 위를 채움이 그리므로
색이 다르면 시트가 끝나는 높이에 선이 그어진다.

**한 레이어의 색으로는 맞출 수 없었다.** 가장 먼 시트(3.png) 맨 윗줄 × 그 틴트
= #7382A8로 잡았더니 **오히려 나빠졌다**(0.0562 → 0.2993). 그 높이에는 2.png와
1.png의 반투명 실루엣이 겹쳐 있어 실제 화면 색은 #292E4D였다. 계산이 아니라
**렌더된 화면을 찍어서 재야 하는 값**이다(가운데 UI를 피해 좌우 가장자리만 표본).

### 결과 — 세 지역 모두

| 지역 | 옛 세로타일링 자리 | 아트 윗끝선 | 채움 틴트 |
|---|---|---|---|
| 1 봄숲 | — | **0.0339** | #92CCD7 |
| 2 가을숲 | 0.0028 → **0.0115** | 0.2993 → **0.0000** | #2C3151 |
| 3 사쿠라 밤 | — | **0.0000** | #6A5D78 |

(0.05를 넘으면 선으로 보인다. 밴드 중턱 실측은 수정 전 육안 확인, 수정 후 0.0028)

- **지역 3은 원래 이음매가 없었다.** Sky.png가 63,540픽셀 전부 같은 색인 완전 단색이라
  세로로 반복해도 표가 나지 않는다. 그래도 같은 면을 쓰게 한 이유는, 채움이 지역마다
  다른 규칙을 따르면 다음 지역에서 또 틀리기 때문이다.
- **지역 1만 0이 아니다.** 끝선 바로 아래에 있는 것이 흐르는 구름이라 그 높이의 색이
  매 프레임 달라진다. 구름이 닿지 않는 평평한 하늘에 맞췄고, 남는 0.0339는 이음매가
  아니라 구름 자체다.
