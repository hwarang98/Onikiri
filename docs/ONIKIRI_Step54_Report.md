작업일: 2026-08-13
테스트: EditMode **539/539 통과** (신규 23)
세이브: **v18 → v19** — 새 필드 하나(`playerName`). 진행·밸런스 값은 한 글자도 안 바뀜

클라가 주장한 숫자이고, 잠근 것은 값이 아니라 **구조**다.

## L-1. 자동 제출 — 계기 셋, 그리고 "높을 때만"

`LeaderboardSubmitter`가 `StageProgress.Changed`를 듣는다. 제출이 나가는 계기는 셋이다:

| 계기 | 왜 |
|---|---|
| 도달층 갱신 후 **20초 조용** | 후반에는 한 시간에 수백 층이 오른다. 층마다 쓰면 `updatedAt`이 초 단위로 갱신되어 **동점 tie-break가 뒤집힌다** |
| 앱이 뒤로 갈 때 | 모바일의 실제 종료는 `OnApplicationPause(true)`다(GameSession 머리 주석). 놓치면 마지막 구간이 다음 실행까지 안 보인다 |
| 종료 | 에디터·데스크톱 경로 |

복귀(`paused=false`)에서는 **안 보낸다** — 나갈 때와 같은 값이라 요금만 쓴다.

**"높을 때만"은 두 겹이다.** 클라가 서버 값을 읽어 비교하고(`SubmitIfHigherAsync`),
규칙이 같은 검사를 다시 한다. 클라 검사만 두면 조작 클라 앞에서 무의미하고,
규칙만 두면 정상 클라가 매번 거부당하는 쓰기를 보낸다.

에디터 실측(플레이 모드, 서버 170 보유):

```
[Leaderboard] 제출 시도 (도달층 갱신): 도달층 170     <- 시작 20초 뒤 (디바운스 동작)
[CloudScores] 제출 생략(후퇴 방지). 로컬 170 / 서버 170
[CloudScores] write 성공. scores/ojKk... maxStage = 171   <- 171로 올렸을 때
[CloudScores] 제출 생략: 로컬 171 <= 서버 171          <- 스테이지 진행 뒤 자동 제출
```

**같은 값도 거부한다.** 쓸 이유가 없고, 쓰면 `updatedAt`만 갱신되어 동점
tie-break에서 **자기 순위를 스스로 내린다**.

## L-5. 규칙 4-B — 실측으로 확인한 것

배포 후 세 가지를 실제로 쳐봤다.

| 시도 | 결과 |
|---|---|
| 비인증 읽기 (REST) | **통과** — 랭킹은 로그인 전에도 보여야 한다 |
| 비인증 쓰기 (REST, `scores/hacker`) | **403 PERMISSION_DENIED** |
| 인증된 정상 write (171 > 170) | **통과** — 너무 조여서 본인 write까지 막히지는 않았다 |
| 인증된 **후퇴** write (171 → 5, 클라 검사 우회) | **거부** — 서버 문서는 171 그대로 |

마지막 줄이 이 스텝의 핵심 검사다. 클라의 `LeaderboardPolicy`를 지나지 않는
경로(스파이크의 무조건 write)로 낮은 값을 밀어 넣었고, 서버가 막았다.

⚠️ **다만 그 거부가 클라에는 조용히 온다.** Firestore Unity SDK에서 규칙에
막힌 write의 Task는 15초 안에 실패로 떨어지지 않았고, 우리 타임아웃이
"오프라인 큐에 남았습니다"로 보고했다 — **거부와 오프라인이 클라에서
구분되지 않는다.** 지금은 무해하다(둘 다 "게임은 계속 돈다"로 끝난다).
구분이 필요해지는 것은 사용자에게 "제출 실패"를 보여줘야 할 때이고,
그건 서버 재검증이 서는 다음 스텝이다.

### 규칙이 강제하는 것 / 못 하는 것

강제: 남의 문서 금지 · 문서 ID = uid · 필드 넷만 · 타입 · 범위(0~100,000) ·
이름 길이(1~12) · `updatedAt == request.time`(클라 시계 금지) · **단조**.

못 함: **값의 진위**. 개조 클라가 "99,999층"을 주장하면 위 검사를 전부
통과한다. 도달층은 세이브에서 결정론적으로 재계산되는 값이라(52단계) 서버가
다시 시뮬레이션하면 잡히지만, 그 계산에는 Cloud Functions가 필요하고
Functions에는 Blaze가 필요하다. **다음 스텝.**

**상수가 두 곳에 있다** — 클라(`ReachSanityCap` 100,000 / `MaxLength` 12)와
규칙. 갈리면 증상이 조용하다(로컬 통과 → 서버 거부 → 아무 말 없음). 그래서
테스트가 `firestore.rules` 파일을 읽어 두 숫자가 같은지 검사한다.

## L-3 / L-4. 랭킹표

정렬은 **도달층 내림차순 + `updatedAt` 오름차순**이다. 동점 tie-break가 없으면
순서가 Firestore 내부 순서로 정해져 새로고침마다 뒤바뀌고, "내가 왜 내려갔지"가
설명 불가능해진다. 두 필드 정렬이라 **복합 인덱스가 필요했다** —
`firestore.indexes.json`에 선언하고 규칙과 함께 배포했으며, 배포 직후 조회가
`FAILED_PRECONDITION` 없이 통과했다(인덱스 실측).

**내 순위는 목록이 아니라 집계로 낸다** — `maxStage > 내 값`인 문서 수 + 1.
만 명이 있어도 문서를 내려받지 않으므로 읽기 비용이 인원에 비례하지 않는다.
동점자는 공동 순위가 된다(정확한 등수를 내려면 쿼리가 둘 필요한데, 목록 안에서는
tie-break가 이미 보이므로 목록 밖 사람에게 공동 순위로 충분하다).

**폴링이 없다.** 열 때 1회 + 새로고침 버튼. 랭킹은 초 단위로 볼 값이 아니고,
폴링은 읽기 과금을 사람 수 × 시간으로 곱한다.

상태 넷을 서로 다른 문구로 가른다 — 로딩 / 목록 / **빈**("아직 아무도 오르지
않았습니다") / **실패**("불러올 수 없습니다 - 연결을 확인하고 다시 시도하세요").
빈 상태와 실패를 같은 문구로 묶으면 "아무도 없음"이 고장으로 읽힌다.

## L-2. 닉네임 — 그리고 예상 못 한 폰트 문제

이름은 12자 상한, 제어문자 제거, 앞뒤 공백 제거. **줄바꿈 제거가 길이보다
중요하다** — 줄바꿈이 낀 이름은 랭킹표 한 줄을 두 줄로 만들고, 그 일은
**남의 화면에서** 일어난다.

변경 횟수는 안 막았다. 이름이 자산이 될 때(시즌 보상·거래) 잠글 일이고,
지금은 오타 하나를 영구히 박제하는 쪽이 더 나쁘다.

### ⚠️ 실기에서 잡은 결함: 개명이 서버에 안 닿았다

기기에서 이름을 바꿔보다 발견했다. 제출이 "도달층이 서버보다 높을 때만"이라
**같은 도달층에 머무는 동안에는 새 이름이 영영 안 올라간다.** 최전선에서 몇 시간씩
파밍하는 것이 이 게임의 정상 상태이므로, 그 사람에게 개명은 화면에서만 일어난 일이 된다.

고침은 두 줄이다:

  - `LeaderboardPolicy.ShouldSubmit`에 `nameIsStale`이 들어간다 — **같은 값일 때만**
    이름을 이유로 쓴다. 로컬이 더 낮으면 여전히 안 보낸다(후퇴 방어를 안 뚫는다)
  - `LeaderboardSubmitter`가 `PlayerProfile.Changed`를 듣는다 — 개명도 제출 계기이고,
    같은 20초 창으로 묶여 세 번 고쳐도 쓰기는 한 번이다

테스트 둘이 이것을 못 박는다(개명이 닿는가 / 개명이 후퇴 방어를 뚫지 않는가).

### ⚠️ 실기에서 잡은 결함 둘: 첫 사용자가 이름을 못 정한다

기기에서 실제로 이름을 쳐보다 막혔다. 두 가지가 겹친다:

  1. **소프트 키보드가 확인 버튼을 덮는다.** 입력 줄과 확인 버튼이 같은 높이에 있고,
     키보드는 화면 아래 절반을 가린다
  2. **키보드를 닫으면 입력이 사라진다.** 뒤로가기로 키보드를 닫으면 TMP_InputField가
     ESC를 편집 취소로 해석해 방금 친 글자를 되돌린다

즉 "치고 → 닫고 → 확인"의 가운데에서 입력이 증발한다. 그리고 이 경로는
**이름을 안 정한 사람에게 입력 줄이 자동으로 열리므로** 첫 사용자가 정확히 밟는다.

고침: 키보드의 **완료 키로도 확정**된다(`TMP_InputField.onSubmit` → `ConfirmName`).
확인 버튼은 그대로 남는다 - 키보드를 이미 닫은 사람에게는 그쪽이 자연스럽다.

### ⚠️ 그 고침을 확인하다 또 하나: 런타임 문구가 아틀라스에 없었다

수정 뒤 실기에서 `이름이 바뀌었습니다 - 잠시 □ 랭킹에 반영됩니다`가 나왔다.
문구를 고치면서 `UIStrings.txt`를 안 고쳤고, "뒤" 한 글자가 아틀라스에 없었다.

빌드 검사(`VerifyGlyphCoverage`)가 못 잡는 자리다 - 그 검사는 **씬에 적혀 있는**
라벨만 훑는데, 이 화면의 문구는 대부분 코드가 상황에 따라 넣는다. 그래서 테스트를
하나 더 뒀다: 이 판의 런타임 문구 목록을 `FontCharset.txt`와 대조한다. 문구를
고치고 charset을 안 고치면 이제 **빌드가 아니라 테스트에서** 걸린다.

### ⚠️ 이 스텝이 부순 전제: 정적 폰트 아틀라스

이 프로젝트의 폰트는 **정적**이다 — 화면에 나오는 모든 글자가
`UIStrings.txt`에 적혀 있고, 안 적힌 글자는 빌드 검사가 잡는다. 그 계약이
성립하는 이유는 **문구를 우리가 쓰기 때문**이다.

랭킹표에는 남이 지은 이름이 뜬다. 한글 음절만 11,172자이고 그중 무엇이 올지
알 수 없다 — 정적 아틀라스로는 **원리상** 덮을 수 없는 첫 자리다. 안 덮으면
증상은 "남의 이름이 빈 네모". 대응:

  - `Galmuri11 Name SDF` 한 벌만 **동적**(런타임 래스터)으로 굽는다
  - **이름 라벨만** 그 폰트를 쓴다(랭킹 줄·내 이름·입력칸). 작성한 UI는 여전히
    정적이고 검사도 그대로 돈다
  - 빌드 검사에서 동적 폰트는 제외한다 — 정적에서 "글리프 없음"은 □가 뜬다는
    뜻이지만 동적에서는 "아직 안 구웠다"는 뜻일 뿐이다

대가: 원본 TTF가 빌드에 실린다(정적 아틀라스는 안 실린다).

## UI 자리

랭킹은 **하단 탭이 아니라 상단 바**다. 여섯 탭이 이미 찼고, 나머지가 전부
"내 것을 키우는" 화면인 반면 랭킹은 "남과 견주는" 화면이라 스탯·설정과 같은
줄이 동선의 뜻에 맞는다. 2행 우측(스테이지 칩 오른쪽의 빈 자리)에 칩 하나.
새 스프라이트 0장 — 글리프 중 뜻이 맞는 것이 없어 글자로만 세웠다.

내 줄은 **새 색이 아니라 같은 판을 밝힌 것**이다(강조색 셋 규칙).

## L-7. 세이브 · 밸런스

`playerName` 한 칸. v18 → v19 마이그레이션은 **이름을 지어내지 않는다**(빈
문자열) — 기본 이름을 적어 넣으면 옛 플레이어 전원이 "이름을 직접 고른 사람"이
되어 첫 진입 안내를 띄울 근거가 사라진다.

도달층은 새 상태가 **0개**다. `maxStageReached`(v12부터 존재)를 읽기만 한다.
밸런스·시뮬레이션·전투 루프에 닿는 줄이 없다 — 기존 516개 테스트가 전부 통과하는
것이 그 증거다.

## 실기 검증 (SM-N981N)

개발 빌드를 폰에 설치하고 실행했다. logcat:

```
06:21:39 [Leaderboard] 제출 시도 (도달층 갱신): 도달층 3     <- 실행 20초 뒤 자동
06:21:40 [CloudScores] 기존 로그인 재사용. uid = A9aMgx...
06:21:40 [CloudScores] 제출 생략(후퇴 방지). 로컬 3 / 서버 3
06:22:21 [CloudScores] 랭킹 조회 성공. 2줄
06:22:21 [CloudScores] 내 순위 2위 (도달층 3)
```

화면(`docs/media/step54/leaderboard_device.png`): 상단 바의 랭킹 칩 → 랭킹 화면.
이름을 안 정한 기기라 **입력 줄이 열린 채로** 떴고(설계대로), 목록에서 **내 줄만 밝다**.
바닥에 `내 순위 2위 (3층)`.

**이름 왕복도 기기에서 닫았다**(`leaderboard_device_rename.png`):

  1. 키보드의 완료 키로 이름 확정 (확인 버튼은 키보드에 가려 못 누른다)
  2. 상태줄 `이름이 바뀌었습니다 - 잠시 뒤 랭킹에 반영됩니다` — □ 없음
  3. 20초 뒤 자동 제출 → REST로 서버 문서 확인: `name = Rang20`
  4. 앱을 껐다 켜도 이름 유지(v19 세이브) + 목록의 내 줄에 그 이름이 서버에서 돌아온다

에디터에서 바꾼 이름(`랑무사`)이 기기의 목록 1위 줄에 그대로 뜨는 것도 함께 확인됐다 —
두 기기가 같은 컬렉션을 보고 있다는 뜻이다.
