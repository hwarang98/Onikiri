## 2. 폰트를 5배로 재빌드

### 2.1 왜 3배가 문제였나

게임 아트는 PPU 32 + 기준 해상도 216×384로 그려지고, 1080 폭 기기에서 Pixel Perfect Camera가 **정확히 5배**로 확대합니다. 아트의 픽셀 하나가 화면 픽셀 5×5입니다.

폰트를 3배로 구우면 글자의 픽셀은 3×3이 됩니다. 같은 화면에 크기가 다른 픽셀이 두 종류 존재하게 되고, 픽셀 아트에서 이것은 해상도가 섞인 것처럼 보이는 가장 흔한 원인입니다.

| | 이전 | 현재 |
|---|---|---|
| Galmuri11 | 33pt (11×3) | **55pt (11×5)** |
| ThaleahFat | 48pt (16×3) | **80pt (16×5)** |
| 표시 크기 체계 | 33 / 66 | **55 / 110** |
| 아틀라스 페이지 | 1 / 1 | **1 / 1** (205자 / 44자) |

RASTER_HINTED · Point 필터 · `TextMeshPro/Bitmap` 셰이더 · 패딩 1은 그대로입니다. 페이지가 2장 이상 필요해지면 경고를 남기도록 빌더에 검사를 넣었습니다 — 페이지가 늘면 머티리얼도 늘고 표시 크기 규칙이 조용히 깨집니다.

### 2.2 검증 시트가 스스로 거짓말하지 않게

`FontProofSheet`가 크기 숫자(33/48)를 직접 갖고 있었습니다. 폰트를 다시 구우면 **시트만 옛 크기로 남아**, 정작 찾아야 할 리샘플 흐림을 시트가 스스로 만들어 보여주게 됩니다. `PixelFontSizes` 상수를 참조하도록 바꾸고 줄 높이도 폰트 크기에서 유도합니다.

### 2.3 ⚠️ 데미지 숫자 30~40%는 달성하지 못했습니다

TMP 글리프 메트릭에서 실측한 숫자 높이:

| | 글리프 높이 | 캐릭터(34px × 5 = 170px) 대비 |
|---|---|---|
| 48pt (이전) | 21px | 12.4% — 말씀하신 13%와 일치 |
| **80pt (현재)** | **35px** | **20.6%** |

5배로 키운 비율(48→80 = 1.67배)만큼만 커졌습니다. 30~40%는 51~68px인데, **허용 표시 크기는 아틀라스의 정수배뿐**이라 다음 선택지는 160(41%)입니다.

**160을 쓰면 이번 작업이 무효가 됩니다.** 폰트 픽셀이 10×10, 아트 픽셀이 5×5가 되어 픽셀 크기 불일치가 반대 방향으로 되살아납니다.

근본 원인은 배율이 아닙니다. ThaleahFat의 숫자는 **16px 엠 중 7px만** 씁니다(35 ÷ 5 = 7). 배율로는 이 비율을 바꿀 수 없습니다. 해결하려면 셋 중 하나입니다:

| 선택지 | 결과 | 비용 |
|---|---|---|
| 80 유지 | 20.6%, 픽셀 크기 일치 | 숫자가 작음 |
| 160으로 | 41%, 숫자가 큼 | 폰트 픽셀만 2배 — §2.1이 무효 |
| 다른 서체 | 엠 대비 숫자가 큰 픽셀 폰트로 교체 | 에셋 추가 필요 |

현재는 **80(픽셀 일치 우선)** 입니다. 판단이 필요합니다.

## 3. 참격 VFX에 CombatFeel 예산 적용

히트스톱과 흔들림에만 있던 예산 규칙을 참격에도 넣었습니다. 상한이 없던 마지막 효과였습니다.

| 항목 | 값 |
|---|---|
| 기본 길이 | 4프레임 ÷ 22fps = 0.182초 |
| 초당 예산 | 0.45 |
| 교차점 | 2.48회/초 |

**프레임 수를 줄이지 않고 재생 속도만 올립니다.** 픽셀 아트에서는 이펙트의 형태를 깎는 것보다 화면에 머무는 시간을 줄이는 쪽이 훨씬 덜 티가 납니다.

이것이 없으면 스윙 압축(9.2 수정)으로 공격속도가 두 자릿수까지 오르는 순간, 흰 호가 항상 두세 개 포개져 개별 타격이 보이지 않고 화면 가운데가 흰 얼룩이 됩니다.

테스트는 길이가 아니라 **동시 표시 개수**를 검사합니다. `표시 시간 × 초당 횟수 ≤ 1`이면 평균적으로 화면에 참격이 하나 이하입니다. 1.15 / 4 / 8.23 / 10 / 30회초 전부 통과.

## 6. 7단계 — 업그레이드 UI + Safe Area

### 6.1 강화 곡선

| 트랙 | 곡선 | 기본값 | 레벨당 | 기본 비용 | 비용 배수 | 상한 |
|---|---|---|---|---|---|---|
| 공격력 강화 | 지수 | 5 | ×1.12 | 10 | ×1.15 | 없음 |
| 공격속도 강화 | **선형** | 1.15/초 | +0.12 | 25 | ×1.35 | Lv.60 (8.23/초) |

**비용은 항상 지수입니다.** 방치형의 진행은 "다음 것이 늘 조금 더 멀다"로 만들어지며, 선형 비용이면 골드 획득량이 조금만 올라도 남은 레벨을 한 번에 전부 사버립니다.

**공격속도만 선형인 이유**: 지수로 두면 몇 십 레벨 만에 프레임당 여러 번 공격하는 값이 되어 축 자체가 무의미해집니다. 공격력은 요괴 체력도 티어마다 지수로 오르므로 같은 형태여야 따라갑니다.

`UpgradeTrack`은 MonoBehaviour가 아니라 직렬화 클래스입니다. 곡선 계산에 씬이나 프레임이 필요 없고, 밸런싱이 어긋나면 **폰에서 몇 시간 방치한 뒤가 아니라 테스트에서 먼저** 드러나야 하기 때문입니다.

### 6.2 스탯 적용 지점의 독점

`UpgradeSystem`이 유일한 적용 경로입니다. UI가 `PlayerCombat`을 직접 만지면 **"버튼은 눌리는데 아무것도 안 세지는"** 상태를 알아채기 어렵습니다.

레벨 1의 값도 `Start`에서 적용합니다. 그러지 않으면 시작 스탯은 프리팹에 적힌 값, 강화 후 스탯은 곡선 값이 되어 첫 구매에서 수치가 튑니다.

### 6.3 ⚠️ 9.2 수정 검증 — 동작하지만 설정값에 못 미칩니다

요괴가 죽지 않게(데미지 1e-9) 하고 히트스톱을 끈 뒤 **게임 시간 기준**으로 측정:

| 설정 | 실측 | 달성률 |
|---|---|---|
| 1.15/초 | 1.25 | 108% |
| 4.00 | 3.49 | 87% |
| **8.23** (상한 레벨) | **6.99** | **85%** |
| 20.00 | 14.23 | 71% |
| 30.00 | **20.95** | 70% |

**애니메이션 상한 2회/초는 확실히 사라졌습니다.** 설정 30에서 20.95회/초 — 옛 천장의 10배입니다.

남은 부족분은 **프레임 양자화**입니다. 공격 하나가 정수 개의 프레임을 차지하므로, 공격 주기가 프레임 길이에 가까워질수록 반올림 손실이 커집니다.

### 6.4 공격 스케줄링 수정 (검증 중 발견)

스윙이 끝나면 상태를 Idle로 바꾸기만 하고 **다음 공격은 다음 Update로 미루고 있었습니다.** 그 프레임의 switch는 이미 Idle 분기를 지나간 뒤이기 때문입니다.

공격속도가 낮을 때는 오차가 1%도 안 되지만, 초당 20회에서는 **프레임 하나가 공격 주기의 절반**입니다. 스윙이 끝난 프레임에서 바로 다음 스윙을 시도하도록 고쳤습니다.

### 6.5 Safe Area

`SafeAreaFitter`를 UI 캔버스와 밴드 사이에 넣은 `SafeArea` 루트에 붙입니다.

**월드는 보정하지 않습니다.** 배경까지 안으로 밀면 노치 옆에 검은 띠가 생기고, 그건 `CropFrame.None`으로 피하려던 바로 그 결과입니다. 잘려도 잃는 것은 하늘뿐입니다. 반대로 골드 표시나 강화 버튼이 노치에 가리면 그대로 못 쓰는 UI가 됩니다.

앵커(0~1 비율)로 적용합니다. `offsetMin/Max`를 쓰면 캔버스 스케일이 곱해져 기기마다 다른 값이 됩니다. 해상도·방향 변화를 매 프레임 감시하되 값이 같으면 아무것도 하지 않습니다 — 안드로이드에서는 앱이 살아 있는 동안에도 safeArea가 바뀝니다(멀티윈도우, 제스처 바 전환).

기존 씬 이관은 `EnsureSafeArea()`가 처리합니다. `Rebuild Main Scene`은 스테이지를 통째로 날리므로 씬을 다시 만들 수는 없고, 밴드의 앵커는 부모 기준 비율이라 **옮기기만 하면 그대로 유효합니다.**

### 6.6 배선 검증 확장

`VerifyWiring`에 세 가지를 추가했습니다. 전부 **눌러봐야만 알 수 있는 종류의 실패**입니다.

| 검사 | 놓쳤을 때 |
|---|---|
| `UpgradeSystem.combat` | 버튼은 눌리는데 스탯이 안 변함 |
| `UpgradeSystem.tracks` 비어있음 | 패널은 보이는데 아무 반응 없음 |
| `SafeAreaFitter` 존재 | 노치 기기에서만 UI가 잘림 |

## 7. 측정에서 두 번 헛짚은 기록

§6.3의 표는 **세 번째 측정**입니다. 앞의 두 번을 남깁니다. 같은 함정이 반복되기 때문입니다.

### 7.1 요괴 공급이 병목이었다

첫 측정에서 공격속도를 상한까지 올렸더니 실측이 **오히려 떨어졌습니다**(1.00 → 0.67회/초). 공격력도 함께 올려 데미지가 150이 되면서 요괴가 즉사했고, 사무라이가 다음 요괴를 기다리는 시간이 지배적이 됐습니다. 데미지를 1e-9로 낮춰 요괴가 죽지 않게 하고 다시 쟀습니다.

### 7.2 창 길이를 실제 시간으로 쟀다

두 번째 측정은 값이 뒤죽박죽이었습니다(설정 20 → 10.91, 설정 30 → 5.46).

전투는 `Time.deltaTime`으로 도는데 이 값은 **`maximumDeltaTime`(0.333초)로 잘립니다.** 에디터가 한 프레임에서 길게 멈추면 게임 시간이 실제 시간보다 뒤처지므로, 창을 `Time.unscaledTime`으로 재면 공격 횟수가 실제보다 적게 나옵니다.

거기에 제가 폴링하면서 `Thread.Sleep`으로 메인 스레드를 막아 측정 창 한가운데에서 게임을 몇 초씩 세웠습니다(로그에 `0fps`, `11fps`로 남았습니다). **5단계의 오디오 측정에서 겪은 것과 같은 함정입니다** — 프레임이 돌지 않으면 게임 상태를 잴 수 없습니다.

창을 `Time.time`으로 바꾸고 대기 없이 폴링해서 §6.3의 값을 얻었습니다.

### 8.1 테스트 패널

§7의 측정 실패를 반복하지 않기 위해 만들었습니다. 이 게임의 값 대부분이 화면만 봐서는 확인되지 않습니다 — 소리가 실제로 출력에 도달하는지, 공격속도 스탯이 실제 공격 횟수로 이어지는지, 풀이 조용히 증식하는지.

패널이 두 함정을 대신 피해줍니다:

- 공격 횟수를 **게임 시간**으로 나눕니다(§7.2). 실제 시간으로 나누면 에디터가 멈칫한 만큼 낮게 나옵니다.
- 오디오는 `isPlaying`이 아니라 **리스너 출력 파형**을 읽습니다(§5-6단계 무음 사건). 리스너가 없으면 그 자리에서 에러 박스가 뜹니다.

읽는 값: 화면 크기·안전 영역·픽셀 배율 / fps·timeScale / 공격속도 설정 대 실측 / 데미지·골드 / 요괴 생존 수 / 풀 증식 3종 / 오디오 진폭.
조작: 골드 지급, 강화 +1·+10·최대, 공격속도 직접 설정, 시간 배속, 요괴 전멸, 효과음 재생, 9:16↔9:19.5↔9:21 전환, 스크린샷, 빌더 일괄 실행.

## 11. 다음 단계

사양서 §7의 8단계입니다. 주의사항 2가 먼저 처리돼야 합니다 — **공격속도를 올려도 체감이 없는 상태**라 성장의 절반이 작동하지 않는 것과 같습니다. 스폰 간격과 동시 생존 수를 공격속도에 연동하거나, 요괴 체력을 올려 처치당 타격 수를 늘리는 방향입니다.

세이브/로드도 이 시점부터 필요합니다. 강화 레벨과 잔액을 기억하지 못하면 방치형의 진행이 성립하지 않습니다. `PlayerWallet.SetBalance`와 `UpgradeTrack.SetLevel`이 그 용도로 이미 열려 있습니다.
