# ONIKIRI 18단계 보고서 — 성장 패널 탭 재구성 (재화 기준 3탭)

작업일: 2026-08-07
테스트: EditMode **187/187 통과** (17단계와 동일 — 순수 UI 재구성이라 늘지 않음)
세이브: **v5 그대로.** 밸런스 상수 변경 없음.

17단계에서 강화를 공격/치명타/생존으로 나눴는데, 성장(스탯 포인트) 축이 그 탭들
**아래에** 남아 있었다. 그래서 어느 계열을 골라도 화면 아래쪽에는 포인트 축이
붙어 있었고, "이 탭이 골드인지 포인트인지"의 규칙이 반만 지켜졌다 — 탭 줄은
골드뿐이었지만 **화면**은 두 재화가 섞여 있었다.

이번 스텝은 최상위를 재화로 다시 갈랐다.

## 18-1 두 줄 탭을 유지했다 — 헤더 방식은 스크롤을 되돌린다

지시가 "2행이 과하다고 판단되면 강화 내부를 헤더 방식으로 바꿔도 됨 — 판단해서
보고"였다. **두 줄을 유지했다.**

근거는 높이 하나다. 성장 패널은 화면 10~45%이고 최상위 탭 줄이 한 줄(88px)을
가져가므로 페이지가 쓸 수 있는 높이는 **584px**이다.

| 방식 | 강화 페이지 높이 | 결과 |
|---|---|---|
| 계열 **서브탭** (선택) | 12 + 2줄×158 + 탭줄 88 = **416px** | 스크롤 없음 |
| 계열 **헤더** | 6줄×158 + 헤더 3개 ≈ **1236px** | 584에 절반도 안 들어감 |

헤더 방식은 탭 줄 하나(88px)를 아끼는 대신 **목록을 다시 스크롤에 넣는 거래**다.
17단계가 서브탭을 고른 이유가 정확히 스크롤을 없애는 것이었으므로, 그것을
되돌리면서 얻는 것이 88px뿐이다.

두 줄이 층위로도 읽힌다 — 위는 **무엇을 쓰는가**(재화), 아래는 **무엇을 세게
하는가**(계열)다. 같은 줄에 섞으면 둘 중 하나의 규칙이 반드시 깨진다.

### 결과: 세 탭 전부 스크롤이 없다

| 페이지 | 높이 | 584px 대비 |
|---|---|---|
| 강화 (계열 탭 + 2줄) | 416 | 여유 168 |
| **성장** (머리글 + 2줄) | **486** | 여유 98 ← 가장 김 |
| 전직 (잠금 안내) | 328 | 여유 256 |

17단계에는 골드 6줄 + 포인트 3줄이 한 목록이라 **802px**였다. 재화로 가르니
가장 긴 페이지가 486px이다. **스크롤이 구조적으로 사라졌다** — 이것이 이번
구조를 고른 진짜 이유다.

그 근거가 조용히 깨지지 않도록 `VerifyPagesFitWithoutScrolling`이 빌드에서
계산해 경고한다. 축을 하나 더 붙이면 화면에서는 "스크롤이 생겼다"로만 보여
의도인지 사고인지 구분되지 않는다.

`ScrollRect`는 남겼다. 넘쳤을 때 스크롤이 없으면 행이 **잘려서 아예 사라지고**,
그러면 "행이 없다"와 "행이 안 만들어졌다"가 화면에서 구분되지 않는다.

## 18-2 페이지를 오브젝트로 만들었다

```
GrowthPanel
├── TopTabBar          강화 / 성장 / 전직      (GrowthPanelTabs)
├── CategoryTabBar     공격 / 치명타 / 생존    (UpgradeCategoryTabs, 강화 전용)
└── Viewport / Content
    ├── EnhancePage    Upgrade0..5   ← 골드 6축
    ├── GrowthPage     남은 포인트 + Stat0/1  ← 포인트 2축
    └── AwakenPage     전직 잠금 안내
```

행이 절대 좌표로 놓이므로 **페이지 루트가 위쪽 여백을 흡수한다**. 강화 페이지만
계열 탭 줄 자리(88px)를 자기 몫으로 비우고, 그 덕에 행 쪽 배치식은 페이지와
무관하게 `TopPadding + index × 줄높이` 하나로 유지된다. 행마다 소속을 따져
오프셋을 더하는 식이면 페이지를 하나 더 만들 때마다 그 식을 고쳐야 한다.

켜고 끄는 단위이기도 하다. `GrowthPanelTabs`는 루트만 SetActive 하고, 계열 탭이
강화 페이지 **안에서** 행을 다시 가리는 것과 층이 겹치지 않는다.

선택된 탭은 세이브하지 않는다. 기본은 강화 — 골드는 방치 중에도 쌓이므로 켤
때마다 살 것이 있다. 계열 서브탭이 이미 같은 판단을 하고 있다.

### 배지

성장 탭에 남은 포인트 숫자가 붙는다. 17단계 플레이에서 24점이 쌓인 채로
방치돼 있었는데, 화면 어디에도 "쓸 것이 있다"는 신호가 없었기 때문이다.

**탭 줄에 붙는 것이 요점이다.** 성장 페이지 안에 두면 그 탭을 연 사람에게만
보이는데, 알려야 할 상대는 정확히 그 탭을 **안 여는** 사람이다.

점이 아니라 숫자다 — 남은 개수가 곧 몇 번 누를 수 있는가이고, 그것이 보상의
크기다(레벨업 버튼이 대기 레벨 수를 적는 것과 같은 규칙).

## 18-3 전직: 하단에서 탭으로

하단 탭바의 "전직 Lv.30" 버튼을 지우고 성장 패널의 최상위 탭으로 옮겼다. 같은
것이 두 곳에 서 있으면 어느 쪽이 진짜 전직 화면인지 알 수 없다.

**스킬은 하단에 남는다.** 전직은 캐릭터 성장의 한 축(골드/포인트와 같은 층위)
이지만 스킬은 별개 시스템이라, 성장 패널 탭 줄에 올리면 "이 줄은 캐릭터 성장"
이라는 규칙이 깨진다.

탭이 하나가 되면서 균등 분할 식이 남은 탭에 폭 1080을 통째로 줬다. 그러면
"잠긴 탭 하나"가 아니라 **하단 바 자체가 스킬 버튼**으로 보인다. 최소 칸 수를
둘로 잡고 가운데에 모아, 탭이 둘이던 때와 크기가 같다.

## 만들면서 잡은 것

### 한글 폭을 33.7px로 계산했다 — 배지가 "성장"을 덮었다

17단계가 남긴 "55pt Galmuri = 33.7px/자"를 그대로 썼는데, **그것은 숫자·영문의
반각 폭**이다. 한글은 두 배에 가깝다.

```
TMP 실측 (55pt)
  "성장" 110px      (한글 55px/자)
  "24"    74px      (숫자 37px/자)
  "999"  111px
```

67px로 계산한 탭 이름이 실제로는 110px이라, 배지 왼쪽 끝(198)이 글자 오른쪽
끝(213)을 **15px 덮어 "장"이 잘렸다.** 화면을 보고서야 알았다.

```
전:  폭 132, 내밈 14  ->  배지 왼쪽 198  <  글자 끝 213   겹침
후:  폭 104, 내밈 16  ->  배지 왼쪽 228  >  글자 끝 213   15px 여유
```

**이 프로젝트에서 글자 폭 어림이 틀린 것이 세 번째다**(16·17단계 상단 경험치
줄, 이번 배지). 그래서 이번에도 어림을 걷어냈다 — `VerifyBadgeClearsLabel`이
빌드에서 TMP에게 가장 긴 탭 이름의 폭을 직접 물어 배지 왼쪽 끝과 비교한다.
`VerifyExpRowFits`와 같은 계열이다.

### 페이지를 끄니 자리표시 글자가 한 프레임 보였다

성장 페이지가 **꺼진 채로 씬에 저장**되면서 그 안의 `StatPointButton`이
Start를 못 돌았다. 꺼진 오브젝트의 Start는 처음 켜진 **다음** 프레임에 도는데,
그동안 화면에는 빌더가 넣어둔 자리표시가 그대로 남는다.

```
성장 탭을 처음 누른 프레임:
  Name="Name"  Cost="Cost"  Value="Value"
```

성장 탭을 처음 누른 사람이 정확히 그 글자를 본다. `OnEnable`에서도 다시
그리도록 고쳤다 — OnEnable은 첫 활성화에서 Start보다 먼저 돌고,
`CharacterLevel`은 자기 Awake에서 Instance를 세우므로 그 시점에 이미 찾을 수
있다. 전직 안내(`LockedTab`)도 같은 처리를 했다.

11단계 유령 텍스트와 뿌리가 같다 — **행의 부모/수명이 바뀌면 그 행을 채우는
코드도 같이 옮겨야 한다.**

### 전직이 이미 "해금"돼 있었다 — 밝게 열린 빈 판

지금 세이브가 **Lv.41**이라 전직의 Lv.30 조건을 이미 넘겼다. `LockedTab`은
"해금되면 잠금 표시만 푼다"로 쓰여 있었고, 그때 화면이 이미 있을 것을
전제하고 있었다. 그 전제가 이번에 깨졌다 — 조건은 넘겼는데 전직 화면은 없다.

그대로 그리면 **밝게 열린 빈 판**이 나오고, 그것은 "해금됐다"와 "고장났다"가
구분되지 않는 화면이다.

조건과 구현은 다른 사실이므로 따로 적도록 고쳤다(`pendingLabel`). 조건을
넘겼어도 구현이 없으면 열리지 않은 것으로 그린다.

```
Lv.30 미만 :  "전직 Lv.30"   (잠김)
Lv.30 이상 :  "전직 준비 중"  (조건은 넘겼고 화면은 아직 없다)
```

이 컴포넌트가 처음부터 지켜온 "거짓말은 하지 않는다"가 그쪽이다. 전직 화면이
실제로 생기는 단계에서 `pendingLabel` 한 줄을 지우면 된다.

글리프 검사가 새 문구(`준`/`비`/`중`)를 잡아, UIStrings에 적고 아틀라스를 다시
구웠다 — 274자. 17단계에 `생존`을 잡은 것과 같은 자리다.

### 잔재를 세는 단위도 페이지로 옮겼다

행의 부모가 또 바뀌었으므로(Content → 페이지 루트) 검사도 함께 옮겼다.
Content 직속만 세던 예전 식을 그대로 뒀으면 페이지 셋만 세고 그 안의 잔재는
못 봤을 것이다. `VerifyRowIcons`도 한 겹 더 들어가지 않으면 조용히 0행을
세게 되어 있었다.

하단 탭바에도 같은 처리를 넣었다 — `Tab1`(옛 전직)은 새 루프가 이름으로
건드리지 않으므로 아무도 지우지 않고 화면에 남는다.
