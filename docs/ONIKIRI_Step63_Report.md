## 1. 기존 정책과 신규 정책 — 무엇이 달라졌는가

### 1.1 62단계까지의 정책 = "먼저 잡은 기기"

세션은 **첫 커밋 직전**에 잡혔다(`CloudSaveSync.CommitAsync`). 못 잡으면 상태가
`Busy`가 되고 **커밋만 조용히 보류**됐다.

```
기기 A 플레이 중 (세션 보유)
기기 B 실행       -> 부팅 정상 · 게임 시작 · 플레이 계속
기기 B 첫 커밋    -> Busy. 로그 한 줄. 화면에는 "다른 기기가 활성" 상태 문장
                     ...그리고 B는 계속 논다
```

**구멍은 "살아 있는 기기 둘"이 정상 상태로 취급됐다는 것이다.** 두 기기가 각자
진행을 쌓고, 나중에 하나가 세션을 얻으면 **나머지 한 벌은 충돌 화면에서
버려진다.** 재화가 복제되지는 않았다(전체 스냅샷이라 지불과 상품이 함께 빠진다,
설계 §3) - 사라지는 것은 **진행**이다.

### 1.2 63단계의 정책 = "묻고, 넘기고, 멈춘다"

| | 62단계까지 | **63단계** |
|---|---|---|
| 다른 기기가 살아 있을 때 | 커밋만 보류(`Busy`) | **확인 팝업** - 사람이 고른다 |
| 인수 조건 | 놓아줬거나 180초 만료 | + **사람이 누른 인수 요청**(20초 익음) |
| 이전 기기 | 계속 논다. 나중에 충돌 화면 | **즉시 정지 + 종료 팝업 + 타이틀** |
| 경쟁 판정 | `sessionId` 일치 | `sessionId` **+ `generation`** |
| 세션을 잡는 시점 | 첫 커밋 직전 | **부팅 게이트 - 게임 시작 전** |
| Firebase 계정 | — | **건드리지 않는다** |

핵심 문장 하나: **갈라짐을 뒤에서 처리하는 대신 앞에서 만들지 않는다.**

### 1.3 회수되는 것 / 회수되지 않는 것

| 회수한다 | 그대로 둔다 |
|----------|-------------|
| 전투 진행 · 스테이지 진행 | **Firebase 로그인** (uid 그대로) |
| 재화 변경 (골드·보석) | **로컬 세이브 파일** (복구 자료로 남는다) |
| 뽑기와 구매 | 랭킹 문서 (읽기 전용) |
| 로컬 진행 저장 | 설정·사운드 등 진행과 무관한 것 |
| 클라우드 작성권 | |

```

                 │    generation · heartbeatAt              │
                 │    takeoverSessionId · takeoverDeviceId  │
                 │    takeoverAt                            │
                 └──────────────────────────────────────────┘

  [빈 자리]  ──create(gen 1)──▶  [A 소유 gen N]
                                     │  │  ▲
              ownerRenew(heartbeat) ─┘  │  └─ ownerRenew(release) ─┐
                                        │                          │
                     takeoverRequest    │                          ▼
              (owner·heartbeat 불변) ───┤                   [A 소유·released]
                                        │                          │
                                        ▼                          │
                            [A 소유 + B의 요청]                    │
                                        │                          │
                takeoverCommit          │  takeoverCommit          │
                (요청 20초 익음)        │  (released / 180초 만료) │

**네 갈래 밖의 모양은 어느 것도 통과하지 않는다.** 특히 예전 기기(A)의

막히고, 나머지 세 갈래는 그 기기가 만족할 수 없다.

### 2.1 클라이언트 국면 (`CloudSaveTakeoverPhase`)

```
Idle ─▶ Checking ─┬─(빈 자리·놓아준 자리·만료)─▶ Acquired ─▶ [부팅 계속]
                  │
                  ├─(서버 못 봄)──────────────▶ Offline  ─▶ [부팅 계속]
                  │
                  └─(다른 기기 활성)──▶ AwaitingConfirm
                                          │        │
                                     [취소]│        │[이 기기로 이어하기]
                                          ▼        ▼
                                     Cancelled   Requesting ─▶ Waiting
                                          │                       │
                                    [게임 시작 안 함]              ├─▶ Acquired
                                                                  └─▶ TimedOut
                                                                        │
                                                                  [게임 시작 안 함]

`MayStartGame`은 `Idle` · `Acquired` · `Offline` **셋뿐**이다. `Cancelled`와
`TimedOut`에서는 부팅이 거기서 멈춘다 - EditMode가 이 목록을 소스로 못 박는다.

## 3. generation 규칙

### 3.1 왜 sessionId만으로 부족한가

`sessionId`는 "내 것인가 아닌가"까지만 말한다. 자리를 넘긴 A가 **다시 잡으려
들어오면** 같은 자리를 두고 두 기기가 번갈아 뺏는 상태가 되고, 그 순서를
`sessionId`로는 말할 수 없다.

`generation`은 **단조**다. 늦게 온 것은 언제나 늦은 것으로 판정된다 - 시계가
아니라 사슬로 순서를 정하는 것은 `revision`과 같은 이유다(기기 시각은 사용자가
바꿀 수 있다).

### 3.2 규칙

| 갈래 | generation |
|------|-----------|
| `create` (첫 세션) | **1** 고정 |
| `legacyUpgrade` (62단계 문서 → 63단계 형식) | **1** 고정 |
| `ownerRenew` (heartbeat · release) | **그대로** |
| `takeoverRequest` (요청만) | **그대로** |
| `takeoverCommit` (owner 교체) | **정확히 +1** |

`request.resource.data.generation == resource.data.generation + 1` 한 줄이
**동시 인수의 판정자**다. 둘이 같은 세대 N을 보고 둘 다 N+1을 쓰면, 먼저 든 쪽이
N+1로 올리는 순간 나중 쪽의 전제(`resource.generation == N`)가 무너진다.

### 3.3 세이브 문서에 generation을 넣지 않은 이유 — **의도적 판단**

지시서는 "클라우드 커밋은 현재 owner session과 generation이 모두 일치해야 한다"고
적었다. 그 **보장**은 성립하지만, 세이브 문서에 `generation` 필드를 **더하지는
않았다.** 근거 셋:

1. **보장은 이미 성립한다.** 커밋 규칙 `writerHoldsSession(uid)`는 세션 문서를
   `get()`으로 읽어 그 문서의 `sessionId`가 봉투의 `sessionId`와 같기를 요구한다.
   세대는 **owner가 바뀔 때만** 오르므로, "지금 owner인 세션"과 "그 세션이 owner가
   된 세대"는 **같은 하나의 사실**이다. 세대만으로 걸러지고 세션으로는 안 걸러지는
   커밋은 존재하지 않는다.
2. **필드를 더하면 봉투 형식이 바뀐다.** `hasOnlySaveFields`는 정확 일치이고
   `formatVersion == 1`이 규칙에 박혀 있다. 형식 2로 올리면 **62단계 빌드가 설치된
   기기가 그 문서를 `FutureFormatVersion`으로 차단**한다(설계상 옳은 동작이지만,
   그 기기는 그때부터 아무것도 못 받는다).
3. **Emulator가 그 보장을 직접 잰다.** "이전 기기의 세이브 커밋이 거부된다"와
   "현재 owner 세션만 커밋한다" 두 검사가 세대가 오른 뒤의 상태에서 그것을 확인한다.

지시서의 요구는 **필드가 아니라 보장**이라고 읽었다. 다르게 읽는다면 봉투 형식 2가
필요하고, 그것은 별도 스텝의 일이다.

### 3.4 옛 문서 호환 (`legacyUpgrade`)

운영에는 이미 62단계 형식의 세션 문서가 있다(네 필드). 63단계 클라이언트가 그
문서에 쓰면 `resource.data.generation`이 없어 모든 비교가 오류가 되고 **전부
거부된다** - 그 기기는 이유를 모른 채 영영 못 쓴다.

그래서 `!('generation' in resource.data)` 갈래를 하나 뒀다. 올릴 수 있는 사람은
**62단계까지의 인수 조건을 그대로 지난 기기**뿐이다(내 세션이거나, 놓아줬거나,
180초 만료). 바뀌는 것은 문서의 모양이지 **누가 가져갈 수 있는가**가 아니다.

Emulator 두 검사가 양쪽을 잰다: "세대가 없는 옛 문서를 자기 세션이 올릴 수 있다" ·
"옛 문서라도 살아 있는 남의 자리는 못 가져간다".

## 4. 인수 흐름

### 4.1 온라인 A (정상 경로)

```
B 실행
 └─ 부팅 게이트: PeekAsync -> "다른 기기가 살아 있다"
     └─ [인수 확인 팝업]  ── 사람이 "이 기기로 이어하기"
         └─ RequestTakeover      (owner·heartbeat 불변, takeoverAt = 서버 시각)
             │
             │   A: 세션 감시(5초 주기)가 owner 변경을 본다
             │      ...아직 owner는 A다. A는 요청을 보고 **자기가** 정리한다:
             │        ① 로컬 저장   ② 마지막 커밋 시도   ③ release
             │
             └─ B: 5초마다 TakeoverAsync 재시도
                 └─ A가 released -> **곧바로** 인수 (generation +1)
                     └─ Acquired
                         └─ CloudSaveCoordinator.ChooseBootSave  ★ 서버 정본 재조회
                             └─ 판정 -> 적용 -> 게임 시작

  A: 감시가 owner 교체를 본다 -> CloudSavePlayLock.Engage
      -> [종료 팝업] -> 확인 -> 타이틀 (Firebase 로그인 유지)
```

### 4.2 오프라인 / 응답 없는 A (강제 인수)

```
B: RequestTakeover  ...A는 응답이 없다
   5초마다 TakeoverAsync 재시도 -> 전부 거부 (요청이 아직 안 익음)
   20초 뒤: takeoverAt < request.time - 20s  ->  **강제 인수 성립**
   -> generation +1 -> Acquired -> 서버 정본 재조회 -> 게임 시작
```

- **B는 자기 로컬을 자동 업로드하지 않는다.** 인수 뒤 하는 일은 `ChooseBootSave`,
  즉 **서버 정본 재조회와 판정**이다. 로컬이 서버와 갈라져 있으면 그 답은 60단계
  충돌 화면이지 업로드가 아니다.
- **A가 나중에 온라인으로 돌아오면**, 감시가 `LostWrite`를 보고 **아무 서버 쓰기도
  하기 전에** 플레이를 멈춘다. A의 로컬 기록은 지우지 않는다.
- 35초(`GiveUpSeconds` = 20 + 3×5) 안에 성립하지 않으면 `TimedOut`이고, 게임은
  시작되지 않는다. 화면에는 "다시 확인"이 남는다.

### 4.3 오프라인 기기를 실시간으로 종료시킬 수는 없다 — **명시**

> **오프라인 기기에 우리가 보낼 수 있는 것은 아무것도 없다.**

푸시도, 소켓도, 폴링 응답도 그 기기에 닿지 않는다. 그래서 63단계가 보장하는 것은
"오프라인 A가 즉시 멈춘다"가 아니라 이것이다:

1. **A는 서버에 아무것도 못 쓴다.** 인수가 커밋된 순간부터 규칙이 거부한다.
2. **A는 온라인이 되는 순간(최대 5초 폴링) 멈춘다.**
3. **A의 로컬 기록은 남는다.** 그 사이 A가 쌓은 진행은 디스크에 있고, 다음 부팅의
   판정이 그것을 사람에게 보여 준다 - 조용히 덮지도, 지우지도 않는다.

이 세 줄이 이 기능의 실제 경계이고, 코드 주석(`CloudSaveTakeover` 머리)과 이
보고서에 같은 문장으로 적혀 있다.

## 5. 이전 기기 차단 시점 — `CloudSavePlayLock`

### 5.1 깃발이 팝업보다 **먼저**다

감지와 팝업 사이에는 언제나 한두 프레임이 있다. 그 사이에 10연 버튼이 눌리면 그
뽑기는 **이미 남의 기기가 정본을 쥔 계정**에서 일어난다 - 올라가지 못하는 지불이고,
다음 부팅이 그것을 버린다.

```csharp
public static void Engage(string reason)
{
    if (Locked) return;

    Locked = true;                 // ★ 깃발이 먼저
    Reason = ...;
    Time.timeScale = 0f;

    var handler = Engaged;         // 이벤트는 그 다음
    if (handler != null) handler();
}
```

EditMode가 이 순서를 잰다(`TheFlagIsUpBeforeTheEventFires`): 이벤트가 울리는 시점에
`Locked`가 이미 참이고, 여러 번 `Engage`해도 **한 번만** 울린다(폴링은 매 주기 같은
상실을 다시 본다 - "종료 팝업이 한 번만 뜬다"가 그 계약이다).

### 5.2 어디에 물려 있는가

문 하나마다 한 줄이다. 시스템마다 흩는 대신 **재화가 지나는 유일한 문**과 **진행이
지나는 유일한 문**에 건다.

| 문 | 막는 것 |
|----|---------|
| `PlayerWallet.Add` / `TrySpend` | 골드 획득·소비 (전투 보상이 여기로 온다) |
| `GemWallet.Add` / `TrySpend` | 보석 획득·소비 (뽑기·구매의 지불) |
| `GachaSystem.TryFreePullAt` | 무료 뽑기 - 지불이 없어 지갑을 안 지난다 |
| `StageProgress.RegisterKill` / `AdvanceStage` | 처치 누적과 스테이지 상승 |
| `GameSession.Save` | 로컬 진행 저장 |
| `GameSession.Update` | 자동 저장 시계 · 동기화 Tick |
| `CloudSaveSync.Tick` / `NoteSaved` / `RequestUrgent` | 클라우드 작성권 |
| `CloudSaveSession.HoldsWrite` | 작성권 판정 자체가 거짓이 된다 |

`Time.timeScale = 0`도 함께 내린다. 위 문들이 이미 값의 변화를 막지만, **화면이
계속 싸우는 것은 사람에게 거짓을 보여 주는 것**이다.

### 5.3 감지 방식 — 폴링, 5초

리스너(스냅샷 구독)가 아니라 폴링이다. 이 프로젝트의 Firestore 접근은 전부 단발
요청이고, 구독 하나를 들여오면 수명 관리가 따라온다 - 씬 재로드(충돌 화면), 계정
교체(61단계 Recover), 앱 pause/resume, 도메인 리로드. 그 넷을 새로 다루는 값이 최대
5초 지연보다 크지 않다고 봤다.

**지연이 위험하지 않은 이유가 하나 더 있다**: 이 5초 동안 이 기기가 서버에 쓸 수
있는 것은 없다. 인수가 커밋되는 순간 `writerHoldsSession`이 그 시점부터 이 기기의
커밋을 거부한다. **폴링이 늦는 것은 화면이 늦게 멈추는 것이지, 서버가 늦게 잠기는
것이 아니다.**

> 실제 감지 지연 실측은 §9에서 한다. 지금 적을 수 있는 것은 상한(5초)뿐이다.

## 6. 서버 정본 재조회 근거

부팅 순서가 이렇게 바뀌었다:

```
62단계까지:  세이브 로드 -> (서버 확인) -> 판정 -> 적용 -> 게임 -> 첫 커밋에서 세션
63단계:      세이브 로드 -> ★세션 게이트★ -> (서버 확인) -> 판정 -> 적용 -> 게임
```

순서가 뒤집히면 B는 **자기 로컬**로 판정을 마친 뒤 세션을 얻는다. 그 판정은 A가
방금 올린 최신을 못 본 것이고, 그 상태에서 올라가는 것이 곧 **"오래된 로컬의 자동
업로드"**다.

EditMode가 소스에서 이 순서를 못 박는다(`TheSessionGateRunsBeforeTheServerRefetch`):
`yield return TakeoverGate()` → `CloudSaveTakeover.MayStartGame` →
`CloudSaveCoordinator.ChooseBootSave` 순서가 아니면 실패한다.

**부팅 판정 자체는 62단계 그대로다.** `CloudSavePolicy`에 `generation`이라는 단어가
없어야 한다는 검사를 따로 뒀다 - 판정에 세대가 끼면 "세대가 올랐으니 클라우드"라는
**자동 선택**이 생기고, 그것은 이 프로젝트가 57단계부터 만들지 않기로 한 물건이다.

## 7. UI — 차단 팝업 **둘**

### 7.1 새 기기: 인수 확인 (`CloudTakeoverPanel`)

```
┌────────────────────────────────┐
│  다른 기기에서 플레이 중        │
│                                │
│   다른 기기에서 플레이 중입니다.│
│                                │
│   이 기기에서 이어서 플레이하면 │
│   기존 기기의 플레이가 종료됩니다.│
│                                │
│  [취소]      [이 기기로 이어하기]│
└────────────────────────────────┘
```

국면 하나에 화면 하나다. `AwaitingConfirm`은 위 모양, `Requesting`/`Waiting`은
버튼을 끄고 "이전 기기의 응답을 기다립니다", `Cancelled`/`TimedOut`은 "다시 확인"
하나. **국면 → 화면은 전사(全射)**여야 한다 - 열고 닫는 결정이 흩어지면 "취소했는데
팝업이 남는" 조합이 반드시 하나 생긴다.

### 7.2 이전 기기: 종료 알림 (`CloudEvictedPanel`)

```
┌────────────────────────────────┐
│  플레이 종료                    │
│                                │
│   다른 기기에서 접속했습니다.   │
│   현재 기기의 플레이를 종료합니다.│
│                                │
│            [확인]              │
└────────────────────────────────┘
```

확인 → 깃발을 내리고(`Release`) 씬 재로드 = 타이틀. 그 새 실행은 같은 uid로 세션
게이트를 처음부터 지난다.

### 7.3 적용한 것

| 요구 | 적용 |
|------|------|
| Safe Area | `PopupBuilder.Ensure(safeArea, ...)` - 기존 팝업과 같은 부모 |
| 뒤로 가기 | Input System `Keyboard.escapeKey` (§7.5) |
| 중복 클릭 방지 | `Confirm()`이 `AwaitingConfirm` 국면에서만 먹는다 + 버튼 즉시 비활성 |
| 요청 중 버튼 비활성화 | `Requesting`/`Waiting` 국면에서 두 버튼 모두 꺼진다 |

Firebase 로그아웃 · 전투 화면 상시 세션 표시.

### 7.4 ★ 이 회차가 스스로 만든 사고 둘 (검사가 잡았다)

**① 전체 `Build()`가 씬의 참조를 끊었다.**
처음에는 `HudScreensBuilder.Build()`를 통째로 배치 실행했다. `PopupBuilder.Ensure`는
기존 팝업을 **부수고 다시 만든다**(`DestroyImmediate` → `new GameObject`) - 그러자
씬의 다른 오브젝트가 들고 있던 참조가 끊겼다. `Main.unity` diff가 **17991 삽입 /
14809 삭제**로 부풀었고, `PromotionTrialPlayTests.EveryTab_ClosesEveryOtherScreen`이
잡았다: `LockedTab.otherScreens`에 `null` 한 칸("그 화면은 이 탭을 열어도 안 닫힌다").

4단계에 그 목적으로 쓰인 검사가 이번에 값을 했다. 씬을 되돌리고
`BuildSessionPanelsBatch()`를 따로 만들어 **새 팝업 둘만** 짓는다. 최종 diff는
GameObject **1617 → 1640 (+23)**, 사라진 오브젝트 0.

**② 꺼진 GameObject에서는 `Awake`가 안 돈다.**
두 팝업은 남이 열어 주지 않는다 - 자기 이벤트(국면 변화·회수)를 구독해 스스로 뜬다.
그런데 뿌리를 `SetActive(false)`로 두면 `Awake`가 영영 안 돌아 **구독이 안 걸리고
팝업이 영영 안 뜬다.** PlayMode 넷이 잡았다("묻지 않고 지나갔다").

`CloudConflictPanel`은 설정 화면이 켜 주므로 그 자리에서 `Awake`가 돌았다 - 63단계의
둘은 **켜 줄 사람이 없다**는 것이 다른 점이다. 고침: 뿌리는 켜 두고 **창과 딤**을
죽인다(`SetVisible`). 딤을 함께 죽이지 않으면 보이지 않는 전체 화면 판이 게임 위에
깔려 아무것도 눌리지 않는다.

### 7.5 ★ `UnityEngine.Input`은 이 프로젝트에서 예외를 던진다

`activeInputHandler: 1`(Input System 전용)이라 옛 `Input.GetKeyDown`은 **읽는 순간**
`InvalidOperationException`이다. 뿌리를 늘 켜 두자 `Update`가 매 프레임 돌며
PlayMode 여덟을 무너뜨렸다.

고침: `Keyboard.current.escapeKey.wasPressedThisFrame`. `Onikiri.Runtime.asmdef`에
`Unity.InputSystem` 참조 한 줄을 더했다 - 이 프로젝트에 **뒤로 가기 처리가 있는
화면은 이 둘이 처음**이라 참조도 여기서 처음 생긴다. `Keyboard.current`가 null인
경우(키보드 없는 기기)를 함께 본다.

### 9.2 두 화면과 그 순간의 로그

**인수 확인 (B).** 인트로 위에 뜨고, 뒤의 게임은 아직 시작되지 않았다.

```
06:02:46.106  B ▸ 세션 게이트 전에 인증 준비를 기다립니다 (최대 6초).
06:02:48.652  B ▸ 다른 기기가 세션을 쥐고 있습니다. 인수 확인을 띄웁니다.
```

**인계 (A가 스스로 물러난다).** 사람이 "이 기기로 이어하기"를 누른 뒤:

```
06:02:52      (B에서 탭)
06:02:57.565  A ▸ 이 기기의 플레이를 회수합니다 (Firebase 로그인은 유지됩니다).   ← 차단
06:02:57.566  A ▸ 인수 요청을 확인했습니다. 저장하고 자리를 넘깁니다.
06:02:58.016  A ▸ 인수 인계 완료 (rev 212)                                      ← 마지막 커밋
06:02:58.183  A ▸ 자리를 넘겼습니다. 이 기기의 플레이를 종료합니다.               ← release + 팝업
06:03:02.527  B ▸ 세션을 인수했습니다 (세대 9)
06:03:02.661  B ▸ 부팅 선택 (서버 정본 재조회)
```

**감지 지연 실측**: 요청이 서버에 적힌 06:02:52 → A가 본 06:02:57.565 = **약 5.5초**.
설계 상한(`SessionPollSeconds` 5초 + 왕복)과 맞는다. 탭에서 B 진입까지 총 **약 10초**이고,
그 안에 강제 대기 20초는 들어 있지 않다 - A가 스스로 넘겼기 때문이다.

**종료 알림 (A).** 확인을 누르면 타이틀로 가고 로그인은 그대로다.

```
06:04:42.469  A ▸ [CloudScores] 기존 로그인 재사용. uid = A9aMgxR5qNSmuR9tmobfs4PT8St1
06:04:42.603  A ▸ 다른 기기가 세션을 쥐고 있습니다. 인수 확인을 띄웁니다.
```

이 두 줄이 항목 8·20·21을 한꺼번에 보여 준다: **uid가 같고**(강제 로그아웃 없음),
재실행한 A는 B가 활성이므로 **다시 묻기만** 한다.

**회수 뒤 조작 (A).** 팝업이 뜬 상태에서 `보스 도전` · `상점` · `캐릭터`를 차례로 눌렀다.
골드·보석·레벨·지역·강화 수치가 **한 자리도 바뀌지 않았고** 어떤 화면도 열리지 않았다.

**오프라인 강제 인수.** B의 Wi-Fi·데이터를 끄고 A에서 승인:

```
06:07:24      (A에서 탭, B는 오프라인)
06:07:43.159  A ▸ 세션을 인수했습니다 (세대 10)                    ← 약 19초
06:07:43.348  A ▸ 부팅 선택: 클라우드 채택 (rev 213, 43층 · Lv.61)  ← **자기 로컬을 안 올린다**
06:07:43.356  A ▸ 서버 사슬 확정: rev 213 (로컬 저장 완료 후)
```

지시서 요구 그대로다: 강제 인수한 기기는 **자기 로컬을 자동 업로드하지 않고**
서버 정본을 다시 조회해 판정을 지난다.

### 9.3 ★ 실기가 잡은 결함 **아홉 건**

자동 검사 셋이 전부 초록인 상태에서 실기를 시작했고, **첫 부팅에서 셋이 즉시
드러났다.** 나머지 다섯은 시나리오를 밀면서 하나씩 나왔다. 여덟 건 전부
고치고 검사를 붙였다(EditMode +10 · Emulator +2).

| # | 증상 | 원인 | 고침 |
|---|------|------|------|
| ① | 부팅 3초 만에 **자기 자신에게 회수**당했다 ("세대 0 → 0") | `CloudSaveSessionStatus.Acquired`가 열거형의 **0**이라 `LastStatus` 기본값이 그것이었다 - 한 번도 안 잡은 기기가 `HoldsWrite == true`로 시작 | 시작값을 `Offline`로 명시 + `HoldsWrite`가 **세대**를 함께 본다 |
| ② | 같은 증상의 나머지 절반 | `LostWrite`가 owner 비교를 **세대 검사보다 먼저** 했다 - 서버에 남은 이전 실행의 문서를 상실로 읽었다 | "잡은 적 없으면 잃을 것도 없다"를 맨 앞으로 |
| ③ | **다른 기기가 켜져 있어도 아무것도 묻지 않았다** | 세션 게이트가 `ChooseBootSave`보다 앞에 서면서 **로그인보다 빨라졌다** - uid 없이 들어와 곧바로 `Offline`. 62.1 P0-1과 같은 모양 | `CloudSaveCoordinator.AwaitIdentity()`를 꺼내 게이트 앞에 세우고, `AwaitedIdentity`로 **예산은 하나** 유지 |
| ④ | 사람이 화면 앞에 있는데 **180초 뒤 자리가 만료**됐다. 다른 기기가 묻지도 않고 가져갔다 | heartbeat가 **커밋 경로에만** 있었다 - `Conflict` 상태의 기기는 영영 커밋하지 않으므로 시계를 못 감는다. "살아 있다"가 "최근에 썼다"와 같은 뜻이었다 | 감시가 폴링하는 김에 **60초마다 시계를 감는다**(`HeartbeatSeconds`) |
| ⑤ | **로그에는 팝업이 떴는데 화면에는 없었다** (두 번) | 인트로가 **UI Canvas 직속**의 마지막 형제다. 팝업은 SafeArea 안에 살아서, SafeArea 안에서 아무리 형제 순서를 올려도 그 아래다 | 팝업 뿌리에 **정렬을 덮어쓰는 Canvas**(+ `GraphicRaycaster`). Safe Area 여백은 그대로 |
| ⑥ | 모든 인수가 **20초 강제 대기**를 거쳤다. A의 마지막 몇 초가 서버에 못 올라갔다 | 온라인 A가 요청을 보고 **스스로 물러나는 경로(§4.1)를 구현하지 않았다.** 강제 갈래가 있어서 "동작하는 것처럼" 보였다 | 감시가 요청을 보면 **차단 → 저장 → 마지막 커밋 → release → 팝업**. 잠금을 `Locked`/`Sealing` 둘로 나눠 마지막 한 벌만 통과 |
| ⑦ | A가 **자기가 방금 놓친 자리를 되찾지 못했다.** 작성권 없이 돌았다 | "같은 기기의 이전 실행은 묻지 않는다"를 **클라이언트에만** 넣고 규칙에 안 넣었다 - 서버가 그 쓰기를 거부했다 | `firestore.rules`의 `takeoverCommit`에 같은 갈래 + Emulator 2개 + 상수 대조 검사 |
| ⑧ | 오프라인에서 돌아온 기기가 **회수되지 않고 계속 놀았다** | 세션 호출이 한 번 `Busy`를 받으면 `HoldsWrite`가 false가 되고, 감시가 그 값을 보고 **영영 멈췄다** | 감시가 `HasHeldSeat`("가진 적이 있는가")를 본다 |
| ⑨ | 회수 뒤 **확인 → 타이틀**로 나가면 새 실행이 **곧바로 다시 회수**됐다 (종료 팝업과 인수 확인이 겹쳐 뜬다) | 씬을 다시 열어도 **정적 상태는 살아남는다** - `currentId`·`MyGeneration`이 방금 자리를 잃은 실행의 것 그대로라, 첫 폴링이 또 상실을 봤다. 그 뒤에는 인수에 성공해도 저장이 잠긴 채였다 | `CloudSaveSession.BeginNewRun()` - 타이틀로 나갈 때 **다음 실행의 몫을 비운다** |

> **⑦이 이 목록에서 가장 값비싼 교훈이다.** 규칙↔코드 상수 대조는 58단계부터
> 이 프로젝트의 규칙이고, 이 파일의 주석에도 "갈리면 클라가 가능하다고 판단한
> 순간 서버가 거부하고, 그 기기는 이유를 모른 채 못 들어간다"고 적어 뒀다.
> **그 주석을 쓴 회차에 그 실수를 했다.** 검사가 상수만 대조하고 **갈래**는
> 대조하지 않았기 때문이다 - 지금은 그 갈래도 대조한다.

> **⑨는 최종 확인 회차가 잡았다.** ①~⑧을 고치고 "이제 처음부터 한 번 더"를
> 돌리지 않았으면 그대로 남았을 것이다 - 고친 뒤의 전체 재훑기가 값을 했다.

> **⑥은 검사로 못 잡는 종류다.** 강제 인수라는 대체 경로가 있어서 자동 검사도
> 실기 로그도 "성공"으로 읽혔다. 드러난 것은 **시간을 재 봤을 때**였다 -
> 매번 정확히 20초가 걸리는 것이 이상해서 들여다봤다.

> "세 번 반복된 것은 잊지 말자로 풀 문제가 아니다"라고 적어 둔 **네 번째**다.
> `UIStrings.txt`에 63단계 문장 열일곱 줄을 넣고 아틀라스를 463자로 다시 구웠다
> (GUID 유지). **코드 안 문자열은 그 파일에 손으로 옮겨야 한다**는 것이 여전한 조건이다.

### 10.1 이 스텝이 새로 만든 것

1. **`firestore.rules`를 운영에 배포했다** (2026-08-28, `firebase deploy --only
   firestore:rules`). 바뀐 것은 `playerSaveSessions` 규칙뿐이고 scores·playerSaves·
   백업은 한 줄도 안 건드렸다. `legacyUpgrade` 갈래 덕에 **62단계 빌드도 계속 돈다**
   (그 기기가 지나던 인수 조건 그대로 문서를 새 형식으로 올린다).

   > ⚠️ MCP `firebase_deploy`는 `{"status":"success"}`를 돌려줬지만 **실제로는
   > 릴리스되지 않았다** - 배포 뒤 `firebase_get_security_rules`가 여전히 62단계
   > 규칙을 돌려줬다. CLI(`npx firebase-tools deploy`)로 다시 올려 릴리스를 확인했다.
   > **배포 뒤에는 반드시 서버 규칙을 되읽어 대조한다.**
2. **강제 인수 대기 20초는 실기에서 안 재봤다.** 온라인 A가 요청을 보고 정리하는 데
   걸리는 시간(감시 폴링 5초 + 저장 + 커밋 + release)이 20초를 넘으면 **살아 있는 A를
   강제로 끊는다.** 설계상 A는 첫 폴링(≤5초)에서 정리를 시작하므로 여유가 있지만,
   그 여유가 실제로 얼마인지는 §9의 5번이 답한다.
3. **폴링 5초 = 화면이 멈추기까지의 상한.** 서버는 즉시 잠기지만(§5.3), 그 5초 동안
   A의 화면은 계속 돈다. 재화·진행은 이미 막힌 상태가 아니라 **아직 안 막힌** 상태다.
4. **`Onikiri.Runtime.asmdef`에 `Unity.InputSystem` 참조가 생겼다.** 런타임 어셈블리
   전체의 의존이 하나 늘었다 - 빌드 크기·컴파일 시간에 미치는 영향은 재보지 않았다.
5. **`Main.unity`가 바뀌었다.** 팝업 둘이 들어가 GameObject 1617 → 1638(+21)이고
   사라진 것은 없다. 전체 `Build()`를 돌리면 안 된다(§7.4 ①) - 새 팝업만 짓는
   `HudScreensBuilder.BuildSessionPanelsBatch()`가 그 자리다.
6. **폰트 아틀라스가 다시 구워졌다** (§10.0). 463자 1페이지, GUID 유지.
7. **실기 열두 항목은 최종 빌드에서 전부 닫혔다** (§9.2.1). 남은 것은 손으로 만들 수
   없는 둘뿐이고(동시 인수 · 인계 중 저장 실패) 그 둘은 Emulator와 EditMode가 잰다.

### 10.2 62단계 계열에서 이어지는 것 (변동 없음)

1. **production 서명 인증서 없음** — 등록된 SHA-256은 이 기계의 debug keystore 것
2. **`PLAY_RECOGNIZED` 요구 해제 상태** — 출시 전 되돌려야 한다
3. **Editor Debug Provider 미등록** — 콘솔에서 디버그 토큰 발급 필요
4. **Firestore App Check enforcement 미활성** — 이번 단계에서도 켜지 않았다

### 10.3 이 기능이 **보장하지 않는 것**

- **오프라인 기기를 실시간으로 멈출 수 없다**(§4.3). 보장하는 것은 "서버에 못 쓴다" ·
  "온라인이 되면 멈춘다" · "로컬 기록은 남는다" 셋이다.
- **세이브 문서에 `generation` 필드는 없다**(§3.3). 보장은 `writerHoldsSession`이
  들고 있고, 그 근거를 §3.3에 적었다. 필드가 필요하다는 판단이라면 봉투 형식 2가
  필요하고 그것은 별도 스텝이다.
- **`gems`는 여전히 클라이언트 JSON 값이다.** 단일 활성 기기는 유료 재화 원장이
  아니다 - IAP 전에 영수증 서버 검증·서버 원장이 별도로 필요하다.
