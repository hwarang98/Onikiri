## 17-1 달리기 + 배경 스크롤

### 뒤집은 것

16단계까지 사무라이는 제자리에 서 있고 요괴가 걸어왔다. 플레이어가 하는 일은
기다리는 것이었다. 이제 반대다 — 사무라이는 화면 X를 지키되 달리고, 배경이
흘러 전진을 만든다.

```
사거리가 비었다  ->  달린다 (스크롤 3.2 u/s, RUN 클립)
벨 것이 들어왔다  ->  멈추고 벤다 (스크롤 0)
베고 나면        ->  다시 달린다
```

판단은 `StageAdvance` 한 곳에만 있다. 배경 스크롤과 달리기 클립은 **같은 사실의
앞뒤**라서, 각자 판단하게 두면 "배경은 흐르는데 사무라이는 서 있는" 조합이
생긴다 — 버그로 안 보이고 그냥 어색해 보이는, 원인을 찾기 가장 어려운 종류다.

### 좌우 이음새 — 실측

지시하신 확인 항목이다. 배경이 16:9를 세로로 크롭한 것이라 좌우가 맞물리는지
알 수 없었다.

```
레이어              크기      좌우 끝 열 차이
Sky/Clouds/Fuji     353x180   0.000
Mountain_*          353x180   0.000 ~ 0.044
Trees/BackgroundTrees 353x180 0.042 ~ 0.046
Ground/Gras         353x180   0.000 ~ 0.017
```

**11개 전부 맞물린다.** 353×180 동일 규격이라 두 장 교대로 충분하다.

### 패럴랙스

| 레이어 | 처음 | **최종** |
|---|---|---|
| Sky | 0 | 0 (무한히 멀다) |
| Clouds | 0.04 | **0.15** |
| Fuji | 0.06 | **0.20** |
| **탑(Shrine)** | 0.09 | **0.22** |
| Mountain_Back/Middle/Front | 0.12 / 0.20 / 0.30 | **0.34 / 0.48 / 0.62** |
| BackgroundTrees / Trees | 0.45 / 0.62 | **0.76 / 0.88** |
| Ground / Gras | 1.00 | **1.00** (기준) |

지면이 1.00인 것은 사무라이의 발이 닿는 면이기 때문이다. 이 속도와 달리기
클립이 맞아야 발이 안 미끄러진다.

#### 처음 배분이 느리게 보인 이유 — 넓이로 가중해야 한다

첫 배분(25:1)으로 돌려보고 나온 소감은 **"이동속도가 왜 이리 느리냐"**였다.
지면은 3.2 u/s로 화면폭(6.75 units)을 2.1초에 지난다 — 느리지 않다. 문제는
**그 지면이 화면의 13.9%밖에 안 칠한다**는 것이었다. 나머지를 칠하는 층이 느렸다:

| 레이어 | 화면 칠하는 면적 | 속도 | 화면폭 통과 |
|---|---|---|---|
| Clouds | 49.6% | 0.13 u/s | 52초 |
| Trees | 45.0% | 1.98 u/s | 3.4초 |
| Ground | 13.9% | 3.20 u/s | 2.1초 |

면적으로 가중한 평균이 **0.94 u/s = 체감 7.2초**. 눈이 읽는 속도는 기준 속도가
아니라 화면 대부분을 칠하는 층의 속도다.

그래서 **기준 속도는 건드리지 않고 패럴랙스 범위만 25:1 -> 6.7:1로 압축했다.**
3.2 u/s는 RUN 클립의 발 주기에 맞춰둔 값이라 올리면 발이 미끄러진다 — 느린 쪽을
올리는 것이 맞는 손잡이였다.

```
가중 평균 0.94 -> 1.60 u/s,  체감 7.2초 -> 4.2초 (화면폭당)
탑 사본 간격 x4 -> x8 로 늘려 재등장 주기는 125초로 유지
```

`Time.deltaTime`(스케일 타임)을 쓴다. 히트스톱이 배경도 함께 얼린다 — 벚꽃
파티클과 같은 규칙이고, 타격 순간 배경만 흐르면 정지가 "게임이 멈췄다"가 아니라
"배경만 고장났다"로 읽힌다.

## 랜드마크 분리 (보강 지시)

배경이 흐르기 시작하자 두 가지가 드러났다.

- **반복 스크롤에 섞인 랜드마크는 계속 다시 나온다** — 탑이 근경 속도(0.80)로
  11 units마다 지나갔다
- **스크롤에서 빠진 랜드마크는 화면에 붙박여 따라온다** — 토리이가 그랬다

둘 다 "왜 토리이가 계속 나오지?"가 된다.

### 탑 = 먼 패럴랙스 느린 드리프트

```
상대속도 0.80 -> 0.09,  사본 간격 x1 -> x4 (44.1 units)
=> 같은 탑 재등장 153초
```

(패럴랙스 압축 후 0.22 / 간격 x8 = 88.2 units => 재등장 125초. 속도를 올린 만큼
간격을 벌려 주기를 지켰다.)

탑 스프라이트는 왼쪽 일부만 그림이고 나머지가 투명이라, 사본을 넓게 벌려도
배경에 구멍이 나지 않는다. 벌린 만큼 반복 주기가 길어진다.

### 토리이 = 보스 관문 (`BossGate`)

배경이 아니라 **사건**이 됐다. 파밍 중에는 화면에 없고, 보스에게 달려가는 동안
딱 한 번 나타나 그 밑을 지나면 보스의 영역이다.

```
관문 x=4.53 통과=False  보스 x=17.30   <- 관문이 먼저
관문 x=-5.02 통과=True  보스 x= 5.36   <- 통과 후 보스 접근
```

지역 피날레는 **붉은 토리이**다. 처음에 ×2 배율로 만들었다가 되돌렸다 — 세로로도
두 배가 되면서 관문 상단이 화면 밖으로 잘리고 보스 체력 바·타이머와 겹쳤다.
전투 밴드가 화면 45~90%로 고정이라 세로로 키울 여유가 없다. **크기가 아니라
색**으로 무게를 준다.

## 17-2 지역 구조

상단이 `지역 4 · 7/10  처치 3/10` 을 항상 보여준다.

**세이브에 지역 필드를 만들지 않았다.** 스테이지에서 유도한다.

```csharp
RegionOf(stage)      = (stage - 1) / 10 + 1
StageInRegion(stage) = (stage - 1) % 10 + 1
```

필드를 따로 두면 진행(stage)과 표시(region)가 어긋날 수 있는 상태가 생기고, 그
둘이 갈리면 어느 쪽이 맞는지 판단할 근거가 없다. 유도하면 갈릴 수 없다.
**세이브 v5 그대로.**

10스테이지를 넘으면 금색 "지역 클리어" 배너가 뜨고 상단이 곧바로
`지역 2 · 1/10` 이 된다.

## 17-3 보스 달려가 처치

`Approaching` 페이즈가 생겼다. 보스를 화면 밖에 세우고, **사거리에 닿을 때까지
시계가 안 돈다**(`State.Engaged` 감지). 도달 실패 대비 안전장치 15초.

모든 보스가 달려가기를 거친다. 13단계에서는 피날레만 워크인을 썼는데, 그때는
워크인이 제한 시간을 갉아먹었기 때문에 아껴 쓴 것이다. 타이머 밖이 된 지금은
아낄 이유가 없고 오히려 매 스테이지 리듬이 된다.

접근 중에도 보스 체력 바가 뜨고 시계는 "30초"에 멈춰 있다. 0으로 두면 도착하는
순간 0에서 30으로 튀어 시계가 고장 난 것처럼 보인다.

## 17-4 강화 카테고리 — 라벨이 아니라 서브탭

지시가 "서브탭 or 라벨 섹션 — 판단해서 보고"였다. **서브탭을 골랐다.**

라벨로 구간을 나누면 **스크롤이 그대로 남는다.** 성장 패널 높이는 672px이고 한
줄이 158px이라 네 줄이 들어간다. 여덟 줄은 어떻게 나눠도 화면 밖으로 넘친다.

계열당 두 축이면 탭 하나에 두 줄이고 **스크롤 없이 전부 보인다.** 목록을 나누는
진짜 이유가 이름을 붙이는 것이 아니라 한눈에 들어오게 하는 것이기 때문이다.

```
공격    공격력 강화 / 공격속도 강화
치명타  치명타 확률 / 치명타 피해
생존    체력 강화   / 체력 회복
```

스탯 포인트는 탭에 안 섞었다. 골드가 아니라 포인트로 사는 다른 재화라, 같은 탭
줄에 넣으면 "이 탭들은 전부 골드"라는 규칙이 깨진다. 성장 구역은 탭 아래에 그대로
남아 항상 보인다.

선택된 탭은 세이브하지 않는다. 앱을 껐다 켜면 공격으로 돌아가는데, 그것이 잘못된
상태가 아니라 가장 자주 보는 화면이다.

## 17-5 공속 MAX "완성"

```
전:  MAX      (회색)
후:  MASTER   (금색 글자 + 금빛 행 배경)
```

공격속도는 아트가 정한 상한이라(7프레임/14fps = 3.88회/초) 앞으로도 안 열린다.
죽은 회색으로 두면 화면에 "고장난 버튼"이 영구히 남고, 플레이어는 자기가 뭘
잘못했는지 모른 채 그 줄을 계속 본다.

같은 사실을 **완성**으로 표현하면 읽는 방향이 뒤집힌다. 더 못 사는 것이 아니라
다 산 것이고, 금색은 이 게임에서 이미 보상의 색이다.

지시대로 **캡을 올리려고 아트에 투자하지 않았다** — 프레임을 늘리면 곧 또 막힌다.

### 완성 축을 아래로 접는 것은 하지 않았다

계열당 두 줄뿐이라 정렬을 바꿔도 얻는 것이 거의 없고, 런타임에 스크롤 행 순서를
바꾸는 코드가 새로 필요하다. 금색 표현만으로 "이 줄은 끝났다"가 충분히 읽힌다고
판단했다.

## 17-6 밸런스 재확인

두 변경이 여유를 밀어올렸다.

| 변경 | 효과 |
|---|---|
| 타이머를 도달 시점부터 | 유효시간 24.7 -> **30초** = 여유 x1.215 |
| 클리어 골드 추가 | 골드 유입 증가 |

반영 직후 `일반 2.18~4.12 / 챕터 2.13~2.41 / 피날레 1.84~2.20` — 전 등급 천장 돌파.

### 재조정

| 상수 | 전 | 후 | 근거 |
|---|---|---|---|
| `BossHealthMultiplierBase` | 8 | **10.8** | 타이머 변경이 전 구간 **균일** |
| `BossHealthRampFinal` | 1.110 | 유지 | 램프는 후반 편향이라 안 맞다 |
| `ClearGoldMultiplier` | — | **x2** | 신규 |
| `FinaleClearGoldMultiplier` | (x6 시도) | **x3** | x6이면 st11이 3.39 — 16단계 사고 재발 |

램프를 안 쓴 것이 이번 조정의 핵심이다. 16단계에서는 증폭이 후반으로 갈수록
커져 램프가 맞는 손잡이였지만, 타이머 변경은 1스테이지든 30스테이지든 똑같이
×1.215다.

### 최종

| 구간 | 일반 (1.5~3.0) | 챕터 (1.3~2.0) | 피날레 (1.15~1.7) | 생존 |
|---|---|---|---|---|
| **1~20** | 1.61 ~ 2.98 | 1.57 ~ 1.64 | 1.21 ~ 1.61 | ≥ 1.16 |
| **21~30** | 2.19 ~ 2.79 | 1.95 | 1.50 | ≥ 1.18 |

무강화 게이트: **화력 2 / 체력 5스테이지** 유지.

### 얇은 경계 — 넓히지 못했다

| | 16단계 | 17단계 |
|---|---|---|
| st11 천장까지 | 0.046 | **0.023** |
| st20 피날레 바닥까지 | 0.055 | **0.065** |

st11은 오히려 절반으로 얇아졌다. 일반 밴드 폭(2.0배) 안에 실제 분포(1.85배)가
거의 꽉 차 있어 지금 구조로는 여유를 만들 수 없다. 원인은 **보스 처치 골드가
만드는 스파이크**(보스 직후 스테이지만 여유가 높다)이고, 줄이려면
`BossGoldMultiplier`(12)를 손대야 하는데 그것은 "보스가 도전할 가치가 있는가"의
근거라 이번 범위를 넘는다.

## 만들면서 잡은 것

### 시뮬레이션이 워크인을 모든 보스에서 빼고 있었다

중간 보고 중에 발견했다. 16단계까지 계산은 워크인 5.3초를 **모든 보스**에서
뺐는데, 실제로 걸어 들어오는 것은 **피날레뿐**이었다.

```csharp
float spawnX = walkIn ? RightEdgeX() + offscreenMargin : frontLineX;
// walkIn = UsesFullIntro  (= 지역 피날레만 true)
```

일반·챕터 보스는 큐 앞줄에 즉시 스폰돼 처음부터 때릴 수 있었다. **옛 밸런스는
그 둘을 실제보다 어렵게 모델링했고, 게임은 계산보다 쉬웠다.** 이번 재조정으로
모델과 게임이 처음으로 일치한다.

### 상단 경험치 줄이 또 잘렸다 — 어림한 글자 폭이 20% 틀렸다

패럴랙스를 확인하려고 찍은 스크린샷에서 `248.4K/496.…` 로 잘려 있었다.
16단계에서 한 번 고친 자리인데 다시 났고, **두 번 다 원인이 같았다** —
글자 폭을 28px/자로 어림했다. 55pt Galmuri의 실측은 **33.7px**이다.

재보니 잘린 것 하나가 아니었다:

| 라벨 | 최악 문자열 | 필요 (실측) | 상자 | |
|---|---|---|---|---|
| LevelLabel | `레벨 999` | 236 | 200 | **넘침 36** (3자리 레벨에 닿는 순간 터질 예정) |
| LevelUpButton | `레벨업 99` | 254 | 250 | **넘침 4** |
| ExpLabel | `999.9aa/999.9aa` | 488 | 424 | **넘침 64** |

레벨 라벨 쪽은 아직 아무도 못 본 상태였다 — 현재 레벨이 두 자리라서.

**넷을 다 넣으면 1080이 모자란다.** 그래서 가장 값싼 픽셀을 뺐다 — 경험치
숫자의 소수 첫째 자리다. 두 숫자에 걸쳐 네 글자(108px)를 먹는데, 미세한 진행은
채움 막대가 이미 연속으로 보여주고 있다. 숫자가 맡은 몫은 자릿수, 즉 크기다.

```
"248.4K/496.7K" (434px)  ->  "258K/497K" (324px)
최악도 "999aa/999aa" 378px 로 내려간다
```

남은 폭을 실측 기준으로 다시 나눴다:

```
여백48 | 레벨240 | 8 | 별48 | 10 | 막대402 | 16 | 버튼260 | 여백48  = 1080
        (236 OK)              (라벨 382 >= 378)      (254 OK)
```

여유가 4~6px뿐이다. 이는 **55pt 네 요소가 1080의 한계**라는 뜻이고, 그래서
다음 사람이 이 줄에 무언가를 더 넣으면 반드시 다시 터진다. 어림이 두 번
틀렸으므로 어림을 걷어냈다 — `VerifyExpRowFits`가 빌드에서 TMP에게 직접
최악 문자열의 폭을 물어 상자와 비교하고, 넘치면 빌드가 실패한다. 다음에는
스크린샷이 아니라 에러로 알게 된다. 행 아이콘 검사·글리프 검사와 같은 계열이다.

### 요괴가 지면 위를 미끄러졌다

지면은 3.2 u/s로 흐르는데 요괴는 자기 걸음 1.0으로만 움직여서, 지면 대비
**오른쪽으로 2.2 u/s** 밀렸다 — 발이 땅에 안 붙는 그림이다.

요괴도 세계의 일부다. 지면 속도를 실어주고 그 위에서 자기 걸음을 걷게 고쳤다.
접근이 빨라지는 것은 의도대로다(달려가 만나는 것이므로). 공급 속도는
`SpawnPacing`이 정하지 이동 시간이 정하지 않아 밸런스 모델은 그대로다.

### 보스가 관문을 앞질렀다

스폰 거리가 4.5 units뿐인데 스크롤을 실어주며 접근 속도가 4.05 u/s가 되어
**1.1초 만에 도착**했다. 시뮬레이션이 가정한 5.3초와도 어긋났다.

거리를 **시간에서 유도**하도록 고쳤다.

```
보스 스폰 거리 = (보스 걸음 + 스크롤) x 5.3초
관문 위치      = 스크롤 x 5.3초 x 0.45
```

고정 거리로 두면 전진 속도를 바꾸는 순간 순서가 또 뒤집힌다.

### 씬에 직렬화된 값이 코드 기본값을 이긴다

관문 배율을 2→1로 내렸는데 씬의 옛 값이 남아 안 먹었다. 빌더가 명시적으로 적도록
옮겼다 — 강화 곡선을 빌더가 적는 것과 같은 이유다.

### 빌드 순서 함정

`Build Battle Stage`는 씬을 저장하지 않는데 `Build Combat Content`는 디스크에서
다시 연다. 그래서 스테이지 작업이 통째로 날아가고
`BattleStageLayout is missing`이 났다.

```
Rebuild Main Scene -> Build Battle Stage -> 저장 -> Build Combat Content
```

### 글리프 검사가 새 탭 이름을 잡았다

12-1에서 만든 검사가 `생존`이 안 구워진 것을 빌드 시점에 잡았다. 9단계(보스
이름)·11단계(사망 문구)에서 화면을 보고서야 알았던 것을 이번엔 빌드가 먼저 말했다.
