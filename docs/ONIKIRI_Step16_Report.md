# ONIKIRI 16단계 보고서 — 밸런스 정리

작업일: 2026-08-06
테스트: EditMode **187/187 통과** (15단계 181 → 6개 추가)

14~15단계 라이브 스크린샷에서 쌓인 밸런스 문제를 한 스텝으로 정리한다.
전부 "직접 돌려봐야 보이는" 종류였고, 실제로 시뮬레이션만으로는 잡히지 않았다.

---

## 16-1 체력 회복 상한

### 증상과 원인

Lv.54에서 **156.2%/s** — 초당 최대 체력의 1.5배를 회복하면 어떤 피해도 다음
프레임에 지워지고, 11단계에서 만든 체력 게이트가 통째로 무력화된다.

원인은 회복이 최대 체력 **비율**의 곱연산인데 상한이 없다는 것이다. 비율로 바꾼
것 자체는 옳았지만(11단계), **100%를 넘을 수 있다는 사실**을 그때 보지 못했다.
절대량이던 시절에는 체력이 함께 자라 저절로 억제됐는데 비율이 되며 그 억제가
사라졌다.

### 캡 값: 30%/s

| 근거 | 값 |
|---|---|
| 30초 보스전 동안 회복하는 양 | 최대 체력의 **9배** |
| 유효체력 환산 | 최대체력 × (1 + 0.3×30) = **10배** |
| 상한 도달 레벨 | **Lv.37** |

20%/s(7배)면 회복 축이 상한에 너무 일찍 닿아 죽고, 40%/s(13배)면 체력 게이트가
다시 헐거워진다. 시뮬레이션에서 생존 여유가 밴드에 남는 구간으로 잡았다.

```
Lv. 1  무상한    1.0 %/s  ->  캡  1.0 %/s
Lv.30  무상한   15.9 %/s  ->  캡 15.9 %/s
Lv.37  무상한   30.9 %/s  ->  캡 30.0 %/s  <- 잘림
Lv.54  무상한  156.2 %/s  ->  캡 30.0 %/s
Lv.80  무상한 1862.2 %/s  ->  캡 30.0 %/s
```

### 처리 방식

공격속도(9단계)와 동일하다. `MaxLevel`은 "더 팔지 않는다", `ValueCeiling`은
"더 세지지 않는다" — 저장 레벨은 유지되고 효과만 막히며, 상한이 오르면 잠든
레벨이 복원된다. UI에는 **MAX**가 뜬다.

`PerSecondAt`이 캡을 적용하므로 전투와 시뮬레이션이 **같은 입구**를 쓴다.

### 캡 후 생존 축이 다시 의미 있는가

시뮬레이션에서 회복은 Lv.1 → Lv.28(13.1%/s, 30스테이지)까지 정상적으로 팔리고,
생존 여유는 전 구간 **1.16 이상**을 유지한다. 상한에 닿는 것은 실제로는
30스테이지 이후다 — 그 앞에서는 상한이 존재하는 줄도 모른다.

## 16-2 EXP 리듬

### 레벨업 = claim-all 로 변경

12단계에서 "버튼 한 번에 한 레벨"로 정했고 근거는 *"한꺼번에 올리면 스탯
포인트가 뭉텅이로 들어와 안 쓰는 상태가 된다"*였다. **그 판단이 틀렸다.**

15단계 화면에서 레벨 2에 레벨업 16개가 밀려 있었다. 그 상태에서 한 번에
하나씩이면 플레이어가 하는 일은 "찍을 곳을 고르는 것"이 아니라 같은 버튼을
열여섯 번 누르는 것이다.

포인트가 뭉텅이로 들어오는 문제는 여전히 있지만 그것은 **레벨업 버튼이 아니라
증폭 축이 풀 문제**였다(16-3). 누르는 횟수를 늘려서 풀 일이 아니었다.

실측:

```
claim-all: Lv.2 (pending 23) -> Lv.25   한 번에 23레벨, 남은 pending 0
```

### 곡선 재조정 — 하지 않았다

측정해보니 **곡선은 이미 목표를 만족하고 있었다.**

```
시뮬레이션 1~30스테이지: 스테이지당 최대 레벨업 = 2  (목표 0~2)
```

15단계의 pending 16은 곡선 문제가 아니라 **세이브 마이그레이션 결과**였다.
v4→v5가 레벨을 1로 시작시키는데(12단계 결정), 그 세이브는 이미 10스테이지라
경험치가 스테이지 10 속도로 들어온다. 요구량 합(Lv.1~16 ≈ 7,090)과 보유
경험치(10.5K)가 정확히 맞는다.

곡선을 건드리면 **정상 플레이어의 리듬만 망가진다.** claim-all이 마이그레이션
케이스를 처리하고, 곡선은 그대로 뒀다. `LevelUps_DoNotPileUp` 테스트가 이 관계를
못 박는다.

### 시뮬레이션-실전 EXP 일치

`SimulationExp_MatchesTheLiveCurve` 추가. 시뮬레이션이 부르는 함수와
`EnemySpawner.Spawn` / `BossFight.BossExpReward` 가 부르는 함수가 같은지,
1~30스테이지 전 구간에서 보스 경험치가 곡선과 어긋나지 않는지 검사한다.

## 16-3 스탯 포인트 증폭 축

### 결정: 하이브리드 (증폭 유지 + 크기 상향)

| | 전 | 후 |
|---|---|---|
| 포인트당 | ×1.005 (+0.5%) | **×1.025 (+2.5%)** |
| 축당 상한 | 500 pt | **200 pt** |
| 상한 증폭 | ×12.1 | ×139.6 (공격력 강화 **44레벨** 상당) |

상한을 함께 내린 이유: 포인트당 배수를 5배로 올리고 상한을 500에 두면 축당
**×230,000**이 되어 그 지점에서 골드 축 전체가 장식이 된다. 200에서도 실제
도달은 불가능하다(40스테이지에서 총 포인트 30개 남짓) — 상한의 역할은
도달점이 아니라 **폭주 방지**다.

순수 게이트(전투 기여 제거)도 검토했지만 택하지 않았다. 레벨이 전투에 아무것도
안 하면 "레벨업 버튼을 누를 이유"가 해금 시점 한 번뿐이 되고, 그 사이 수십
레벨은 다시 잡일이 된다. 크기를 키우는 쪽이 더 적은 구조 변경으로 같은 문제를
푼다.

### "투자 시점 ≥1% 체감" 테스트

`StatPoint_IsFeltTheMomentItIsSpent` — 초반·중반·후반(st5/12/20) 세 지점에서
포인트 하나를 그 자리에 투자했을 때 DPS와 EHP가 각각 1% 이상 움직이는지.
**상수가 아니라 시뮬레이션이 굴린 스탯에서 다시 계산한다.**

화면에서도 확인된다: `×1.160 → ×1.189` (전에는 `×1.000 → ×1.005`).

## 16-4 죽은 버튼 근절 — 변경 전 실패 확인

지시대로 테스트를 **변경 전 코드에 먼저 걸어** 실패를 확인했다.

```
StatPoint_IsFeltTheMomentItIsSpent
  stage 5: 공격력 증폭 한 칸이 DPS를 0.50%밖에 못 올린다
           (포인트 4개, 공격력 강화 Lv.24)
  Expected: >= 0.01   But was: 0.005
```

`PerPoint`를 1.005로 되돌려 찍은 결과다. 회복 축(11단계)·스탯 포인트
축(14~15단계)이 같은 함정에 두 번 빠졌고, 이제 세 번째는 빌드에서 걸린다.

### 기존 생존성 검사로는 왜 못 잡았나

기존 `EveryAxisIsBoughtAtLeastOnceThrough20`은 골드 6축만 보고, **스탯 포인트
축은 원리적으로 잡을 수 없다.** 포인트는 골드가 들지 않아 구매 정책이 무조건
찍기 때문이다 — 장부에는 "샀다"고 남지만 화면에서는 죽어 있다.

그래서 "샀는가"가 아니라 **"사면 움직이는가"**를 재는 테스트를 따로 넣었다.
`StatPointAxes_AreInvestedThrough20`(배분 여부)과 짝이다.

### 구매 정책 — 포인트 배분 규칙

> **다음 보스에게 죽지 않을 만큼까지는 체력 증폭, 그 뒤는 전부 공격력 증폭.**

골드 축의 정책("생존 먼저, 그 다음 화력")과 같은 규칙이고, 같아야 한다 — 두
재화가 다른 우선순위를 쓰면 시뮬레이션이 재는 것이 어느 쪽 플레이어인지 알 수
없게 된다.

### 곁다리로 잡은 버그 — 12단계에 심어둔 것

증폭을 ×1.56까지 올리자 **회복이 Lv.129까지 팔리고 체력은 한 번도 안 팔리는**
상태가 나왔다(생존 여유 0.65 = 죽는다).

원인은 12단계에 있었다. 그때 `MaxHealth`에 증폭을 곱하면서 구매 정책의
`healthGain` 비교는 증폭 **없는** 곡선값을 그대로 두었다.

```csharp
// 전: 증폭 있는 현재값 vs 증폭 없는 다음값  -> 증폭이 커지면 이득이 음수
HealthCurve.ValueAtLevel(levels.H + 1)
// 후
HealthCurve.ValueAtLevel(levels.H + 1) * levels.HealthAmp
```

증폭이 ×1.005일 때는 묻혀 있다가 ×1.56이 되자 비교가 뒤집혔다. **계수를
바꾸지 않았으면 이 버그는 계속 숨어 있었을 것이다.**

## 16-5 보스 여유 밴드 재검증

세 변경(회복 캡·claim-all·증폭 상향)이 전부 DPS/EHP를 움직여 밴드가 깨졌다.
증폭이 ×1.03 → ×1.60으로 자라면서 여유가 위로 샜다.

### 램프 재조정

`BossHealthRampFinal` **1.065 → 1.110**

램프는 스테이지마다 곱해지므로 후반에 권한이 크고 초반에는 거의 영향이 없다 —
하한(st1 1.79, st5 챕터 1.40)을 건드리지 않고 천장만 누를 수 있는 유일한 손잡이다.
1.080 → 1.095 → 1.110으로 세 번 측정해 잡았다.

### 피날레 보상을 골드에서 경험치로

램프만으로는 **st11이 2.9999**까지밖에 안 내려갔다(천장 3.0에 0.0001 여유).
원인은 st10 피날레의 골드 한 방이 즉시 화력으로 바뀌는 것이었다.

| | 전 | 후 |
|---|---|---|
| `FinaleGoldMultiplier` | 2.2 | **2.0** (챕터와 동일) |
| `FinaleExpMultiplier` | 3.0 | **4.0** (챕터의 2배) |

"피날레가 더 준다"는 설계는 유지하되 주는 재화를 옮겼다. 경험치는 레벨을 거쳐
들어오고 증폭은 포인트당 상한이 있어 다음 보스를 무의미하게 만들지 않는다.

### 최종 밴드

| 구간 | 일반 (1.5~3.0) | 챕터 (1.3~2.0) | 피날레 (1.15~1.7) | 생존 |
|---|---|---|---|---|
| **1~20** | 1.79 ~ 2.96 | 1.40 ~ 1.59 | 1.21 ~ 1.58 | ≥ 1.16 |
| **21~30** | 2.34 ~ 2.77 | 1.94 | 1.62 | ≥ 1.18 |

**21~30 드리프트가 같이 닫혔다.** 13단계에서 "이번 지시 범위 밖이라 보고만
한다"고 남긴 항목이다 — 그때 26~29스테이지가 3.01~3.27로 천장을 넘고 있었는데,
같은 램프 변경으로 2.34~2.77에 들어왔다.

### 무강화 게이트 유지

```
화력 게이트: 2스테이지   (지시한 값)
체력 게이트: 5스테이지   (화력보다 뒤 - 화력을 배운 뒤 체력을 요구)
```

회복 캡 후에도 두 게이트 모두 문다.

## 후속 수정 — 상단 EXP 막대 글자 넘침

스크린샷 확인 중 발견했다. 경험치 숫자가 막대를 넘어 레벨업 버튼과 겹쳤다.

```
막대 폭 342  vs  "21.5K / 12.3K" 13글자 x 28px = 364   -> 22px 초과
```

55pt는 아틀라스를 구운 크기라 글자를 줄일 수 없다(14단계). 줄일 수 있는 것은
**글자 수와 양옆 상자**뿐이다.

| | 전 | 후 | 실제 필요 |
|---|---|---|---|
| 레벨 라벨 | 260 | **200** | "레벨 999" ≈ 196 |
| 레벨업 버튼 | 300 | **250** | "레벨업 99" ≈ 224 |
| **EXP 막대** | **342** | **452** | 351 |
| 구분자 | `" / "` | `"/"` | 공백 2칸 = 56px 절약 |

회수한 130px이 그대로 막대로 갔다. 최종: 라벨 424×88에 필요 351×64.

### 고치다 만든 두 번째 버그

넘침 대비로 `overflowMode`를 `Ellipsis`로 바꿨더니 **숫자가 화면에서 통째로
사라졌다.**

Ellipsis는 가로뿐 아니라 **세로가 모자라도** 잘라내는데, 잘릴 것이 한 줄뿐이면
아무것도 안 남는다. 라벨 세로를 막대 높이(60)에 맞춰놨고 55pt 글자의 라인
높이가 그것을 넘었다.

세로를 위아래 14씩 넓혀(88) 풀었다. 세로로 넘치는 것은 애초에 문제가 아니었다 —
가로만 자르면 됐다.
