## K-0 이펙트 어긋남 — 원인은 앵커가 아니라 **회전**이었다

프롬프트의 진단 후보가 넷이었는데(앵커·회전·스케일·타이밍) 답은 회전이다.
23단계의 방법대로 시트를 다시 재서 산수로 나왔다.

```
피벗                     (31.5, 31.0) px
프레임 5~8 잉크 무게중심   (41.1,40.0) (42.3,29.9) (43.7,22.1) (41.5,18.5)
평균                     (42.2, 27.6) px
피벗 -> 잉크              (+10.7, -3.4) px  /  PPU 32  =  (+0.334, -0.106) u

114도 회전을 걸면 그 오프셋이 (-0.039, +0.348) u 로 돌아간다
x 스케일 1.15  ->  잉크가 앵커보다 0.40u 위에 뜬다
```

**회전은 피벗을 중심으로 도는데 잉크가 피벗에 없으면, 보이는 그림이 앵커에서
밀려난다.** 요괴 키가 1u이므로 0.40u는 머리 위다 — 스크린샷에서 "떠 보인" 것이
정확히 이 값이다.

22단계가 `slashOffset.y = -0.15`로 **절반만** 되돌려둔 것이 이것이고, 26단계에
아크를 되살리면서 그 보정을 빠뜨렸다.

### 손으로 고른 값을 다시 쓰지 않았다

이번에는 오의마다 각도와 크기가 다르다(일섬 수평 86도 x2.0, 귀참 광역 114도 x3.4).
손으로 잡은 오프셋은 각도 하나에서만 맞으므로, `SkillSlash`가 실측 잉크 오프셋에서
**계산**한다.

```
위치 = 앵커 - R(각도) x (잉크오프셋 x 스케일)
```

좌우 반전이 회전보다 먼저 일어나므로(flipX는 메시를 피벗 기준으로 뒤집는다)
잉크 오프셋의 x를 먼저 뒤집은 뒤 회전한다.

### 검증 — 실측 오차 0.0000u

```
귀참 (스케일 3.40, 각도 114도)
  transform  = (1.133, 0.033)     <- 보정이 1.18u 아래로 밀었다
  InkCenter  = (1.000, 1.217)
  요청 앵커   = (1.000, 1.217)     오차 0.0000u
```

`SkillSlash.InkCenter`를 진단용으로 내보냈다. 26단계의 어긋남은 "떠 보인다"로만
나타났고 그것을 숫자로 확인할 자리가 없었다.

## ★ 밸런스 가드 — 재확인

### 보스 여유 밴드: 26단계와 **소수 둘째 자리까지 동일**

```
        26단계                      27단계
일반    1.61 ~ 2.79                 1.61 ~ 2.79
챕터    1.37 ~ 1.71                 1.37 ~ 1.71
피날레   1.22 ~ 1.61                 1.22 ~ 1.61
생존    >= 1.16                     >= 1.16
1~5     175초                       175초
게이트   화력 2 / 체력 5              화력 2 / 체력 5
30까지  13.38분                     13.39분
```

**보스는 언제나 단일 대상이다.** 다타는 총량을 나눠 같은 대상에게 주고,
관통·광역은 대상이 하나면 한 번 준다. 그래서 어느 거동이든 보스에게 들어가는
총량이 같고, `StageSimulation`이 거동을 몰라도 틀리지 않는다.

### 총 데미지/캐스트 불변 — 오차 0

연참의 마지막 타격이 **나머지를 받는다.**

```
share = 총배율 / 3
마지막 = 총배율 - share x 2      <- 나눗셈을 한 번만 한다
```

셋으로 나눠 셋을 더하면 부동소수점에서 원래 값과 미세하게 어긋나는데, 그
어긋남을 허용하면 "총 데미지 불변"이 검사 가능한 성질이 아니게 된다 — 오차인지
설계 변경인지 구분되지 않는다. 테스트가 **delta 0**으로 12레벨 전 구간을 검사한다.

### 잡몹 파밍 속도: 변화 **정확히 0**

"미미해야 한다"고 하셨는데 미미한 것이 아니라 0이고, 그것이 구조적으로 보장된다.

```
st10 잡몹구간 4.0초   st20 4.0초   st30 4.0초
st30 보충간격 0.40초  (하한 0.40)
```

파밍 시간이 **이미 요괴 공급 하한에 붙어 있다.** 스폰 간격 하한이 0.4초이고
스테이지당 10마리이므로 4.0초가 바닥이다 — DPS가 아무리 높아도 다음 요괴가
오지 않으면 때릴 것이 없다(9단계에 만든 성질). 광역이 셋을 한 번에 베어도
다음 셋이 오는 속도는 그대로다.

## K-1 공통 주스

### 숫자 색 — 테스트가 두 번 물렸다

무기 등급 톤(흰/적/금)을 그대로 잡았다가 **화면에 이미 있는 색과 겹쳤다.**

```
연참 #FFF4E4  vs  평타   #FFF4D6   거리 0.05   거의 같다
일섬 #FF6A4A  vs  처치   #FF8A7A   가깝다
귀참 #FFD34D  vs  치명타 #FFD34D   거리 0.00   완전히 같다
```

치명타율 60% 구간에서는 화면의 큰 숫자 **대부분이 이미 금색**이라, 귀참 숫자가
치명타와 구분되지 않는다. 색으로 오의를 가르기로 했는데 그 색이 이미 쓰이고
있으면 설계가 성립하지 않는다.

`SkillShapeTests.SkillColors_AreDistinctFromTheDamagePalette`를 넣고 고쳤는데,
**한 칸 미는 것으로는 부족해서 한 번 더 실패했다** — 흰을 `#E8F4FF`로 잡았을
때도 평타와 거리 0.18이었다. 흰과 크림색은 RGB에서 원래 가까워서 청색을 실제로
섞어야 갈린다.

| | 최종 | 평타 | 치명타 | 처치 |
|---|---|---|---|---|
| 연참 | `#A8D8FF` 창백한 청백 | 0.39 | 0.78 | 0.69 |
| 일섬 | `#FF4A3A` 선명한 적 | 0.91 | 0.54 | 0.36 |
| 귀참 | `#FF9500` 깊은 호박빛 | 0.92 | 0.39 | 0.48 |

오의끼리도 0.37 이상이다. 팔레트는 **컴포넌트에서 읽는다** — 상수를 테스트에
복사하면 그 순간부터 자기 자신을 검사하게 된다.

> **남는 것 하나.** 일섬 `#FF4A3A`는 평타 타격 불꽃 `#FF453A`와 거리 0.02로 거의
> 같다. 그래도 둔 이유는 두 신호의 층위가 다르기 때문이다 — 불꽃은 12px으로
> "여기 맞았다"를 찍고, 일섬은 4.0u 아크와 x2 숫자와 이름으로 나온다. 크기가
> 스물다섯 배 다르면 색이 같아도 같은 것으로 읽히지 않는다. 검사에 데미지 숫자
> 팔레트만 넣은 것도 그래서다 — 숫자는 불꽃과 같은 크기·같은 자리에 뜨므로
> 색이 유일한 구분자이지만, 아크는 아니다.

### 오의 이름 플래시 — 다른 **종류**의 신호

26단계에 있던 신호는 전부 평타와 같은 종류였다(같은 스윙, 같은 타격음, 0.2초
아크, 치명타와 같은 단계의 숫자). 같은 종류의 신호는 아무리 키워도 "무엇이
나갔는지"를 말하지 못한다.

**평타는 이름이 없으므로 글자가 뜨는 것 자체가 오의라는 뜻이고, 어느 오의인지까지
한 번에 말한다.** 88pt 갈무리(제목 크기), 오의 색, 튀어나왔다가 떠오르며 사라진다.

두 번 고쳤다.

* **위치**: 처음에 지면선 위(+210)에 뒀다가 스크린샷에서 사무라이 발밑·지면 띠와
  겹쳤다. +460으로 올려 머리 위 빈 하늘에 세웠다.
* **그림자**: 데미지 팝업이 갖고 있는 것과 같은 이유 — **비트맵 폰트는 TMP의 SDF
  아웃라인을 쓸 수 없어서** 밝은 배경 위에서 글자가 사라진다. 연참이 청백색이고
  지역 1 배경이 하늘과 벚꽃이라 가장 위험한 조합이다.

### 히트스톱·셰이크 무게 차등

| | 히트스톱 | 셰이크 | 타격당 셰이크 | 숫자 크기 |
|---|---|---|---|---|
| 연참 | x1.4 | x1.1 | x0.55 | x1 |
| 일섬 | x1.9 | x1.9 | — | x2 |
| 귀참 | x3.0 | x2.8 | — | x2 |

**평타의 예산 계산 결과에 배수를 곱한다.** 고정 길이로 두면 공격속도가 오를수록
평타 정지만 짧아지고 오의는 그대로라, 후반에 오의 하나가 화면을 통째로 세우는
것처럼 보인다. 예산 규칙(CombatFeel)을 깨지 않는 이유는 시전 빈도다 — 7~22초에
한 번 0.15초를 멈춰도 초당 0.02초로 평타 예산 0.3초/초의 7%다.

무게 순서가 배율 순서와 같은지 테스트가 못 박는다. 어긋나면 화면에서 가장 무겁게
느껴지는 오의가 실제로 가장 센 오의가 아니게 되고, **히트스톱은 숫자보다 강한
신호라 그쪽이 믿긴다.**

## 클립 배정 — 팩에 이미 있는 것만 썼다

23단계의 방법(프레임별 잉크 오른쪽 끝 측정)으로 타격 프레임을 실측했다. 칼이
뻗는 프레임에서만 값이 튀고, 그 프레임이 원화가가 참격을 그려 넣은 자리다.

```
ATTACK 1 (7f)  f4  reach 1.38u  ink 808   <- 타격
ATTACK 2 (7f)  f3  reach 1.22u  ink 870   <- 타격
ATTACK 3 (6f)  f2  reach 1.34u  ink 749   <- 타격
SPECIAL  (14f) f5  reach 1.00u  ink 1140  <- 타격 (f0~4 준비, f6~13 마무리)
DASH     (8f)  f1~3 reach 0.72u          <- 자세만, 칼을 뻗지 않는다
```

| 오의 | 클립 | 재생 | 타격 프레임 |
|---|---|---|---|
| 연참 | ATTACK 1 + 2 + 3 이어 붙임 (20f) | 40fps / 0.50초 | 4, 10, 16 |
| 일섬 | DASH (8f) | 26fps / 0.31초 | 3 |
| 귀참 | SPECIAL ATTACK (14f) | 24fps / 0.58초 | 5 |

**DASH에 타격 프레임이 없다는 사실이 일섬의 설계를 정했다.** 돌진 클립은 베는
그림이 아니므로 베는 것은 아크가 맡는다 — 사무라이가 돌진 자세로 지나가고 수평
아크가 일렬을 가른다.

이어 붙인 클립의 타격 프레임은 빌더가 **각 시트의 실측 프레임 + 앞 시트 길이**로
계산한다. 숫자를 손으로 적으면 시트가 한 프레임 늘어나는 날 타격이 조용히
그림에서 떨어진다.

## K-2 연참 — 제자리 3연 베기

* 총 배율을 셋으로 나눠 그려진 참격 프레임에 맞춘다.
* **대형 아크를 쓰지 않는다.** 클립에 원화가가 그린 궤적이 이미 세 번 나오므로,

* 회당 작은 불꽃 + x1 숫자 + 짧은 셰이크. **히트스톱은 마지막에 한 번** — 중간
  타격에 정지를 주면 0.5초 동안 화면이 세 번 끊기고, 그것은 "연속 베기"가
  아니라 "느려짐"이다.

## K-3 일섬 — 돌진 관통

* DASH 클립 + 런지 1.25u (나갈 때 0.09초 ease-out, 돌아올 때 0.17초 ease-in-out).
  **나가는 쪽에 가속을 몰아주면 순간 이동에 가까워지고, 그것이 거합의 성질이다.**
* 17단계의 "사무라이 X 고정" 규칙을 깨지 않는다. 고정은 **전진을 배경이 만든다**는
  뜻이고, 돌진은 잠깐 튀어나갔다 돌아오는 것이다. 오프셋을 **매 프레임 기준점에서
  다시 놓으므로** 시전이 중간에 끊겨도 0을 쓰는 것만으로 복구된다.
* 관통: 전방 4.6u, 세로 2.6u 안의 살아 있는 요괴 전부. **세로를 함께 보는 이유는
  떠 있는 도깨비불이다** — 안 보면 지면의 요괴만 베고 도깨비불을 지나친다.

### 아크 각도를 한 번 틀렸다

수평 관통이니까 8도라고 잡았는데 스크린샷에서 거의 수직으로 나왔다.
**22단계의 관계식이 `보이는 각도 = aim - 90도`다** — 팩 아크가 세로 베기(-90도)로
그려져 있어서, 114도를 걸면 +24도(발도 방향)가 된다. 8 - 90 = -82도로 거의
수직이었고, 화면에서 "관통"이 아니라 "앞에 뭔가 섰다"로 보였다. **86도**(= -4도,
살짝 내려긋는 수평)로 고치고 크기도 1.5 → 2.0(4.0u)으로 키웠다.

실측: 런지 1.233u(사무라이 X −1.20 → +0.03), 관통 한 번에 숫자 둘(587·710)이
동시에 떴다.

## K-4 귀참 — 화면 광역

* SPECIAL ATTACK 클립(14f) — 팩에서 가장 긴 준비동작이다.
* 초대형 아크 x3.4 = **6.8u**. 카메라 월드 폭이 8.03u이므로 화면 대부분을 덮는다.
* 살아 있는 요괴 **전부**. 관통과 같은 코드를 큰 사거리로 쓰지 않은 이유는 뜻이
  다르기 때문이다 — 관통은 '경로'이고 광역은 '살아 있는 전부'다. 사거리로
  흉내내면 화면 밖의 요괴가 사거리에 들어오는 날 조용히 뜻이 달라진다.
  실측으로 화면 밖 x=4.7의 요괴까지 맞았다.
* 풀스크린 흰 번쩍(0.09초, 최대 알파 0.55) + 비네트(0.30초) + 최강 정지/셰이크.

### 번쩍은 unscaled로 돈다

23단계가 정한 규칙에서 화면 흔들림 하나만 예외였는데(정지 중에도 흔들려야 무게가
산다), 번쩍도 같은 이유로 예외다. 귀참은 강한 정지를 함께 내므로 스케일 타임으로
두면 번쩍이 정지 동안 멈춰 있다가 정지가 풀린 뒤에야 사라진다 — "멈추고 번쩍"이
아니라 "흰 화면이 한참 떠 있다"가 된다.

### 비네트는 코드로 굽는다

128px 방사형 알파. 불꽃·꽃잎과 같은 판단이다 — 필요한 것이 그라디언트 하나이고
그 크기에서는 그림 파일을 관리하는 비용이 아트보다 크다. **이 프로젝트에서
유일하게 Bilinear를 쓰는 텍스처**다. 부드러운 그라디언트라 Point로 두면 128px
계단이 화면 전체로 늘어나 띠가 보인다.

## 만들면서 잡은 것

### 꺼진 오브젝트의 Awake가 자기를 껐다 — **첫 시전이 통째로 삼켜졌다**

`ScreenFlash`와 `SkillNameFlash` 둘 다 Awake에서 `SetActive(false)`를 했다.
두 오브젝트는 꺼진 채로 씬에 저장되므로 **Awake가 씬 로드가 아니라 처음 켜지는
순간에 도는데, 켜는 쪽이 Play다.**

```
Play  ->  SetActive(true)  ->  Awake  ->  SetActive(false)  ->  끝
```

화면에서는 "귀참인데 번쩍이 없다"로만 나타나고 두 번째 시전부터는 정상이라
간헐적으로 보인다. 실제로 `flashActive=False`인데 `activeCasts=0`(시전은 끝났다)인
상태를 보고서야 잡았다.

이 프로젝트가 LockedTab·StatPointButton에 "꺼진 오브젝트의 Start는 처음 켜진
다음 프레임에 돈다"고 적어둔 것과 같은 함정이고, 여기서는 Awake가 **자기를 끄기**
때문에 한 단계 더 나쁘다.

고친 규칙 두 줄:

* Awake는 알파와 기준 위치만 초기화하고 **자기를 끄지 않는다.** 끄는 것은
  Update가 끝날 때와 빌더뿐이다.
* Play는 **활성화가 먼저, 상태가 나중이다.** `SetActive(true)`가 Awake를 그
  자리에서 돌리므로, 상태를 먼저 쓰면 Awake가 덮어쓴다.

### 오의 클립이 평타 스윙에 잘렸다

평타는 자기 타이머로 계속 스윙을 걸므로, 오의 클립이 도는 도중에 스윙이 걸리면
오의 동작이 첫 프레임으로 잘린다(26단계 메모가 예고한 자리). `IsPlayingOneShot`
동안에는 스윙을 걸지 않게 했다. **데미지는 그대로 들어간다** — 12단계 규칙대로
타이머가 결정하고 애니메이션은 장식이다.

### PlayerCombat이 "한 대"와 "한 시전"을 섞고 있었다

26단계에는 `CastSkill` 하나가 겨냥·한 방·정지·흔들림을 전부 했다. 셋 다 단일
대상 한 방이라 충분했고, 그 결과가 "색만 다른 같은 아크"였다.

거동이 갈라지면서 세 연출의 주기도 갈라졌다 — 연참은 타격이 셋인데 정지는 마지막
한 번, 귀참은 타격이 여럿인데 화면 정지는 한 번이다. 경계를 다시 그었다:

```
PlayerCombat    한 대가 무엇을 하는가       피해·불꽃·꽃잎·숫자·소리
SkillPerformer  한 시전이 그것을 어떻게 뿌리는가  안무·정지·흔들림·화면
```

12단계의 "한 함수 안에서 전부 난다"는 규칙은 그대로다 — 한 대의 다섯 연출은
여전히 같은 프레임에 난다.

## K-5 성능

풀링만 쓴다. `Instantiate`는 시전 경로 어디에도 없다.

| 풀 | 소유 | prewarm |
|---|---|---|
| 대형 아크 | SkillPerformer | 3 |
| 타격 불꽃 | PlayerCombat | 6 (기존) |
| 데미지 숫자 | DamageNumberSpawner | 12 (기존) |
| 꽃잎 | SakuraBurst | 기존 |

다타·광역이 늘리는 것은 숫자와 불꽃인데 둘 다 기존 풀이다. 실측 증식 0.
테스트 패널의 "풀 증식" 줄에 **참격**을 추가했다 — 26단계에 새 풀을 만들면서
세는 자리에 안 넣어서 그 풀만 관측 밖에 있었다.

오의 이름 플래시는 풀링하지 않는다. **인스턴스가 하나**이고 겹치면 나중 것이
이긴다 — 둘을 나란히 띄우면 어느 쪽이 방금 나간 것인지 알 수 없어서 이름을 띄운
목적이 사라진다.

**237/237 통과** (231 → +6)

| 테스트 | 막는 것 |
|---|---|
| `MultiHitShares_SumExactlyToTheTotal` | 다타의 합이 총 배율과 어긋남 (delta 0) |
| `PierceAndScreen_DealTheFullMultiplierPerTarget` | 관통·광역이 배율을 나눔 |
| `AgainstOneTarget_TotalPerCastIsTheMultiplier` | **보스 밴드 불변의 근거** |
| `Weights_FollowTheMultiplierOrder` | 약한 오의가 더 무겁게 느껴짐 |
| `SkillColors_AreDistinctFromTheDamagePalette` | 오의 색이 기존 숫자 색과 겹침 (2회 실패 후 통과) |
| `SkillColors_AreDistinctFromEachOther` | 오의끼리 색이 겹침 |

빌드 검사(`VerifySkillChoreography`)도 추가했다:

* 안무 개수·id가 카탈로그와 일치
* **타격 프레임 수 = `SkillCatalog.HitsPerCast`** — 어긋나면 총 데미지가 조용히
  바뀐다(셋으로 나눈 것을 두 번만 때리면 3분의 1이 사라진다)
* 클립이 비어 있지 않음
* **MultiHit이 대형 아크를 쓰지 않음** (23단계 이중 참격 재발 방지)

기존 밴드·시뮬레이션 테스트는 **하나도 고치지 않았다.** 밸런스가 안 바뀌었으므로
그대로 통과하는 것이 맞고, 실제로 그렇다.
