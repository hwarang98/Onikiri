## 0. 한 줄 요약

머리("클라우드 기록")와 요약("최고 43층 · Lv.65 · 로닌 · 보석 8717")이 **한 줄에 가로로**
나눠 서 있었다. 머리는 왼쪽 45%, 요약은 **전체 폭에 오른쪽 정렬**이라, 요약이 길어지면
왼쪽으로 뻗어 머리 위를 지났다. 카드를 **두 칸짜리 행**으로 만들고 머리를 위, 요약을
아래에 두어 **겹침을 구조적으로 불가능**하게 했다. 창은 526 → 658px, 마지막 행 아래
여백 48px은 그대로다.

## 2. 원인 — 폭으로는 막을 수 없었다

`StretchInside`는 `anchorMin.x`를 **항상 0**으로 두고 `anchorMax.x`만 받는다. 그래서
머리(`anchorMax.x = 0.45`)와 요약(`anchorMax.x = 1`)이 **같은 지점에서 시작하는 두 상자**가
되고, 요약은 오른쪽 정렬이라 글자가 길어질수록 왼쪽으로 자란다. `Ellipsis`가 켜져 있어도
기준 폭이 100%라 잘릴 일이 없었다 — 머리 위를 그대로 지난다.

### 2.1 실측 (에디터, 창 1008 기준)

| 항목 | 폭 |
|---|---:|
| 행 | 912 |
| 머리 상자 (45%) | 362.4 |
| 머리 글자 `현재 기기 기록` | 288.56 |
| 요약 상자 | **864 (전체)** |

요약에 남는 자리는 `864 − 288.56 = 575`다. 그런데 요약은:

| 요약 | 폭 | 판정 |
|---|---:|---|
| `최고 1층 · Lv.1 · 로닌 · 보석 0` | 445.68 | 안전 |
| `최고 43층 · Lv.65 · 로닌 · 보석 8717` (71.1 실기) | **560.68** | 여유 14px — 실기의 좁은 창에서 터졌다 |
| `최고 200층 · Lv.300 · 검귀 · 보석 30000` | 631.68 | **겹침** |
| `최고 999층 · Lv.9999 · 검귀 · 보석 999999999` | 741.68 | **크게 겹침** |

**요약은 값에서 나오고 상한이 없다.** 전직 이름만 해도 폭이 이렇게 흔들린다:

| 티어 | 이름 | 폭 |
|---:|---|---:|
| 0~4 | `로닌` · `무사` · `검객` · `검귀` · `귀장` | 66.01 |
| 5 | `데몬사무라이` | 198.01 |
| 6 | `진 데몬사무라이` | **240.21** |

이름 하나로 174px이 움직이고, 보석은 자릿수가 는다. 그래서 **폭 배분을 다시 고르는 것은
해법이 아니다** — 값이 자라면 또 터진다. 71.1 §8.4-2에서 한 번, 72 §4-2에서 한 번 밀린
자리다.

## 3. 고친 것

```
전   LocalCard(1칸)   [ 머리 45% | ........ 요약 100% 오른쪽정렬 ........ ]
후   LocalCard(2칸)   [ 머리 100%                                        ]
                      [ 요약 100%                                        ]
```

- `EnsureRow(panel, name, index, span)` — `span`칸을 먹는 행은 **칸 사이 간격까지 삼킨다**.
  그래야 `RowBottom(index)`의 식이 그대로 맞고, 72단계가 묶은 "마지막 행 아래 48px"이
  어긋나지 않는다. 다음 행은 `index + span`에 선다
- `StackInside(label, padding, minY, maxY)` — 라벨을 행의 **세로 한 칸**에 둔다. 두 라벨이
  가로를 통째로 쓰고 세로 칸만 다르면, 글자가 아무리 길어져도 서로의 칸에 못 들어간다
- 요약 정렬은 오른쪽 → **왼쪽**. 두 줄이 된 이상 머리와 같은 기준선에서 시작해야 읽힌다

## 4. 테스트 — 신규 7

| 검사 | 잠그는 것 |
|---|---|
| `Card_StacksTheSummaryUnderTheHead` ×2 | 요약 천장 ≤ 머리 바닥(세로로 갈림) **그리고** 둘 다 `anchorMin.x = 0` · `anchorMax.x = 1`(가로를 나눠 쓰지 않는다). 가로 배분이 돌아오면 여기서 먼저 걸린다 |
| `Summary_ClipsInsideItsOwnBox` ×2 | 넘치는 글자는 **제 칸 안에서** Ellipsis로 잘린다 |
| `Summary_FitsTheReachableWorstCase` ×2 | 닿을 수 있는 최장형(71.1 실기 계정 · 전직 5 + 보석 3만)이 칸에 든다 |
| `EvolutionNames_SwingTheSummaryWidth` | 전직 이름만으로 폭이 100px 넘게 흔들린다 — **이 설계의 전제**다. 전제가 깨지면(이름이 다 짧아지면) 가로 배분을 다시 따져볼 수 있다는 뜻이고, 그때 이 검사가 알려준다 |
| `TwoSpanCard_KeepsTheRowGrid` | 카드가 한 칸보다 크고, 카드 아래 간격이 정확히 행 간격(6)이다 — 격자가 어긋나면 창 높이가 틀어진다 |

**무회귀**: `UiLeftoversStep72Tests` 12개(창 높이 · 행이 창 안 · 마지막 행 아래 48 포함)가
그대로 통과한다. 72단계 검사는 상수가 아니라 **실제 rect를 읽어** 판정하므로, 행 높이를
키워도 계약이 유지되는지 그 검사들이 직접 확인해 준다.

## 5. 남은 것

1. **비현실적 최장형은 여전히 잘린다** — `진 데몬사무라이` + 보석 아홉 자리 = 915.89px로
   상자(864)를 넘는다. 잘려도 **머리를 덮지는 않으므로**(§4의 검사 둘) 이번 결함은 닫혔다.
   보석에 `NumberFormatter`를 물리면 해소되지만, 다른 화면이 보석을 날것으로 보여주므로
   **표기 일관성 판단이 따로 필요하다** — 이번 범위 밖으로 남긴다.
2. **실기 캡처 없음.** 72 §4-1과 같은 이유다 — 충돌 화면을 실기에서 띄우려면 옛 rev 세이브와
   사이드카로 서버와 일부러 갈라놓아야 한다. 이번 변경은 배치라 에디터 측정으로 판정했다.
3. 72 §4-3(전설 상한 → 파편을 "하락"으로 부르는 문제)은 그대로 열려 있다.
